Flock’s CLI talks to the running server over the same local socket API used by integrations and agents.

Most commands print JSON responses. Use them from scripts when you want deterministic automation.

When an existing status ping, submission guard, or failed command reveals a different server protocol, the CLI prints one warning to stderr per invocation. Read-only commands add no status probe; a state-changing command adds one ping per invocation, cached for the rest of it (see below). Unknown-method errors from older-protocol servers become `server_version_gap`, with the server version, protocol, required client protocol, and recovery command: `flk server live-handoff` (or restart the server). Surfaced failures return **exit code 78**; optional lookups that consume the error preserve the command's successful exit. Equal or newer protocols retain the original API error. Every state-changing command (`delegate start` and `send`, `agent start`, `restart` and `send`, `pane send-*` and `submit`, `worktree create`, `msg send` and `reply`, and the rest) checks the server protocol before its first state-changing request and refuses an older server with `server flk X (protocol N) is incompatible with client flk Y (protocol M)` and exit 78, so nothing is half-created. That check costs one ping per invocation. Read-only commands, `flk status` and `flk server` (including `live-handoff` and `stop`) still reach an older server, since handing it off is the fix. Diagnosis probes have a 500 ms timeout and reuse a server identity already obtained during the invocation. An unavailable probe leaves the original error intact. MCP tools return the same skew message with `error.data.refusal: "server_version_gap"`.

## Exit codes

`flk --help` lists every exit code, what it means and whether retrying is safe, from one registry (`src/cli/exit.rs`). Four cases moved in #1025, and for one release each prints `note: exit code is now N (was M); see CHANGELOG` on stderr when it returns its new code. stdout, `--json` output included, is unchanged.

| Case | Old | New |
| --- | --- | --- |
| send-like and guarded verbs (`agent send`, `agent restart`, `pane send-text`, `pane run`, `pane stash restore`, `msg send`, `msg reply`, `delegate send`, a rolled-back `delegate start`): refused before acting, nothing changed (`not_settled`, `input_not_empty`, `operator_active`, any error whose retry class is `later`) | `1` | `10` |
| `agent wait` / `wait agent-status --status settled`: the agent is blocked on a dialog | `3` | `6` |
| `delegate` awaits: `not_started` | `8` | `11` |
| `wait reply`, `msg send --await`, `msg status`: the receiver refused the message | `4` | `13` |

Every verb now exits what the error-code registry assigns its error, for send-like and guarded verbs too, which is also what MCP reports as `data.exit` (#1238, #1195, #1241). Three codes changed with no stderr notice: `server_version_gap` exits `78` (was `1`), and `questions_widening_refused` and `operator_only` exit `13` (were `1`). A `later` refusal from a send-like or guarded verb stays `10`, and every other code stays `1`.

## Output format and the error envelope

`--format json|text` is a global flag, and `--json` is its synonym (ADR-0029 §3). Where it may appear:

- **Before the verb**, always: `flk --json pane run 1-1 ls`.
- **Among the verb's own flags and operands**, for most verbs anywhere: `flk agent get w1 --format json` is `flk --json agent get w1`.
- **Never inside a verb's free text.** `pane run`, `pane send-text`, `pane send-keys`, `agent send`, `pane arm-self-compact` and the `rename` verbs (agent, pane, tab, workspace) end in words they type into a pane or store as a label. Those words start at the first word after the verb's operands (its target) that is not one of the verb's own flags, and from there on everything passes through verbatim: `flk pane run 1-1 git log --format=%H` types `git log --format=%H`, and `flk agent send w1 gh pr view --json state` sends `gh pr view --json state`. To switch the output of such a verb, put the flag before the verb or before its target.
- **Never after a `--`**: everything after it is left to the verb (`agent start <name> -- <argv>`, `pane run --if-input-empty -- <target> <text>`).
- `msg send` and `msg reply` read their own options anywhere in the message, `--json` among them, and take text that starts with a dash after `--`.

 Each verb keeps its default: most print JSON, and the verbs with a text form (`delegate status`, `worktree list`, `msg send --await`, `wait reply`, `events read` and the others that documented `--json`) switch to JSON with either spelling. `--format text` selects a verb's text form where it has one; a verb that only prints JSON keeps printing it. `pane read` and `agent read` keep their own `--format text|ansi` for the screen they return, so after those verbs only `--format json` is the global flag. A value other than `json` or `text`, or `--json` with `--format text`, is a usage error (exit 2).

Under `--format json` / `--json` an error prints on **stdout** as one JSON document, and a one-line human message (`error: <code>: <message>`) goes to stderr (ADR-0029 §4):

```json
{"id": "cli:agent:get", "error": {"code": "agent_not_found", "message": "…",
 "retry": "never", "exit": 1, "data": {…}}}
```

`id` is the id of the request that failed, or `null` when the client failed before or without a request (no server socket, a version gap found by the probe, a usage error). `code` is the error-code registry's (`src/api/error_code.rs`), `retry` is that code's retry class (`never`, `maybe`, `yes`, `later`, `after_inspecting`, `after_human`, `after_handoff`; a code the registry does not know, such as an older server's, takes the class of its exit status), and `exit` is the status the command exits with. The envelope prints once, as the command ends, so `exit` is always the process's exit status, a version gap's 78 included. `data` is the server's, when it sent one. So `flk agent get nosuch --json | python3 -c 'import json,sys; json.load(sys.stdin)'` always has a document to read. A refusal a send-like or guarded verb exits 10 on says `"exit": 10, "retry": "later"`; a not-found code exits 1 for now (ADR-0029 §2 assigns 4; #1151). A client-side failure is an envelope too: no server socket is `transport`, a timed-out read `timeout`, anything else `internal_error`, all exit 1; the version-gap refusal is `server_version_gap`, exit 78; a `delegate` usage error such as `not a delegate: <name>` is `invalid_params`, exit 2. A send whose effect is uncertain or abandoned (exit 8 or 9) is a result, not an error: under `--json` its result object is the stdout document instead of going to stderr.

Without `--format json` / `--json` nothing changes: an error is the one line on stderr it always was (the response JSON for most verbs), and stdout stays empty.

Known limit: other usage errors (exit 2) and some verb-local text failures (most of `delegate`'s exit-1 failures, the `--status settled` waits) still print only on stderr under `--json`, leaving stdout empty (#1150).

MCP tool errors carry the same `data.retry` and `data.exit` beside `data.refusal`, from the same registries: `exit` is what the matching CLI verb returns (10 for a `later` refusal of `flock_pane_submit`, `flock_msg_send`, `flock_msg_reply` or `flock_agent_restart`; 78 for `server_version_gap`; 2 for `not_exposed_via_mcp`; 1 for `transport_error`). An effect failure (MCP error code 8 or 9) adds `retry` and `exit` to the result it carries in `data`.

## Launch and status

```bash
flk                         # launch or attach to the default session
flk --session work          # launch or attach to a named session
flk --remote workbox        # attach through SSH, using local keybindings
flk --remote workbox --remote-keybindings server
flk --remote workbox --handoff
flk --no-session            # single-process escape hatch
flk --default-config        # print default config
flk update                  # download and install from the configured channel
flk update --handoff        # opt into live handoff for supported running servers
flk channel show            # print stable or preview
flk channel set preview     # opt into preview builds
flk channel set stable      # return to stable releases
flk --version               # print version
```

Status commands:

```bash
flk status
flk status server
flk status client
```

`flk status` also probes the selected installed launch path with `--version`, bounded to two seconds. It shows client, running server and installed executable versions, the launch path, and `client_drift` / `server_drift`. JSON includes an `installed` object. Missing, failed or timed-out probes report an error and unknown drift rather than claiming the versions match. Server drift is unknown when no server is running. `restart_needed` retains its client/server comparison.

Server status includes the API socket listener’s accept-error count, latest error, and `stopped` flag. Transient accept failures retry with exponential backoff from 50 ms to 2 s, reset on a successful accept. Invalid listener descriptors stop immediately; unclassified errors stop after five consecutive failures. Failure runs log on onset and recovery rather than on every attempt. Diagnostics remain until that listener is replaced. With `--json`, these are under `server.api_listener` (or `api_listener` for `status server --json`). Older servers report no listener diagnostics. A stopped listener cannot accept new status requests; its terminal error is also recorded in the server log.

## Peer enrollment

`flk peers` and `flk status` show each peer's name, pin direction, short node
ID, and enrollment state: `pending`, `pinned`, `retrying`, or `refused` with the reason.
The acceptor shows live inbound edges only; handshake refusals remain visible
on the dialer. Unknown handshake failures retry as transient failures.

During post-handoff recovery, status reports `mesh: recovering store after handoff`
while the server and panes keep running. Failed recovery reports the suspension
reason and retries every five seconds. Quarantined records
are reported as `mesh quarantined: N` when the count is nonzero;
`peers.enrollment` exposes the count as `mesh_quarantined`.

If a peer server is restarting or temporarily unavailable, held edges retry with
jittered exponential backoff with a ceiling that grows from 1 second to 30 seconds,
reset after successful enrollment. Retries occur on the configured gossip poll
cadence. Version or identity refusals retain a 60-second backoff and their reason
remains visible in status.

Inbound keys remain bound to their signed remote names. Configured peer aliases
supply local display names and may differ from those remote names. An inbound
peer claiming a configured peer's name must match that peer's configured pin.
If no pin exists, the first authenticated inbound contact pins both the
configured and inbound identity in one transaction. Fresh mutually configured
peers can enroll simultaneously. Status marks pins created by inbound contact
as `(first contact inbound)` and pins created by dialing as `(dialed)`.
This origin survives reconnects and restarts, including later outbound dials.
Pins created before origin tracking show `(pin origin unknown)`.
Verify inbound first-contact node IDs through a trusted channel, or use the
reset command below to enroll again.
With an older running server, the rest of status remains available and
enrollment reports `unknown (server predates mesh; restart needed)`.
`flk peers status --json` includes `source`, `node_id`, `pin_origin`, `enrollment`, and
`enrollment_reason`; `flk status --json` includes a `peers` array with the same
`pin_origin` values: `dialed`, `inbound_first_contact`, or `unknown`.

Each JSON peer row also includes `routes: [{node, name, next_hop, hops}]`
for destinations reached through that peer. Use `flk peers status --json` to
inspect destinations, next hops and hop counts. Routes use enrolled live edges in
either direction and disappear when their path closes. Healthy silence does
not expire a route; a last-known owner remains an offline hint, not a live
route. Unpinned names are marked `(advertised)` with an eight-character node ID suffix.

A node can accept up to 32 inbound relay edges. `peers status` lists each live
inbound edge separately. Each edge authenticates its own identity; a second hub
can connect without displacing the first. A newer handshake for the same node ID
supersedes the older edge. Resetting an inbound pin clears all edges enrolled
under that identity. Transient connection failures show `retrying` with the
reason; `refused` identifies a handshake or compatibility refusal.

Held SSH edges authenticate both node keys using fresh challenges and require
identical mesh protocol versions. Mismatches name both versions and say
`upgrade flk on <peer>`; upgrade the fleet together. First contact pins the
identity.
Enrollment uses trust on first use (TOFU): possession of a node key proves the
key holder, not that its claimed name belongs to the intended machine. Inbound
edges arrive over SSH into this host; a caller with that access who wins first
contact can claim an unpinned configured name. Both directions then trust that
first key and refuse a different one. Verify first-contact identities through a
trusted channel when that risk matters.
Pins survive restarts. An unexpected key change is refused as a possible
impersonation or re-key. After verifying the replacement, reset the pin from
the operator's shell and reconnect:

```bash
flk peers enroll --reset <peer>
```

The default reset clears the configured-peer pin. Use
`flk peers enroll --reset <peer> --direction inbound` for an inbound pin.
The command shows the direction, name, and node ID before clearing that pin.
Reset is refused with `operator_only` and exit 13 (1 before #1195) when
invoked from an agent pane or over MCP/relay; the operator's shell is the
trust boundary. Peers using incompatible versions or a
failing relay are refused with a concrete reason. Version refusals include
`upgrade flk on <peer>` (or `this node` when the local version is older); discovery does not fall back to one-shot SSH.

## Server

```bash
flk server
flk server stop
flk server live-handoff [--skip-undrained]
flk server reload-config
```

`flk server` runs the headless server explicitly. Use it for supervised or service-style setups. `reload-config` applies reloadable settings without restarting panes.

`live-handoff` moves every live pane to a new server process without stopping it, which is how an upgrade reaches a running session. The new server is the binary of the `flk` you ran, resolved through symlinks to its real path, and the importer must report that binary's version and protocol or the handoff rolls back and the old server keeps the panes. On a versioned install (Nix, or any `/store/<hash>-flock-<version>/bin/flk` layout) the old server's own path stays valid after an upgrade, so re-executing it would only restart the old version. When it finishes, the command prints both versions (`live handoff complete: server flk A -> flk B`) after the new server answers with the target version. It exits 1, rather than reporting success, when the new server is not the requested version, or when it is the same version the old server ran while the client is a different one. A client older than the running server (a stale `flk` earlier on `PATH`) refuses the default handoff instead of downgrading the server to itself, naming both versions and the client's path.

`--import-exe <path>` hands off to another binary instead, and is the explicit way to choose an older one. A relative path is resolved against your current directory before it is sent. Without `--expected-version`, its version is read from `<path> --version`, and a binary that reports the version the server already runs is refused while your client is a different one. `--expected-version` and `--expected-protocol` pin the importer's identity explicitly.

A client from before #958 does not send its own path, so the old server re-executes itself. For that first upgrade, name the new binary explicitly:

```bash
flk server live-handoff --import-exe "$(readlink -f "$(command -v flk)")"
```

When `flk` finds an older server, its `Flock was updated` message names both commands, before the stop-and-restart fallback that exits pane processes.

Before a pane moves, its queued input is written out before its terminal moves. All panes drain at the same time. If a pane's input does not drain within two seconds, or its terminal keeps accepting zero bytes, the handoff is refused. The old server keeps running with that input still queued, and the error names each stuck pane with its pending byte count, pid and title, for example `timed out draining PTY writes before handoff: w2:p6 (17 bytes pending, pid 4242, "zsh")`. Close those panes and retry, or pass `--skip-undrained` to hand off anyway: the stuck panes' pending input is dropped, and each is printed as `skipped undrained pane <id>: dropped <n> bytes`. If the handoff then fails at a later step, its error still lists the input that was dropped.

The old server writes the drain error, so a server from before this release still prints the bare `timed out draining PTY writes before handoff` and ignores `--skip-undrained`. The CLI then prints how to get off it. First, find the stuck internal pane numbers: grep the server log for `write returned zero bytes` and note each `"pane":N`. Map each `N` to its public id with `jq -r --arg n N '.workspaces[] | select(.public_pane_numbers[$n]) | "\(.id):p\(.public_pane_numbers[$n])"' session.json` in the data directory (numbers 1 to 9 read as they are, 10 is `pA`). Then close those panes and retry the handoff.

## Config

```bash
flk config check [--path PATH] [--json]
flk config edit
flk config reset-keys
```

`config check` validates a config without starting or touching a server, and exits on a three-way code so it can gate a deploy:

| Exit | Meaning |
| --- | --- |
| `0` | clean |
| `1` | loaded, with advisory warnings (removed or unknown keys, deprecated keys, keybinding conflicts) |
| `2` | did not load — a session would fall back to built-in defaults |

`--json` emits an object with `path`, `exit_code`, and `diagnostics` on stdout. Removed and unknown keys include file and line locations. Removed keys always produce exit `1`, even though the configuration loads successfully.

Every diagnostic is printed, unlike the in-app warning banner, which truncates to four lines. The check resolves keybindings in full, so conflicts and deprecation renames are caught rather than just TOML syntax errors.

`--path` checks a file that is not the live config, which is what a build-time gate wants:

```bash
flk config check --path ./config.toml || exit 1
```

Base and `config.local.toml` layering resolves exactly as it does at runtime. This is unrelated to `flk checks`, which runs the health-check runner.

## Preflight

```bash
flk preflight [--require TARGET]...
```

Answers one question: **is flock functional on THIS host right now?** `config check` proves the config parses; preflight also asks whether the things that config switches on are actually wired here. It exits on the same three-way code, so an activation or deploy can gate on it:

| Exit | Meaning |
| --- | --- |
| `0` | ready |
| `1` | works, but something wants attention |
| `2` | a configured feature is broken here |

It checks the config (by running `config check`), each agent integration, that the worktree directory is writable, and that `git` / `ssh` / `gh` are on `PATH`. Failures name the fix rather than the symptom.

**It never touches the network.** Preflight is built to run inside a Home Manager activation, so it cannot be allowed to hang one — peer reachability belongs to `flk status`, on a different clock.

### Why `--require`

An integration that is missing might be a deliberate opt-out, so flock will not fail your deploy over it on its own judgement:

| Hook state | Agent on this host | Result |
| --- | --- | --- |
| current | — | `0` |
| stale | — | `2` — it was wired and is now broken |
| missing | yes | `1` — might be intentional |
| missing | no | silent — not this host's business |

`--require TARGET` (repeatable) says *this deployment meant to have that one*, turning a missing hook into a `2`. flock cannot infer intent; the thing that deploys it can. A required target whose agent has vanished entirely still fails — passing quietly there would hide exactly the breakage this catches.

```bash
# In an activation: fail loudly if the Claude hook did not install.
flk preflight --require claude || exit 1
```

This matters because a half-wired host is silent by nature. Before the prompt-history panel read session transcripts it was fed purely by lifecycle hooks, so a host whose integration never installed showed an *empty panel* — indistinguishable from having no history yet.

:::note
A debug build reads `~/.config/flock-dev/config.toml`, so a debug-built preflight checks a different file than an installed one.
:::

## Worktrees

```bash
flk worktree list [--workspace ID | --cwd PATH] [--scan] [--json]
flk worktree create [--workspace ID | --cwd PATH] [--branch NAME] [--base REF] [--path PATH] [--label TEXT] [--focus] [--no-focus] [--json] [--dry-run]
flk worktree open [--workspace ID | --cwd PATH] (--path PATH | --branch NAME) [--label TEXT] [--focus] [--no-focus] [--json]
flk worktree remove --workspace ID [--force] [--json]
flk worktree kill (--workspace ID | --path PATH) [--dry-run] [--force] [--keep-branch] [--keep-procs] [--json]
```

Allocation commands (`worktree create`, `agent fork`, `agent start`, `workspace create`, `tab create`, and `pane split`) accept `--dry-run`. The server returns an `allocation_plan` JSON result with resolved paths, placement, and command arguments where applicable. It creates no directories, branches, workspaces, or terminal processes. A `pane.split` preview cannot predict a size refusal when the split is executed. Fork previews perform the same admission and transcript checks as a real fork. Generated branch names are chosen independently for each request; reuse the preview's branch and path explicitly to execute that plan. `agent start --dry-run --wait-ready` returns the plan immediately.

Worktrees are normal Flock workspaces with Git checkout provenance. `worktree create` creates a Git worktree checkout, opens it as a workspace, and groups it with the parent repo workspace. Without `--path`, Flock creates the checkout under `<worktrees.directory>/<repo>/<branch-slug>`. `--base` is refreshed from its remote first, exactly as `delegate start --base` does (below), and the ref and commit used are printed on stderr (`base origin/dev (<sha>)`). The TUI's new-worktree dialog refreshes its base the same way. The refresh happens in the CLI and the TUI's worker, never in the server: a raw socket `worktree.create` uses its `base` as written (see the socket API).

`workspace close` closes Flock state only. `worktree remove` is the explicit checkout deletion path; it runs `git worktree remove`, never deletes the branch, and requires `--force` when Git refuses a dirty checkout.

`worktree list` prints a table ordered stale-first: the repo's own checkout, then linked checkouts oldest work first. `AGE` is the last commit on the branch — deliberately not the directory's mtime, which a build that rewrites `target/` makes meaningless. `--scan` adds a `VERDICT` column (`merged`, `not_merged`, `open_pr`, `protected`, `unknown`) resolved through the same gate `worktree kill` runs, so a squash-merged branch reads `merged` here exactly as it does there; it is opt-in because it costs local Git plus a `gh` call per checkout. Absence of a verdict means "not scanned", never "not merged". `--json` prints the raw response, where the fields are `last_commit_at` and `kill_verdict`.

`worktree kill` is the scriptable twin of the TUI's "Kill worktree & branch": it runs the same merge gate (merged PR via `gh`, merged into a landing branch or the branch's own PR base, an unpushed branch with no commits of its own, or content already landed by a squash or rebase) and deletes the local branch only with positive evidence. Containment in some other remote feature branch is not evidence. A branch that heads an **open** PR is live work: `--dry-run` reports `open_pr: true` and `would_delete_branch: false` (exit 3), and a real kill is refused with `worktree_open_pr`, exit 10, before anything moves; `--force` does not clear it. `--keep-branch` removes the checkout alone, as does `worktree remove`. The same refusal reaches `delegate reap` of a delegate whose PR is still open. Address it with `--workspace ID` or `--path PATH`; a path that is open as a workspace closes that workspace too. `--path` is what makes a stale checkout nobody has open actionable at all — removing one with raw `git worktree remove` leaves the workspace pointing at a directory that no longer exists. `--dry-run` prints the gate verdict as JSON (exit 0 evidence found, 3 none); `--keep-branch` always preserves the branch; dirty checkouts exit 4 until `--force`. The landing branches (the detected default branch plus `dev`, `main` and `master`, and any `[worktrees] integration_branches` entry) and any `[worktrees] protected_branches` entry are kept under every path. See [Which branch counts as merged](/docs/configuration/#which-branch-counts-as-merged) for how that set is decided.

A kill also sweeps the processes left in the checkout. Removing a worktree unlinks a directory but does not touch the processes whose working directory it was, and a `setsid` child is out of reach of the pane teardown — those keep running against a path that no longer exists. Once the checkout is removed and the workspace is closed, anything still alive from inside it gets `SIGTERM`, a grace period, then `SIGKILL`. Matching is against the leaf checkout exactly, never the parent directory worktrees of a repo share, and the calling process and the shell it was typed into are never signalled. The result JSON carries `processes` (what was standing there when the kill began), `orphans` (what outlived the teardown) and `orphans_surviving` (what outlived `SIGKILL`), each as `pid` plus command name; the same is summarised on stderr. `--keep-procs` reports without signalling anything, and `--dry-run` names what is standing in the checkout without touching it.

## Panes

```bash
flk pane list [--workspace <workspace_id>]
flk pane get <target>
flk pane rename <target> <label>|--clear
flk pane split <target> --direction right|down [--cwd PATH] [--focus] [--no-focus] [--dry-run]
flk pane close <pane_id>
flk pane stash show|restore <pane_id> [--json]
```

Every pane verb takes a target: a pane ID, a terminal ID, an agent ID, a unique agent name/label, or `self` for the calling pane. A pane ID takes precedence over a same-named agent. Ambiguous names are rejected with candidate details; use a terminal ID or pane ID to select one. An unknown target is refused with `data.expected` listing these shapes. Against an older server, `flk` first resolves a name to its pane ID through `agent get`. It skips that step for an agent whose name is shaped like a pane ID (`w1:p2`, `p_3`, `1-2`), so on an older server such a name means the pane, not the agent.

Read output:

```bash
flk pane read <pane_id> [--source visible|recent|recent-unwrapped|detection] [--lines N]
flk pane read <pane_id> --source visible --ansi
flk pane read <pane_id> --source recent-unwrapped --lines 120
```

`pane read` scrapes what is drawn on the terminal. `recent` returns the bottom `--lines` rows of the screen, reaching further up when those rows are blank; `visible` is the user-visible viewport and follows the operator's scroll, so it is not a stable source for a script. For an agent TUI both give you that TUI's own chrome rather than its conversation — use `flk agent history <target>` for what the agent said.

Send input:

```bash
flk pane send-text [--raw] <pane_id> <text>
flk pane send-keys <pane_id> <key> [key ...]
flk pane run [--raw] <target> <command>
```

**Automated text never joins an operator's draft (#1162).** An operator half-way through a sentence in an agent's composer must not have flock, a script or another agent type onto it: the next Enter would submit both as one turn. Every verb that types into an **agent pane** (one running a harness flock reads: Claude Code, Codex, OpenCode) therefore checks the composer first, on the server, before writing anything:

| verb | the composer holds a draft | `--raw` |
| --- | --- | --- |
| `agent send` (submits) | a one-row draft moves aside and is typed back after the submit; a multi-row or chip draft refuses `input_not_empty` | refused: the guard is the point of the verb |
| `pane run`, `pane send-text`, `agent send --no-submit` | refuses `input_not_empty` | types onto the draft (`pane run` then presses Enter) |

A refusal exits **10** and types nothing; send again once the composer is empty. While a flock injection holds the pane, the typing verbs refuse `injection_pending` (exit 10) too: text held during the injection would replay after it, onto the draft it puts back. A shell pane (no harness, or one flock does not read) has no composer to protect and is typed into as before. The socket methods carry the opt-out as `raw: true` (see [Socket API](./socket-api.mdx)).

Why these verbs refuse instead of stashing: `send-text` and `--no-submit` leave their text in the composer, so a draft moved aside would have nowhere to go back to until a human submits. `pane run` confirms no turn, so it cannot tell when to put a draft back either, and it keeps its fast type-and-Enter contract (no idle requirement, no confirmation wait) for the callers built on it. Only `agent send`, which confirms its turn, stashes and restores. A draft over several rows or with a paste or image chip refuses even for a submit, because the screen cannot tell a typed newline from the harness's soft wrap and does not show a chip's content (#950 §2).

Known limits:

- The stash restore compares screen text (#850): a one-row draft comes back with the text it showed, but trailing spaces and where the cursor stood inside it are not preserved.
- Whether a pane is an agent pane is its effective agent label. After an agent exits, its label can outlive it until a hook or the detector clears it. While it does, the check still looks for that harness's composer: if the old composer is still drawn with text in it, `pane run` and `send-text` refuse (exit 10), failing safe; if a shell prompt has replaced it, nothing is found and the text is typed. `--raw` types regardless.
- The draft check reads the editor from the screen. When the editor is not on screen (a dialog over it, or OpenCode's busy footer while it works, #950 §4) no draft is visible and the text is typed. Automated callers should submit to agents with `agent send`, which also refuses a busy agent, and keep `--raw` for an operator who means it.

`pane send-text` reports the same observed delivery result and exit codes as `agent send --no-submit` (see below).

`pane send-text` uses bracketed paste when the terminal enables it and does not send Enter. Terminals without bracketed paste receive the text bytes directly. Embedded paste delimiters are removed when bracketed paste is enabled. Use `pane send-keys` for control keys such as `Enter`, `C-c`, or `Esc`; control bytes passed to `send-text` are pasted as text when bracketed paste is enabled. To submit a prompt to an agent, use `agent send`, which confirms the turn started, rather than `send-text` followed by an Enter key.

`pane run` types the command and then presses Enter, as two separate writes with a short pause between them. It is deliberately *not* atomic: a program reading a raw-mode stdin sees read boundaries rather than keystrokes, and agent TUIs use those boundaries to tell typing from pasting — text and a carriage return arriving in one read look like a pasted block containing a newline, so the newline is inserted and nothing is submitted. The pause is a heuristic, not a guarantee. A TUI that has not started reading stdin at all misses the text as well as the Enter; wait for the pane to be ready (`agent start --wait-ready`, `agent wait --ready`) before typing into a freshly started agent. `pane run` confirms nothing and needs no idle agent; in an agent pane the server checks the composer before the typed step and, on a draft, refuses it with exit 10 and sends no Enter. To submit a prompt and know whether a turn started, use `agent send`.

Arm a self-compaction of your own context:

```bash
flk pane arm-self-compact [--pane <pane_id>] [--abort] [--instructions <text> | --instructions-file <path>] <handoff prompt>
```

The one thing flock types into a pane on an agent's own instruction, and the reason it is a verb rather than a `send-text` is that it is not typing *at* the agent — it is the agent asking to be allowed to shorten its context and carry on. The prompt is the agent's own handoff to its next self: the text an operator otherwise copies out of the transcript and pastes back in.

The call **arms** and returns. Nothing is typed, because an agent calling it is mid-turn and its harness cannot compact inside a turn. Then, in order: the agent finishes the turn; once its pane is idle, settled and untouched by a human, flock types `/compact` and submits it; when the harness reports the compaction back through the session hook, flock types the handoff prompt in and submits it as the next turn. A harness that compacts on its own first — Claude Code does, exactly when the context fills up — is not a special case: the report still counts, and flock does not then compact a context that was just compacted.

Two writes and a signal, and the signal is a hook report rather than a timer — `session_start_source: compact` is the harness saying in its own words that the compaction happened. So the wait is bounded: `[session] self_compact_timeout_ms` (default 120 s), `self_compact_settle_ms` and `self_compact_fresh_ms` drop an arming the harness never confirms, naming in the log which half was lost. An arming that has not typed anything is never timed out, because an agent may legitimately be mid-turn for minutes. Flock never types over an operator: a quiet window, an empty prompt box, and a re-check immediately before each keystroke all stand between the arming and the pane.

If a compaction is already armed, a second arming is **refused** with `state: "pending"` rather than replacing the stored prompt — two written handoffs, and silently keeping one discards work the agent believed it had saved. `--abort` drops one. Claude Code only: `/compact` is a harness affordance, and another agent is refused by name instead of being armed into a no-op. Off `[session] self_compact` forbids it outright.

The continuation is checked before anything is typed. A prompt carrying a control or escape byte, an embedded line break, or a leading `/` or `!` is **refused with a reason** rather than scrubbed: the encoder wraps text between the bracketed-paste markers without escaping, so a prompt containing the closing marker would end the paste early and be read as keystrokes, and a leading `/` or `!` is a command the harness runs instead of instructions it reads. A scrub would report success for a plan that is silently missing part of itself.

`--instructions <text>` (or `--instructions-file <path>`, whose one trailing newline is dropped) steers the compaction itself rather than what comes after it: flock types `/compact <instructions>` as one paste, so the harness's summary keeps what the agent named — the goal, the status file's next step, open PRs, the standing rules — instead of whatever its default summariser picks. The handoff prompt still arrives afterwards as the next turn. Instructions get the continuation's checks except the leading-`/` one (they are an argument, never the start of a line): one line, plain text, at most **500 bytes**. That cap is far below the continuation's on purpose: Claude Code collapses a paste of roughly 800 characters or more into a `[Pasted text #N]` chip, and a collapsed `/compact <instructions>` may be sent as an ordinary message rather than run as the command. Name a file in the instructions if there is more to keep. Per harness: Claude Code's `/compact` takes them; Codex's and OpenCode's `/compact` take no argument, so instructions for those — or for an unrecognised harness — are refused rather than armed into a summary that silently ignores them. There is no fallback of typing them as a turn of their own first. Omitting them types a bare `/compact`, exactly as before. The answer carries `instructions: true` when they were stored; a client that sent them and gets an `armed` from an older server without that flag aborts the arming and exits 78 (`server_version_gap`) rather than reporting a success that lost them.

Both writes go through the same gates. Claude Code auto-compacts mid-turn, so a confirmation can arrive with the agent still working and a human part-way into a prompt; an occupied prompt box is never typed into, because submitting it would submit the human's draft too.

Over MCP the same thing is `flock_self_compact`, which is an allowlisted way an agent can affect its own pane — `pane.send_*` stays off the closed MCP table, and this is an allowlisted exception rather than an unlock.

Report agent state from custom hooks:

flk pane report-agent [<pane_id>] \

  --agent LABEL \
  --state idle|working|blocked|unknown \

The pane id is optional, as it is for `report-recap` and `report-reply`: name it as the leading argument or with `--pane`, and with neither the report lands on the calling pane — the one your hook is running in, resolved from `$FLOCK_PANE_ID` or from process ancestry. Agent targets can be terminal IDs, unique agent names, detected or reported agent labels, or legacy pane IDs. Names and labels are agent identities. Terminal IDs and legacy pane IDs are low-level escape hatches.

`pane run <pane_id> --if-input-empty [--min-age-secs N] [--if-session ID] <text>` uses the same server-side guard. It refuses a draft with `input_not_empty`; a harness's own hint in an empty box, such as Codex's `Ask Codex to do anything` or any suggestion Claude paints faint into its box, is not a draft, while typed text of any shape is. It refuses an unsettled status with `not_settled`, and a different session with `session_mismatch`. The guard and paste are serialized in the server, avoiding a client read-then-send race. `pane run` without `--if-input-empty` keeps its type-and-Enter behavior, refusing a draft in an agent pane (#1162) but requiring no idle agent. Socket clients can call `pane.submit` with `pane_id`, `text`, optional `if_session`, and `min_age_secs`; MCP clients use `flock_pane_submit` with the same fields. `delegate start` and `delegate send` also use this guard. An unconfirmed delegate submission preserves its workspace and new round cursor, so `delegate wait` can observe a later accepted turn without sending the brief again.

`agent send` moves a one-row draft aside and types it back after the submit, under the [injection lock](./configuration.mdx#injection-lock). While flock types, the pane's own input is held and replayed afterwards. A draft flock could not put back exactly is kept: `flk pane stash show <pane_id>` prints the kept drafts, one per line, and `flk pane stash restore <pane_id>` types the oldest one into the pane's empty composer. Add `--json` for the raw response. A restore refuses `input_not_empty` or `injection_pending` and keeps the draft.

Send outcome codes (`agent send`, `pane send-text`, and guarded `pane run`):

| Code | Outcome |
| --- | --- |
| `0` | `delivered`, `accepted`, or `observed_accepted` |
| `8` | `unconfirmed`: delivery or acceptance could not be confirmed. Reason `typed_not_submitted` means the sent text is still in the composer: inspect or clear it before retrying |
| `9` | `abandoned`: guarded submission stopped because its preconditions changed |
| `10` | refused before anything was typed (`not_settled`, `input_not_empty`, `operator_active`, `injection_pending`, …; the code is in the error JSON). Nothing changed, so send again once the condition clears (`1` before #1025) |
| `1` | API or transport failure |
| `2` | Invalid arguments |

Failure JSON remains on stderr. Guarded results include the delivery `attempt` evidence and `reason`. MCP `flock_pane_submit` uses the same numeric error codes 8 and 9, with the outcome as the error message and the complete result in error `data`. Raw paste tools remain unexposed via MCP.

`agent read` reads the resolved terminal stream. `agent send <target> <text>` **submits by default** (#995): it types terminal input (bracketed paste when enabled, so punctuation such as `!` stays literal input), requires a fresh idle agent with a recognized empty composer, waits 120 ms, and sends a negotiated Enter key event. The server observes acceptance for 2 seconds and retries **only Enter, once**, if the exact prompt, or the harness's folded paste chip in its place (Claude Code's `[Pasted text #N]`, Codex's `[Pasted Content …]`), remains in the composer and no operator input, dialog or execution change intervened. It then observes for another 2 seconds. Codex 0.160.1 is supported in both its default alternate-screen mode and `--no-alt-screen` mode. Unknown composers, and a chip next to other text, cannot authorize a retry. Embedded paste delimiters are removed when bracketed paste is enabled. Use `pane send-keys` for control keys such as `C-c` or `Esc` instead of embedding control bytes in the text. Do not follow `agent send` with `pane send-keys <pane_id> Enter`: the send already submitted, and the extra Enter lands on whatever the agent shows next. Use `agent send -- <target> <text>` for literal text beginning with `--submit` or `--no-submit`. `--no-submit` types only, without Enter: it observes the unscrolled composer (or newly visible text for ordinary terminals) for up to 2 seconds and reports `delivered` or `unconfirmed`, with a reason and before/after SHA-256 screen digests. Confirmation only reads the screen and never sends keys. Evidence `level` is `text_matched` when the changed region contains the pasted text, `composer_changed` when a recognized editor changed (including folded paste chips), or `screen_changed` for a weaker screen-only observation without a matching composer change. A `--no-submit` paste supports busy editors. Into an agent composer that holds a draft it refuses `input_not_empty` (exit 10) before typing, unless `--raw` is given (#1162). Repeated input is compared against the changed region, and whitespace is normalized across wrapped rows. A recognized composer that stays unchanged remains unconfirmed even while output streams elsewhere. `screen_changed` is the weakest evidence and is returned only at the two-second deadline, allowing late text or chips to provide stronger evidence first. A ticking clock or `tail -f` output can produce this level without proving that input reached the application. Retained rows shifted by scrolling cannot count as newly matched text. An unchanged screen remains unconfirmed. Operator input, an execution change, or pane disappearance interrupts observation with a specific `unconfirmed` reason. These observation levels never authorize a guarded-submit retry. Initial missing-runtime errors retain `agent_not_found` / `pane_not_found`; disappearance during observation reports `unconfirmed` with reason `pane_gone`. A submitting send reports `accepted` (matching prompt hook), `observed_accepted` (a new working entry), `unconfirmed`, or `abandoned`; the last two exit 8 and 9 respectively. `unconfirmed` with reason `typed_not_submitted` means both Enters went out, no turn started, and the composer still shows the text or its paste chip; any other `unconfirmed` reason leaves the composer state unknown. `abandoned` leaves the composer untouched. `--submit`, the old opt-in, is still accepted and changes nothing. Acceptance does not mark inbox messages read. `agent get`, `agent focus`, `agent wait`, and `agent attach` require the resolved terminal to have agent identity. `agent rename` can assign that identity.

Use `pane send-text`, `pane send-keys`, `pane run`, and `terminal attach` for ordinary terminals, servers, tests, shells, or low-level terminal control. Use `pane run` when you want to submit a shell command with Enter. Keep `pane send-keys` for real key input: answering a dialog, `Esc`, arrows.

`agent start --wait-ready` and `agent wait --ready` block until the pane reports an agent status other than `unknown`, then print the agent exactly as `agent get` would. `unknown` is the only status Flock reports when its detector has not recognised the agent's own chrome, so it is what a booting TUI looks like — for a Claude pane, for 30-60 seconds during which "still booting", "crashed on launch" and "blocked on a first-run dialog" are the same observation. Ready is the first moment the question is answerable, and the status it lands on is the answer: `blocked` returns immediately rather than waiting a dialog out, which `--status idle` cannot do. A wait that fails says what it saw — the last status and the last line the pane printed — and an agent whose pane exits during the wait ends it straight away with `agent_exited_before_ready` instead of running out the clock. A pane running something Flock does not detect never becomes ready; that is reported at the timeout rather than being papered over. The default timeout is 60s.

`--wait-ready` is opt-in and off unless passed. Because readiness is a detector verdict rather than a liveness check, **a headless agent never becomes ready**: `opencode run "…"`, a CI step, or anything that paints nothing while it works will sit at `unknown` for the whole window and then time out, however healthy it is. Do not pass `--wait-ready` to those; the start itself already refuses a child that dies in its first moments, and `pane_exited` reports the rest.

`agent start` with no placement is refused (`agent_placement_required`) unless the caller is running inside a pane of that server's session, because "the workspace you are looking at" is only an answer to a caller that has one — an `ssh` dispatch or a resume script is told to pass `--workspace`, `--tab`, `--cwd`, or `--active` instead of being placed wherever a human last focused. `--active` names the workspace being looked at; `--here` names the workspace the caller's own pane is in, read from its process ancestry, and is refused (`agent_here_unavailable`) when the server cannot place the caller in a pane. Naming two placements at once is refused (`agent_placement_conflict`). A `--cwd` naming a real directory that matches no open space still gets a space of its own, except under `--split`, which refuses there because there is no space yet to split.

Without `--split`, `--workspace` replaces the workspace’s only pane when it is an untouched root shell created by Flock. `--tab` does the same for a lone root shell in that tab. The pane must have been created with the default shell rather than a custom command, and must never have received input; shell startup scripts may still be running. Otherwise the agent opens a new tab, or a sibling workspace under `tab_mode = "workspace"`. An explicit `--split right|down` always requests a split. Replacement preserves the tab and public pane address, and a failed start leaves the shell running. A dry-run placement can differ from the real run if the shell receives input between the two requests.

**Every agent records where its questions go** (`questions`, ADR-0034 §2): `ask_human` (the harness shows its dialog to whoever watches the pane), `ask_operator` (nobody watches the pane, so questions go to the operator's queue), `route` (questions go to the architect) or `deny` (questions are refused with a reason). `agent start`, `agent fork` and `delegate start` default it from the starter: an agent started from an agent's pane reads `route`, one started by the operator reads `ask_human`, and one started with `--unattended` (or, once they exist, by the server itself for a cron, trigger or owner episode) reads `ask_operator`. `--questions` sets it explicitly. An agent may only narrow, to `route` or `deny`: asking for `ask_human` or `ask_operator`, or passing `--unattended`, from an agent's pane is refused with `questions_widening_refused` and **exit 13**, before anything is created. The policy is shown in `agent get` and `delegate list`, kept across a restart, a resume, a hibernation and a live handoff, and stamped into the agent's pane as `FLOCK_QUESTIONS=<policy>` on every launch (no variable for `ask_human`). The variable is only a hint for when the server cannot answer, never authority. An agent recorded before this release reads `ask_human`. Against a server too old to record a policy, the CLI says so on stderr and starts without it. Nothing acts on the policy yet: the question hooks that read it come in later releases.

`agent start` registers the name it returns itself, before the child has printed anything and independently of any hook the agent runs. The `name` in the `agent_started` result resolves with `agent get`, `agent read`, `agent send` and `agent wait` straight away, so `agent_not_found` for a just-started name is a real failure rather than a race. An agent name cannot look like a pane ID: targets resolve as a pane ID first, so a name written `1:p1` or `p_1_2` is read as that pane.

The stop-hook mail nudge names `flock_msg_read` and, if the MCP tool is unavailable, `flk msg read --pane <pane_id>` with the stopping pane’s ID filled in. Both read and consume the same inbox.

`msg status` and `msg list` include `attempts`: local wake submission evidence with an attempt id, pane, correlation ids, timestamps, retry flag and reason. Attempts progress through `queued`, `typed` and `submit_sent` to `accepted`, `observed_accepted`, `unconfirmed` or `abandoned`. A genuine inbox read during verification (or after an unconfirmed wake) records `read`; a read before Enter cancels the pending submission. An accepted wake does not mean the inbox was read: a message still in an inbox on this server stays `queued` until a genuine read, whether it took the mesh path or the older local one. Explicit guarded-submit responses carry the same evidence. Mesh attempt queries read the custody store; older local attempts use an in-memory registry restored from the retained audit window. Both restore during boot and live handoff. The registry targets 4,096 entries, matching mailbox history: completed attempts are evicted oldest-first. Pending attempts are never evicted. An unconfirmed attempt stays protected while any of its correlated messages is queued in any local mailbox; once none remain queued (including after expiry or dropping), it becomes eligible for oldest-first eviction on the next submission. Unconfirmed explicit submissions with no correlated mail are also eligible. No additional attempt TTL is used. New submissions are refused with `delivery_attempt_capacity` only if all slots are still protected. Restoring older logs with more protected entries preserves them and refuses new submissions until capacity is available. Mesh attempt recovery is independent of audit retention; older local attempt recovery is limited to the retained log window. Interrupted attempts become `unconfirmed` with reason `server_restarted`, and their keys are never replayed. Older pre-mesh `relayed` records still mean transport handoff, not a read receipt. Unconfirmed and abandoned attempts also appear in the digest. The optional System One advisory is deferred to Clef (#714).

Mesh `msg.status` reports `queued` (origin custody awaiting transport, or waiting unread in an inbox on this server, with `detail` saying which), `custody` (transferred custody), `delivered` (durable import into another node's inbox, still unread), `read`, `held` (answer awaiting return), `collected` (answer transferred to its origin), `undeliverable` (a forwarding hub could not deliver it), `expired`, or `outcome_retention_elapsed`. Refusals, undeliverable messages and collection failures include `detail`. `reply` contains the best imported answer independently of the original message state. Queries do not commit store changes. Read receipts return over authenticated collection, including the hub's collection exchange with a spoke.

A status result includes a signed `reference`. Retain it and pass it as `reference` to socket/MCP status or reply-wait calls, or as `--reference JSON` to `flk msg status` and `flk wait reply`, to query an exact message after outcome cleanup. A correlation alone cannot distinguish an unknown message from one whose retention elapsed. Status by correlation only answers for messages this node sent; a correlation another node reused for its own mail never stands in. `msg status` exits 0 for known nonfailure states, 3 for expiry, an undeliverable message, removal, elapsed retention or collection failure, 13 when the receiver refused the message (4 before #1025), and 1 for API errors.

`replyable` means a reply can be routed: a same-host sender pane, a sender agent the directory can resolve, or a durable mesh return binding. `msg.read` and the MCP channel push compute it the same way. `reply_contract` says which promise that is: `durable_return_binding` survives the sender being offline; `best_effort_local_or_directory` depends on the sender still being reachable.

`msg send` queues a message for another pane's agent; it is typed and submitted as a chat turn at that pane's next settled turn boundary, tagged with the sender pane and a correlation id the recipient can `msg reply` to. `<repo>:<pane>` splits only when the left side names a known repo; use `--repo` to be explicit. `--intent` says how much you need from the recipient, and it rides the envelope, so the recipient sees it before reading the body and `msg list` shows it on the queued row: `fyi` never wakes the recipient (it is read whenever the inbox next is), `needs-reply` marks the message as one you are owed an answer to and nudges the recipient at its next turn boundary, and `blocking` says you cannot proceed without one — it also puts the recipient in the operator's attention list and, if the recipient has muted itself, files an operator notification naming sender, recipient and count. `blocking` has its own per-sender budget, `[msg] blocking_per_hour`; past it the message is still delivered, as `needs-reply`, and the send result's `warnings` say it was downgraded. It defaults to `fyi` on the CLI — the MCP tool requires the choice instead, since an agent that never has to look at the field will not. Both verbs **refuse an option they do not recognise** rather than treating it as body text, and `--` ends flag parsing so a message may legitimately begin with dashes. Cross-host sends now persist custody before delivery and return a server-minted message key. A held authenticated mesh edge imports the message exactly once per key. A `delivered` result confirms inbox import; `queued` retains the message for retry after a disconnection or restart. An incompatible peer is named with `upgrade flk on <peer>`; sends do not fall back to a one-shot SSH command. `lineage` prints the fork ancestry chain of a pane, worktree, or branch — reconstructed from the durable event log, so it survives server restarts. `agent fork` branches the target's conversation into a new linked worktree: it creates the worktree, then starts a pane that resumes a fork of the agent's session, optionally seeded with a pivot prompt (`--pivot`; `<branch>` resolves to the final branch name, `--no-pivot` opts out of the configured template). Only Claude sessions can fork; other agents are refused with `unsupported_for_agent` because a plain resume would attach two processes to one session id.

`agent hibernate` parks a pane cleanly: the agent's child process is asked to exit, the resume plan is stashed on the terminal, and the pane is kept. The next focus (or an explicit `agent resume`) respawns it. Panes without a resumable session refuse with `hibernate_unsupported` (data-loss guard).

Hibernation survives a server restart, not only a live handoff: the stashed plan is saved in the session snapshot together with the agent's profile selector (the keys `[spawn.env]` declares, such as `CLAUDE_CONFIG_DIR`), so a cold-started server restores the pane hibernated and `agent resume` brings the agent back logged in to the same account. The selector is recorded when `agent start` carries it, when the agent's hook first reports its session, and again at hibernate. Every `agent` verb also takes the agent's `agent_id`, which is the address that survives a restart (terminal ids are re-minted and pane ids are placements).

Hibernating saves the session snapshot at once rather than after the usual save delay, so a server stopped (even with `kill -9`) right after `agent hibernate` returns still restores the agent hibernated.

When a live handoff is not possible, restart instead: `flk agent hibernate --all` before stopping the server, then after the start `flk agent list --resumable` and `flk agent resume --all`. Both `--all` forms print `{"results":[{"agent_id","name","pane_id","outcome","code"?,"message"?}]}` with an `outcome` per agent (`hibernated`/`resumed`; `skipped` with a `code` of `caller`, `already_parked`, `no_resumable_session` or `not_resumable`; or `failed` with the server's `code` and `message`) and exit 1 if any agent failed. Run from inside an agent pane, `hibernate --all` skips that agent (`skipped`, `caller`): parking it would kill the command halfway through. `agent list --resumable` prints the same object as `agent list`, `{"result":{"agents":[…],"fleet":[]}}`, with `agents` narrowed to local agents that have `"resumable": true` and `fleet` always empty (another server's agents are that server's to resume). `agent list` marks such agents `"resumable": true`; that also covers an agent a restart restored whose deferred resume has not run yet, which on a server with no client attached it never does on its own, so after an unplanned restart `resume --all` brings those back too.

`checks list` enumerates the runner's script checks together with the built-in state (blocked-alert / hibernation / issue-guard). `checks ack <name>` silences the next fire — for script checks the debounce window; for the built-in blocked-alert, the current in-flight episodes. `checks run <name>` forces a script check due right now.

## Goals

```bash
flk goal arm <goal> [--check CMD]... [--agent TARGET] [--json]
flk goal status [--agent TARGET] [--json]
flk goal pause [--minutes N] [--agent TARGET] [--json]
flk goal resume [--agent TARGET] [--json]
flk goal stop [--reason TEXT] [--agent TARGET] [--json]
```

An agent's goal (ADR-0030) lives on the server, keyed by the agent's id, so a restart or a pane move keeps it. `--agent` defaults to `self`, the agent whose pane runs the command; from a shell outside any agent pane, name the agent (its name, pane id, or `agent_id`; an `agent_id` with a goal works after its pane is gone). `arm` records the goal and its frozen checks, and refuses with `goal_already_armed` while one is open. `pause` without `--minutes` lasts until `resume`. `stop` drops the goal. `status` prints the goal, its state (`armed`, `paused until …`, `met`), checks, status, checklist and last verdict; `--json` prints the server's answer, `{"result":{"type":"goal","agent_id","goal":{…}}}`.

An agent may arm its own goal but not pause, resume or stop it; the operator and the agent's supervisor (the architect that delegated it) may do all four. Anyone else is refused with `goal_caller_refused` and **exit 13**. The check is cooperative until uid attestation (#1208): `setsid flk goal stop` from an agent passes as the operator. A timed pause that has run out shows as `armed`. The other refusals (`goal_not_armed`, `goal_not_paused`, `goal_already_armed`, `no_caller_pane`, `invalid_params`) exit 1. No refusal changes anything. Against an older server the four writes exit 78 before anything is sent, and `status` exits 78 too. See [Goals](/socket-api/#goals).

## Waits

Wait for output in a pane:

```bash
flk wait output <pane_id> --match <text> [--source visible|recent|recent-unwrapped|detection] [--lines N] [--timeout MS] [--regex] [--raw]
```

Wait for pane agent state:

```bash
flk wait agent-status <pane_id> --status <idle|working|blocked|done|unknown|hibernated|settled> [--after CURSOR] [--settle MS] [--timeout MS]
```

Wait for the answer to a message you sent:

```bash
flk wait reply <correlation_id> [--timeout MS] [--reference JSON] [--json]
```

Read or wait on the durable event log from a cursor you hold:

```bash
flk events read [--after CURSOR] [--kinds K1,K2] [--subject ID]... [--limit N] [--json]
flk events wait [--kinds K1,K2] [--subject ID]... [--after CURSOR] --timeout DUR
```

`events read` prints one JSON line per event (`seq`, `event`, `data`), oldest first, and `next_after: N` on stderr; resume with `--after N` and dedupe on `seq`. `--json` prints the whole reply. A `gap` on stderr means the cursor is older than what the server still retains. `--kinds` takes durable kind names (`message_queued`, or `message.queued`); `--subject` matches an id the event's data carries as a top-level value (a pane, workspace, agent or message id). `events wait` prints the first matching event after `--after` (default: now) and exits 0, or exits 124 at `--timeout` (`500ms`, `5s`, `2m`). The wait is held on the server, not polled. Against a server without `events.read` both exit 78. Prefer `events wait` over a loop around `agent get`. While it is held, `events wait` is a registered wait: an agent running it (in the foreground or as a background task) reads `phase: waiting_on_event`. See [Registered waits](/socket-api/#registered-waits). To follow agents, wait on the derived kinds: `flk events wait --kinds agent.phase_changed --subject <agent id>`, or `agent.needs_human`, `agent.limit_reached` and `agent.gone` (see [Supervisor events](/docs/socket-api/#supervisor-events)). To catch a question dialog, wait on `agent.question_opened`; `agent.question_closed` follows it (see [Open questions](/docs/socket-api/#open-questions)).

Bind a repo to its resident owner, end the binding, and read the bindings on this node (ADR-0035 §1):

```bash
flk owner bind <owner/repo> --checkout PATH --harness claude|codex|opencode [--model NAME] [--profile NAME]... [--json]
flk owner unbind <owner/repo> [--json]
flk owner list [--json]
flk owner show <owner/repo> [--json]
```

Each verb prints the server's reply (see [Owner bindings](/socket-api/#owner-bindings)) and exits 0. `bind` records the binding on the node whose server answers, which becomes the owner's home node; `--checkout` must name a git checkout on it (a relative path is resolved against the current directory), `--profile` repeats for the profile ladder, first choice first, and binding a bound repo again keeps its `agent_id`. `bind` and `unbind` are operator verbs: run from an agent's pane, relayed from a mesh peer, or from a caller whose pid the server could not read, they are refused with `operator_only` and **exit 13**, and nothing changes. That boundary is **cooperative only** until agents run as their own Unix user (#1208, #1177): a child an agent detaches with `setsid` passes as the operator. `unbind` and `show` of a repo with no binding exit 4 (`not_found`). A bad slug or checkout exits 1 (`invalid_params`), a usage error 2, and a server without the `owner.*` methods 78. Under `--json` every error is the envelope above.

Check a channel adapter's binding before the adapter starts:

```bash
flk adapter hello <binding> [--token-file PATH]
```

Prints the `channel.hello` reply (binding, owner node, target, scopes) and exits 0. Exits 1 with `channel_unauthorized` (unknown binding or wrong token) or `channel_not_owner`, and 78 against a server without `channel.hello`. The token is read from the binding's token file unless `--token-file` names another one. See [Channel adapters](/socket-api/#channel-adapters).

Show or adopt a repo's owner policy, the `[owner]` section of `.flk.toml` committed on its default branch:

```bash
flk owner policy show [--repo PATH]
flk owner policy adopt <VERSION|none> [--repo PATH]
```

`show` prints the current version (the blob id), the adopted one and whether a merged change is `pending`. `adopt` takes the version `show` printed (`none` when the default branch has no `.flk.toml`) and makes it apply. It is an operator verb: from an agent pane it exits 13 (`operator_only`). It exits 1 with `owner_policy_changed` when the default branch has moved past that version, and 78 against a server without it. `--repo` defaults to the current directory. See [Owner policy](/configuration/#owner-policy-flktoml).

Use `wait output` for normal commands and servers. Use `wait agent-status` for coding agents. Use `wait reply` after `msg send --intent needs-reply`: it prints the reply body to stdout and metadata to stderr, or the full result with `--json`. A sender outside any pane can wait for its held answer. `msg send --await` sends and uses the same waiter and exit codes:

| Exit | Reply-wait outcome |
| --- | --- |
| `0` | `replied` |
| `3` | `deferred`, `expired`, `undeliverable`, `recipient_gone`, or `outcome_retention_elapsed` |
| `13` | `refused`; `detail` gives the reason (4 before #1025) |
| `124` | `timeout`; accepted mail continues retrying |
| `1` | API or transport error |

`recipient_gone` means the owner permanently removed that agent incarnation,
not that its host is offline. `outcome_retention_elapsed` means the retained
result has been collected by GC; it makes no delivery claim. Keep the signed
`reference` from `msg status` and pass `--reference JSON` to query that exact
message after cleanup. A correlation alone cannot prove elapsed retention.

`agent restart` returns after scheduling the restart. Finish the requesting turn normally: Flock waits for a settled idle prompt, stops the agent process tree through the runtime, and resumes the same conversation with its original executable, flags, profile environment, cwd, and agent name. `self` requires the caller to be inside the agent pane; an explicit target accepts the usual pane ID, terminal ID, or unique name.

`--continue-with` supplies the next instructions. Prefix a file path with `@` to read them from a file. Instructions must be a single line of plain text, at most 16 KiB; a terminal newline in the file is removed. The default is “You restarted yourself for: <reason>. Continue your task.” Flock queues this through the message inbox/wake path after verifying a fresh report of the same session and an empty idle composer recognized for Claude Code, Codex, or OpenCode. An unrecognized composer remains unconfirmed; verification timeout reports `unknown_composer` instead of sending the continuation.

A configured hard limit or the grace deadline can force a restart mid-turn. The continuation then names the limit, warns that the last tool call may be incomplete, and lists stopped processes and reported background tasks. A failed flush check is disclosed. Unknown startup dialogs and credential prompts are left for the operator; verification timeout emits `restart_stuck` with a screen excerpt. Repeated restarts stop the agent at the rate cap; `agent resume` explicitly releases that stop. See [restart configuration](/docs/preview/configuration/#agent-restarts).

### Waiting for an agent to go quiet

Both wait verbs take the same seven statuses and mean the same things by them. `idle` is **ready for input**, and it matches `done` as well — an agent nobody is watching goes quiet as `done`, which is an effective idle, so `--status idle` is the way to wait for an unattended agent in either verb. `--status done` means exactly `done`. (`flk wait agent-status --status idle` used to match only a literal `idle` and therefore hung on every unattended agent, which is the hang #553 reports.)

`--status settled` is the one to reach for from a supervisor. It is **observed quiescence**, and the distinction is the whole point:

```bash
c=$(flk agent get worker | jq -r .result.agent.turn_cursor)   # capture BEFORE prompting
flk agent send worker "..."
flk agent wait worker --status settled --after "$c" --timeout 3600000
```

`settled` means: after that cursor, the server saw this agent enter `working` (or the cursor was captured while it was already working), and then saw its reported status hold `idle`/`done` with **no state transition at all** for the settle window. Anything in between resets the dwell — including `idle -> blocked -> idle`, which is why the dwell is anchored on a transition counter rather than on the status alone. `--settle MS` sets that window and defaults to `5000`; `--settle 0` settles on the sample after the first qualifying one. Without `--after`, any quiet counts — an agent that is already idle settles after one settle window, so capture the cursor before you prompt.

**It is not proof that a turn produced a result.** It says what Flock observed; for the turn's output use `flk agent result` (once #575 lands). Two consequences follow. Native Claude and opencode agents are read from the screen every 300-500 ms, so a working phase shorter than one sample is never observed — a cursor captured before one waits for the *next* turn instead. And `working_entries` counts *observed* entries, not submitted prompts: capture the cursor after the agent is at its prompt and before you prompt it.

The cursor itself is the `turn_cursor` field on `agent get`, `agent list` and `pane get` — `"{terminal_id}:{execution_epoch}:{working_entries}:{state_seq}:{w|i}"`, opaque to callers. It never satisfies a wait on another terminal or another execution, and one whose counters the server has not reached is refused rather than waited out, so a typo cannot read as "it already worked".

On success `settled` prints one JSON object on stdout:

```json
{"status":"settled","pane_id":"1-1","agent_status":"idle","turn_cursor":"term_1f2e3:0:2:7:i","held_ms":5003}
```

`flk wait agent-status <pane> --status settled` is the same signal with the same result line — a supervisor can use whichever verb fits the command it already has. Exit codes for `--status settled`: **0** settled · **6** blocked (a human has to look; 3 before #1025) · **4** gone, with `"reason":"closed"|"hibernated"|"restarted"` on the line · **124** timeout · **2** a usage error or a refused cursor · **1** any other error. The non-settled statuses keep their historical codes, including `1` for a timeout.

`--after` and `--settle` mean nothing without `--status settled`, and a non-numeric `--settle` or `--timeout` is a usage error: all of these exit `2` before any request is sent, so a typo does not cost you the wait.

### Delegating a task

```bash
flk delegate start <name> --brief FILE (--cwd PATH | --worktree --branch B [--repo PATH] [--base REF])
                    [--harness opencode|claude|codex] [--model M] [--sandbox MODE] [--await] [--timeout MS] [--settle MS]
                    [--ready-timeout MS] [--max-chars N] [--keep-on-failure] [--label TEXT] [--questions POLICY] [--unattended] [--json]
flk delegate send <name> --brief FILE [--await] [--timeout MS] [--settle MS] [--silence DURATION] [--ready-timeout MS] [--max-chars N] [--json]
flk delegate wait <name> [--after CURSOR] [--timeout MS] [--settle MS] [--silence DURATION] [--max-chars N] [--json]
flk delegate result <name> [--max-chars N] [--json]
flk delegate status <name> [--json]
flk delegate reap <name> [--force] [--json]
flk delegate list [--mine | --architect <id> | --all] [--branch <b>] [--json]
```

**After a compaction an architect gets its delegate table back without asking.** On a session start with `source` `compact` or `resume`, flock's own SessionStart hook asks the server for `delegate list --mine` and, when the agent has open edges, returns the table as hook output: at most 10 rows, then a `+k more: flk delegate list --mine` line. Nothing is typed into the pane, so an ordinary auto-compaction gets it as well as an armed self-compaction, whose continuation still arrives as before. Claude Code and Codex receive it as SessionStart `additionalContext`. opencode's plugin adds it to the compaction context through `experimental.session.compacting`. A harness with no session-start hook gets no table: its architect calls `flock_delegate_list` (or `flk delegate list --mine`) itself after a compaction.

Codex defaults to `--ask-for-approval never --sandbox workspace-write`. Workspace-write blocks the network, so a delegate that must `git push` or use `gh` needs `--sandbox danger-full-access`, deliberately chosen by the caller. `--sandbox` accepts `read-only`, `workspace-write`, or `danger-full-access` for Codex only; opencode and Claude reject it with exit 2.

`flk delegate` and `flk agent result` use capabilities first shipped in **0.9.0**. If a request fails because a capability is missing, they check the server version best-effort. A confirmed older server gets a diagnostic naming the required and running versions and `flk server live-handoff` or upgrade guidance. If the version is unknown or already 0.9.0 or newer, the original error is preserved.

`delegate` is the sequence above run as one command: create the space, start the harness in it, wait until it is actually up, type the brief, and — with `--await` — wait for the round's outcome and print it. It is composed from socket methods that already existed, so it adds no new protocol; what it adds is the bookkeeping that was previously in somebody's shell history.

The brief is a file, and exactly one sentence is ever typed into the agent: `Read <absolute path> and execute it exactly.` The path is made absolute without resolving symlinks, and is refused if it contains whitespace, a control character, or any of `` ! $ ` " ' \ `` — the path crosses the agent's shell, and a quote that survives that hop names a different file by the time the agent reads it. Put the instructions in the file; the typed text carries nothing else.

The delegate runs in a workspace it created and **never requests focus**, so your focus is unchanged by any of these verbs and a delegate never lands in the workspace you are looking at. With `--worktree` it makes a linked checkout (`--repo`, `--branch`, `--base`; those three mean nothing with `--cwd` and are refused there) and the agent's cwd is that checkout. A relative `--repo` or `--cwd` is resolved against your current directory, like the brief, before anything reaches the server, so `--repo .` is the directory you are in. A `--repo` that is a linked worktree (or, without `--repo`, a current directory that is one) is swapped for its repository's main checkout, which is where `worktree.create` starts, and the swap is printed; without `--base` the new branch starts from the linked worktree's HEAD, so it forks from the checkout you pointed at. A linked worktree of a bare repository has no main checkout and is refused with exit 2. `--base` is fetched from its remote first: a branch name such as `dev` resolves to `origin/dev` (or the branch's configured remote) unless the local branch has commits the remote lacks, an explicit `origin/dev` is fetched and kept, and a tag, a commit id or `HEAD` is used as written, without a fetch, with the commit it names. A branch the remote does not have is told apart by `git ls-remote --exit-code`, not by git's error text, and a remote that cannot be reached within 20 s is reported (`could not reach origin`). The ref and commit used are printed with the start (`base`, `base_sha` in `--json`); a fetch that fails is reported and the refs on disk decide.

`--harness` is `opencode` (the default) or `claude`, and `--model M` is handed to it as `--model M`. The two differ in where the session comes from, which is what `no_result` reports: opencode's plugin names it mid-turn, Claude's `SessionStart` hook names it from inside the harness.

**The brief is only typed into an agent that is at its prompt.** `start` and `send` both wait out a permission prompt rather than answering it, and time out with the status named (`delegate <name> is blocked`) rather than typing into a dialog. That wait also covers readiness — a pane that has painted nothing yet reports `unknown`, which is a booting TUI, not a crash. Claude Code asks `Quick safety check: Is this a project you created or one you trust?` the first time it starts in a directory, and a `--worktree` checkout is always such a directory: that dialog has no input box, so the delegate names it (`delegate <name>: Claude Code is waiting on its folder-trust dialog (see #605)`) and refuses instead of typing at it. When the directory is a linked worktree of a repository already trusted in that Claude profile, flock records the worktree as trusted before starting `claude`, so the dialog does not appear (#605, `[worktrees] pretrust_claude`); anywhere else accepting it stays a human action. Codex has its own `Trust this folder?` dialog for a repository it has never trusted; the delegate names it `codex_folder_trust` and refuses the same way. Codex records trust for the repository root, so accepting it once in the main checkout covers every later worktree of that repository. `delegate status` names a startup dialog the agent is blocked on (`startup_dialog` in `--json`).

A Codex that is still starting can swallow the typed brief: the composer stays empty and no turn begins. When a Codex submit cannot be confirmed, `start` watches for the same evidence `not_started` uses — an empty idle composer, no turn and no queued or startup marker, held for 30 s plus `--settle` — and only then types the brief once more. A brief that appears anywhere on screen, or a turn that starts late, is never typed again. opencode keeps its rule that a dropped brief is reported, not retyped.

`--await` stays and reports the round's outcome. Settling is not finishing: an agent goes quiet between tool calls, so the await settles and then waits a further grace for a reply recorded at or after this round's submit. A round is therefore only reported when the agent entered `working` after that round's cursor **and** a reply exists from after the submit — a fix round is not reported from the quiet that preceded it, and not from the previous round's reply. A settle is never reported as `no_result` while the store records a turn begun at or after the submit that has not ended (`turn_open_at_ms` on `agent.result`, Claude only): the screen can read idle inside a running turn, so the await settles again from the same cursor and asks the store again, and the round ends only on a reply, a turn the transcript records as over, or the usual blocked, gone, stalled and timeout outcomes (#1257). A turn the transcript closes without a `turn_duration` entry — a resumed session's `No response requested.`, an interrupt, a local command — counts as over (the rules are under `agent.result` in the socket API), so such a round ends as usual, typically `no_sentinel` or `no_result` (exit 5), and the caller re-waits or re-sends. Against an older server, which never reports an open turn, the grace behaves as before. Codex delegates are not covered: a Codex reply ending on `VERDICT:` reported as `no_result` is [#1268](https://github.com/gerchowl/flock/issues/1268). `--timeout` bounds the await only and starts after the submit (for `wait`, at command entry); `--settle` defaults to 5000; `--max-chars` pages the reply.

Exit codes: **0** a finished reply ending on `DONE:` / `VERDICT:` · **3** a `BLOCKED:` reply · **4** the agent's pane closed, hibernated or restarted · **5** a finished reply with no sentinel, or none inside the grace · **6** the agent sitting on a prompt (`blocked`) for the settle window · **7** a stalled round · **11** `not_started` (8 before #1025; continuously idle with an empty composer for the startup window and no new turn since the submit cursor) · **75** `server_unavailable`: the server stopped answering inside the reply grace for 5 minutes, which says nothing about the agent · **78** server protocol mismatch · **124** the timeout · **2** a usage error, or a name that is not a delegate · **10** the composer refused the brief before typing (`delegate send` restores the registry; `start` only when it rolled back) · **1** any other failure. With `--json`, exits 0, 3, 4, 5, 6, 7, 11, 75 and 124 print the same object (a usage error, exit 2, and failures other than readiness expiry, exit 1, print nothing on stdout, only the error on stderr), and its `turn_cursor` is the cursor that await started from — so a timed-out caller resumes with `--after <turn_cursor>` and gets the same round. Without `--json`, stdout is the reply's text and stderr is one summary line.

Write the brief so the agent ends its reply on a final `DONE: …`, `BLOCKED: …` or `VERDICT: …` line: that line is the whole result contract, and a good reply ending on anything else is `no_sentinel` (exit 5). A trailing `※ recap` line after it is fine.

When `start` runs inside an agent's pane, the server records that agent as the delegate's architect (an `agent_delegated` event in the durable event log). `--label TEXT` is stored on that record and defaults to the delegate's name; against a server too old to store it, `start` says so on stderr and starts without it. A `start` whose process ancestry reaches no agent pane (the operator's own terminal, `ssh`, or a spawner that detached with `setsid` or `nohup`) records no architect and prints `delegate <name>: edge: none (unattested)` on stderr.

`list` reads those records back from the server, grouped per architect: `--mine` (the default) is the agent whose pane runs the command, `--architect <id>` names one, and `--all` shows every architect, one block each. `--branch <b>` returns the edge that owns that branch. Each row carries the delegate's name, its edge state, `agent_status` and how long it has held it, harness, branch, the PR the poller last saw (number and state), the edge's age and its label. The state is `live`, `hibernated, awaiting merge` (hibernated with an open PR), `gone` (removed), `gone, worktree retained` (removed, its worktree still on disk), `orphaned` (its architect is gone), or `closed, not merged`, which a PR closed without merging shows whatever else holds, including a batch-landed `landed-in-batch` PR. Everything comes from state the server already holds, so `list` runs no git or `gh` command and the PR can lag GitHub by one poll. `--mine` from the operator's own terminal, which runs in no agent pane, fails with `no_caller_pane` and names `--all`. `--json` prints the verb's result as is, the same object MCP `flock_delegate_list` returns.

A start that fails once its agent exists (readiness timed out, a startup dialog, a composer that refused the brief with `input_not_empty`) prints the agent pane's last 20 lines on stderr, each behind `  | `, read before anything is torn down, so a rolled-back start still shows what the agent was showing. It then rolls back the workspace and checkout as before; a composer refusal that rolled back cleanly exits 10 (1 before #1025), since nothing was typed and nothing persists. With `--keep-on-failure` it keeps them instead, with the agent and the delegate's record, and exits 1: `delegate status` reads it, `delegate send` types the brief once the composer is clear (a start refused before typing ran no round, so that is round 1), and `delegate reap` removes it. `--keep-on-failure` also keeps the workspace and checkout when the server refuses to start the agent at all; there is no agent pane then, so no lines are printed, `delegate status` reports it as `not_started`, `delegate send` refuses it as `gone`, and `delegate reap` removes the workspace and checkout. Under `--json` the same lines are structured: a start that failed once its agent existed, including one whose brief submission could not be confirmed, prints one `start_failed` outcome (`reason`, `kept`, `pane_id`, `data.pane_tail`), and a `ready_timeout` outcome carries `data.pane_tail` too. Every failure exits non-zero.

If the agent exits before it takes the brief (a harness that dies at launch, say on a failed login), `start` and `send` report `gone` and exit 4 rather than a submitted round, whether the pane was already gone when the brief was sent or died while it was being confirmed, and keep the delegate's record so `reap` can remove what is left. A known limit: a harness that accepts the brief and exits right after it is still a submitted round, so `start` without `--await` prints `submitted` and exits 0; `status` then shows `gone`, and `--await` reports it as `gone` (exit 4).

`send` runs another round on the same delegate; one round at a time, so a `send` while a round is being awaited exits 1 and types nothing. `wait` without `--after` waits from the cursor the delegate recorded with its latest submit. `result` and `status` read without waiting; a `result` for a round with no reply whose agent no longer exists or is hibernated reports `gone` (exit 4), as `wait` does. A delegate whose agent is gone is still one: `status` reports `agent_status` `gone` from its record, and `result`, `wait` and `send` report `gone` (exit 4, and `send` types nothing), rather than `not a delegate`. A name whose agent was renamed away is still `not a delegate` (exit 2). A delegate survives a server restart: its entry records the agent id, which outlives the terminal id a restart re-mints. An entry written before the agent id was recorded is recognised after a restart only for a worktree delegate whose agent's cwd is exactly the recorded worktree path; an agent that has `cd`'d into a subdirectory stays `not a delegate` until a verb runs before the next restart and backfills the id. `reap` removes only the workspace and checkout recorded at start, reads just the registry so it works even when the agent is gone or the workspace was closed by hand, and leaves the branch decision to `worktree kill`'s merge gate — use that when you want to see the gate first.

`reap --force` clears the dirty-checkout refusal and proceeds through a busy lock. The teardown is idempotent: each step re-confirms the identity, treats `workspace_not_found` and `not_git_worktree` as "nothing to do", and derives the `removed` output from what actually happened — so two concurrent `reap --force` of the same delegate each exit 0 with the same end state, and the loser simply reports `removed: false` for the fields the winner removed. If the recorded checkout was removed outside flock, `reap` closes the workspace only when it still belongs to that checkout, prunes stale Git worktree metadata, then clears the entry. A reap that cannot get an answer from the server (a timeout or a dead socket) never counts that as removal: it exits 1 and keeps the entry, so it can be retried.

`pane read --source detection` reads exactly the unscrolled screen used by agent detection, excluding scrollback; `--lines` does not expand that screen. It supports text and ANSI formats. Socket clients can ask `pane.read` for `source: "detection_unfaint"` to get the same screen plus `unfaint`, the same rows with faint cells blanked, from one read; that is how `delegate wait` tells an agent's own dimmed suggestion from a typed draft.

### Delegate stall verdicts

An await returns `outcome: "not_started"`, reason `idle_without_new_turn`, and exit **8** only after continuously observing an idle agent with an unchanged empty composer and no new turn for **30 seconds (`STARTUP_ALLOWANCE`) plus `--settle`**. The window cannot start before `submitted_at_ms`; a later `wait` starts a fresh observation window instead of assuming the unobserved interval was idle. Composer changes, queued messages, startup indicators, missing samples, and unknown state reset the window. Working state or a new working entry cancels the not-started diagnosis for that round. This allows queued cold-start prompts and prompt hooks that arrive before working state to proceed normally. A shorter `--timeout` still returns timeout. Exit **8** is command-specific: `agent send` uses it for `unconfirmed`, while delegate awaits use it for `not_started`. Every event-time S1 request includes an `Observed outcome` line with the verdict and reason, including this evidence. Guarded submission waits up to two seconds for a partial composer repaint before refusing to send Enter.

`start --await`, `send --await`, and `wait` accept `--silence DURATION` (default `3m`; `0` disables it). Units are `ms`, `s`, `m`, and `h`, including combinations such as `1m 30s`. A working agent whose unscrolled detection screen stays unchanged after removing recognized harness status rows for this duration returns `outcome: "stalled"`, reason `silence`, and exit **7**. Viewport scrolling and recognized spinner, elapsed-counter, and progress-bar rows do not reset the timer; a new transcript line does. OpenCode provider retry screens report blocked with reason `provider_limit`. `agent get` and `delegate status` expose the live `blocked_reason` and `retry_after_ms`. Delegate waits tolerate short retries: they return reason/verdict `provider_limit` and exit **7** only when the ETA is at least the silence window or the retry persists continuously for that window. With `--silence 0`, only an ETA of at least 5 minutes stalls; short retries continue waiting, and idle means recovery. These rules also apply to older servers reporting working or unknown. Readiness timeout verdicts retain the provider reason and ETA, with `unknown` for a short retry rather than a human-input verdict.

Raise `--silence` for long builds or tools that print nothing while running. Recognized Claude, Codex, and opencode spinners do not count as progress; Claude running-tool elapsed counters are normalized while the tool row remains evidence. Unknown harness animations may still reset the timer, so a hung tool in an unknown harness can go undetected.

Readiness still defaults to 60 seconds. On readiness expiry, JSON includes `outcome: "ready_timeout"`, verdict `waiting_on_input`, `stalled`, or `unknown`, and `last_line` (the last nonblank screen line); exit remains 1. Round outcomes include `verdict`, `reason`, `retry_after_ms`, `last_line`, `s1`, and `settled_with_background_shells`. `delegate status` includes the latest persisted verdict for the current round. A Claude turn that ended (its completion line shows `done <time>`) while background shells it started keep running is idle rather than working, and both `delegate status` and the round outcome report `settled_with_background_shells: true` for it. `delegate status` reports `true` when the server's `agent.get` record carries the field. The server omits the field when it is false, and an older server never sends it, so whenever the field is absent `delegate status` reads the screen itself. The round outcome of `delegate wait` is still computed from the CLI's own screen read.

System One is optional: configure `[systemone] urls = ["http://127.0.0.1:8000/v1/systemone"]` and `timeout_s = 4`, or set `SYSTEMONE_URL` to comma- or space-separated URLs. The environment variable takes precedence. `tier = "full"` uses `full_urls` (or `SYSTEMONE_URL_FULL`) and `full_timeout_s` (default 12 seconds) instead. Only round endings and readiness expiry send the last 4 KB of the unscrolled detection screen; polls never send requests. A response adds advisory `s1: {fused, verdict}` without changing the exit code; only its `answers` are read. Unavailable endpoints yield `s1: null`. An endpoint that refuses the request also yields `s1: null` and prints `System One at <url> …` on stderr. Requests share a bounded timeout (default 4 seconds); an endpoint with three outages in a row (no connection or HTTP 5xx; refusals and timeouts after connecting do not count) is skipped for ten minutes.

## Notifications

```bash
flk notification show <title> [--body TEXT] [--position top-left|top-right|bottom-left|bottom-right] [--sound none|done|request]
flk notification list [--unread] [--limit N]
flk notification read <notification-id> | --all
```

`show` raises a notification through the configured `[ui.toast]` delivery. It exits 0 when `shown:true` and 3 when `shown:false`, preserving the JSON response so callers can inspect `reason` and fall back to another channel. `reason:"disabled"` means the server config has `[ui.toast] delivery = "off"` (the default), which disables popups. Other refusal reasons are `busy`, `rate_limited`, and `no_foreground_client`. API errors exit 1; invalid arguments exit 2. `list` reads what Flock has filed — every outcome it decided was worth saying, newest first: an agent that blocked or finished, and every `show` call, including the ones it refused to display. `read` acknowledges one or all of them.

The notification log panel inside the TUI (`prefix+i`, or the sidebar `menu` row → `notifications`) lists and acknowledges the same records: all three surfaces read one filter over one projection, so `--unread` and the panel's `u` filter can never disagree about what is unread.

Each row carries a `kind`, which is what makes the log readable rather than a stream: `attention` is something waiting on you — an agent that went blocked, or `blocking` mail for a recipient that muted itself — `outcome` is something that finished and produced a result, and `notice` is everything else worth keeping, which is every `show` call and every fleet failure. An escalation of that kind also names the pane that is waiting, so the title badge does not count a blocked pane twice.

Filing does not depend on `[ui.toast] delivery`. `off` — the default — asks for no popups, not for Flock to forget: the outcome is still recorded and still readable here. Records survive a server restart, and reading the list is not the same as acknowledging it, because acknowledging is what lets an old record be dropped.

### Sync after an upgrade

Run `flk integration sync --dry-run` to review the plan, then `flk integration sync` with the newly installed binary to refresh installed Claude, Codex and OpenCode hook assets and flock MCP launch paths. This works for package-manager installs and when the binary is already current. Each target reports `updated` (`would-update` in dry-run, including JSON output), `already-current`, `skipped-declarative`, or `failed`; failures return exit code 1 and do not prevent other targets from being checked.

Sync uses the selected `CLAUDE_CONFIG_DIR` and `CODEX_HOME` profiles (or their defaults) and the user OpenCode config; it does not search other homes or profiles. Only MCP entries named flock launching a store-pinned flk executable (including the legacy flock name) with `mcp serve` are migrated; bare PATH commands and explicit stable custom paths are preserved. Claude project-local registrations under `projects.*.mcpServers` are reported and updated individually. The chosen launch path is printed first; development executable fallbacks are refused, and a missing stable path fails MCP targets while allowing hook refreshes. Custom commands and unrelated entries are preserved, as are arguments, environment, permissions, comments and Codex hook trust. Symlinked or read-only configs are skipped with a fragment to merge through their Nix/Home Manager configuration owner.

Sync reports client, installed binary and server drift but does not perform a server handoff or stop sessions. Use `flk server live-handoff` when needed. Running agents need `flk agent restart` or an MCP reconnect to load the new bridge and tool catalog.

## MCP server

```bash
flk mcp serve
```

Speaks the Model Context Protocol over stdio: newline-delimited JSON-RPC 2.0 on stdin/stdout. Wire it into an MCP client (Claude Desktop, `mcp` CLI, agent runners) to give an agent a read-mostly view of the flock — list agents, read panes, fork Claude conversations, send/reply pane-to-pane messages, walk fork lineage, and read the files a human has handed over. `FLOCK_SOCKET_PATH` selects the flock server socket; the default is the current session's.

The server advertises two capabilities: `tools` (the closed table below) and `resources` (handed-over files). It claims no `subscribe`/`listChanged` sub-capability, because it pushes no resource notifications.

### Addressing across hosts

A pane id names a placement on **one** server, so it cannot address anything on another machine. An `agent_id` can: it is fleet-global and restart-stable (ADR-0008), and it is what `flock_agent_list`'s `fleet` rows report alongside the `host` the agent lives on and a `local` flag.

The two-step is the whole story:

```jsonc
// 1. flock_agent_list  →  find the agent, wherever it is
{ "fleet": [
  { "agent_id": "agent_atlas_6f21c4", "host": "atlas",  "local": false, "route": "atlas" },
  { "agent_id": "agent_hopper_9d0e17", "host": "hopper", "local": true,  "pane_id": "w1:p2" }
]}

// 2. flock_msg_send  →  address it by identity
{ "to": { "type": "agent", "agent": "agent_atlas_6f21c4" }, "body": "…" }
```

Replies need no addressing: `flock_msg_reply` carries the incoming `correlation_id` and uses its durable return binding. For a direct mesh request, the target pushes the reply over an enrolled outbound edge when available, or holds it (`state: "held"`) for origin collection. Collection starts about five seconds after confirmed delivery, works without an active waiter, and stops at the first final answer. The target needs no outbound peer entry. Held answers do not consume outbound retry slots, and a newly enrolled outbound edge pushes them. Automatic collection closes at the first final answer; send a new request for a follow-up that needs automatic collection on a one-way edge. Collection survives restart, deduplicates imports, and pauses with the fleet. An active reply waiter or a reconnect restores fast polling; `msg.status` reports terminal import failures as `collect_failed`. Replies to messages without a valid return binding return `reply_unavailable`.

**Requests use mesh custody across multiple hops.** A known recipient's owning node determines the route, including paths through a hub from a spoke with no outbound peers. A known but offline owner is accepted as `queued`; a new target with no known owner is refused as `msg_target_not_found`. Responses report `path: "direct"`, `"via <next hop>"`, or `"queued"` while no next hop is available. A configured incompatible owner or next hop refuses new acceptance with `peer_incompatible` and an upgrade instruction.

Each hop verifies the origin signature and evaluates `[msg] allow_from` against that origin's configured name, never the forwarding hub. An origin without a configured name matches only `"*"`. Forwarders persist custody before acknowledging and delete their body copy after transfer. The origin retains its copy until final receipt or expiry. Requests carry a visited-node list and a hop budget of eight; loops and exhausted budgets retain upstream custody until routing changes. Fleet pause freezes custody and its TTL. Multi-hop answers and receipts are separate mesh work.

The tool table is closed and intentionally read-mostly. Mutating verbs (`pane.close`, `worktree.remove`/`create`, `agent.start`/`rename`/`focus`, raw pane `send_*`, `server.*`, `notification.*`, `integration.*`) are not exposed and refuse with JSON-RPC code `-32000` and `data.refusal = "not_exposed_via_mcp"`. Modelled flock refusals (`unsupported_for_agent`, `no_agent_session`, `transcript_not_found`, …) propagate through the same code with the flock error code in `data.refusal`.

### Resources: files handed over to an agent

Tools are not the whole surface. A file dropped on a pane used to reach its agent only as a pasted path, deleted when the operator's client disconnected. It is now also an **MCP resource** — content the server holds and can name — so an agent lists and reads it natively instead of scraping it out of its own input surface.

```jsonc
// resources/list
{ "resources": [{
  "uri": "flock://handoff/file:1a04ff2c3b:0",
  "name": "client-1-clipboard-1756-0.pdf",
  "description": "file handed to agent_atlas_6f21c4; staged at /tmp/… on this host",
  "mimeType": "application/pdf",
  "size": 184320
}]}

// resources/read
{ "contents": [{ "uri": "flock://handoff/file:1a04ff2c3b:0", "mimeType": "application/pdf", "blob": "JVBERi0…" }] }
```

Text comes back in `text`, everything else base64 in `blob`. `resources/read` takes a URI carrying a flock-minted id and nothing else — there is no path parameter anywhere on this surface. Files over 4 MiB refuse with `handoff_too_large`; read them from the `path` in the listing instead. The list is not filtered by which agent is asking, because a filtered list that comes back empty cannot be told apart from a server that was handed nothing.

The paste still happens as well: flock cannot tell from outside a pane whether the agent in it has this MCP server wired up.

## Reporting a bug

```bash
flk report template [bug] > bug.md
flk report bug --file bug.md [--print|--open|--body-only] [--repo owner/name] [--last N] [--all-levels] [--no-diagnostics]
flk report bug --current TEXT --expected TEXT --repro TEXT --impact TEXT
```

`flk report` composes a bug report from what you wrote plus what the binary already knows: version, update channel, build commit, OS and architecture, terminal, shell, client protocol, and the running server's version and protocol compatibility. Logs come from the same directory with the server dead — which is exactly when you file one — filtered to WARN and ERROR by default (`--all-levels` includes routine activity, `--last N` changes the count, `--no-diagnostics` attaches none). Every record goes through the allowlist and scrubber first, so paths, hostnames, tokens and usernames are stripped before anything is shown. `--repo owner/name` files against some other repository; nothing else can redirect a report, not even the environment.

Getting the report off your machine takes a human, and there are two ways to do it.

`--open` prints a preview, copies the log tail to your clipboard, and opens GitHub's real bug form, prefilled. This is the route that runs the template's own required-field validation and gives you the reproducibility confirmation to tick.

`--body-only` writes **just the issue body to stdout** — no `destination:` header, no prefilled link, no footer — so it pipes straight into a filing command you run yourself:

```bash
flk report bug --file bug.md --body-only > "$HOME/flock-bug.md"
gh issue create --repo gerchowl/flock --title "pane read never returns" --body-file "$HOME/flock-bug.md"
```

The preview, any advisories and the exact command to run go to **stderr**, so what you reviewed is what gets piped and the preview never lands inside the body. The body has no URL length cap, so on this route the redacted log tail rides inside it rather than going to the clipboard: a headless report carries more evidence than a browser one, not less. `gh` posts a raw body and bypasses the issue form, so nothing validates it and the reproducibility confirmation is not one `gh` can set — use `--open` when you want GitHub's own form to run the checks.

Where you redirect that body is your call and worth choosing deliberately: unlike `--open`, this route writes a file, and the file holds paths, versions and the log tail. Keep it out of a checkout you might commit from, and delete it once the issue is filed.

Flock never files the report itself (ADR-0010 decision 6). The one write path it has is `flk issue drop --file-it`, which is yours to confirm.

## Removed mesh settings and methods

Upgrade the fleet together for mesh transport. Removed config keys are ignored with a warning naming the file, line, and key; all other settings still apply on startup, live handoff, and reload. Delete the named lines. Warnings appear in `flk status` and once per CLI invocation on stderr.

Remove these settings and callers:

- `[msg] uplink_timeout_secs`, `uplink_heartbeat_secs`, and `deferral_relay_concurrency`: delete these lines. Custody pushes use a fixed concurrency of four.
- `[[peers]] summary_command`: delete this line; peers now always hold a mesh edge. Use `relay_command` if the remote executable needs a custom path.
- `flk msg send --from-host` and the `msg.send` fields `from_host` and `intent_unrecognised`: remote origins come from authenticated mesh envelopes. `--from-agent` remains available for operator tooling.
- The old `msg.uplink_*` and `peers.relay_attach` methods: use per-edge
  `mesh.hello` enrollment, delivery and collection.
- The `forward_limit` and `peer_not_configured` routing refusals: known owners
  route through the mesh or queue while offline. New sends outside the gossip
  horizon with no stored owner hint are refused as unknown.

Removed config keys and unknown future keys produce warnings. Run `flk config check --json` before a rollout to list removed and unknown keys with file and line locations; exit `1` means warnings, including removed keys. Startup, live handoff, and reload ignore removed keys and apply the remaining settings.

Existing peer lists become a mesh with fewer edges; reciprocal SSH access is
not required. `[msg] allow_from` names are the authenticated origin's local
pin names (configured or inbound first-contact), never a forwarding hub or
an unpinned advertised name.

Before upgrading a development fleet, make a consistent SQLite backup of
`mesh-mail.sqlite` in Flock's state directory, preserve `mesh/identity.json`,
and copy `mesh-quarantine.jsonl` and `mesh-quarantine.jsonl.1` if present.
Use SQLite's backup facility while the server is running; a raw copy of the
main database can omit committed WAL data. Dev schemas v1–v11 upgrade in
place, idempotently, to the v1.0.0 baseline (v12). Moving a failed store aside
starts empty and loses its custody; preserve it before attempting recovery.

`mesh quarantined: N` in status means malformed records were isolated. The
mode-0600 quarantine sidecar retains full typed rows before bodies are
cleared, with two files capped at 64 MiB each. Copy both before another
rotation; decode `body.base64` and `envelope.base64` for inspection. Repair a database copy rather than blindly resending mail.
See [custody recovery](./socket-api.mdx) for storage details.
