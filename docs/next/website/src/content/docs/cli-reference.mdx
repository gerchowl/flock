Flock’s CLI talks to the running server over the same local socket API used by integrations and agents.

Most commands print JSON responses. Use them from scripts when you want deterministic automation.

## Launch and status

```bash
flk                         # launch or attach to the default session
flk --session work          # launch or attach to a named session
flk --remote workbox        # attach through SSH, using local keybindings
flk --remote workbox --remote-keybindings server
flk --remote workbox --handoff
flk --no-session            # single-process escape hatch
flk --default-config        # print default config
flk update                  # download and install from the configured channel
flk update --handoff        # opt into live handoff for supported running servers
flk channel show            # print stable or preview
flk channel set preview     # opt into preview builds
flk channel set stable      # return to stable releases
flk --version               # print version
```

Status commands:

```bash
flk status
flk status server
flk status client
```

`flk status` also probes the selected installed launch path with `--version`, bounded to two seconds. It shows client, running server and installed executable versions, the launch path, and `client_drift` / `server_drift`. JSON includes an `installed` object. Missing, failed or timed-out probes report an error and unknown drift rather than claiming the versions match. Server drift is unknown when no server is running. `restart_needed` retains its client/server comparison.

Server status includes the API socket listener’s accept-error count, latest error, and `stopped` flag. Transient accept failures retry with exponential backoff from 50 ms to 2 s, reset on a successful accept. Invalid listener descriptors stop immediately; unclassified errors stop after five consecutive failures. Failure runs log on onset and recovery rather than on every attempt. Diagnostics remain until that listener is replaced. With `--json`, these are under `server.api_listener` (or `api_listener` for `status server --json`). Older servers report no listener diagnostics. A stopped listener cannot accept new status requests; its terminal error is also recorded in the server log.

## Peer enrollment

`flk peers` and `flk status` show each peer's name, pin direction, short node
ID, and enrollment state: `pending`, `pinned`, or `refused` with the reason.

If a peer server is restarting or temporarily unavailable, held edges retry with
jittered exponential backoff with a ceiling that grows from 1 second to 30 seconds,
reset after successful enrollment. Retries occur on the configured gossip poll
cadence. Version or identity refusals retain a 60-second backoff and their reason
remains visible in status.

Inbound keys remain bound to their signed remote names. Configured peer aliases
supply local display names and may differ from those remote names. An inbound
peer claiming a configured peer's name must match that peer's configured pin.
If no pin exists, the first authenticated inbound contact pins both the
configured and inbound identity in one transaction. Fresh mutually configured
peers can enroll simultaneously. Status marks pins created by inbound contact
as `(first contact inbound)` and pins created by dialing as `(dialed)`.
This origin survives reconnects and restarts, including later outbound dials.
Pins created before origin tracking show `(pin origin unknown)`.
Verify inbound first-contact node IDs through a trusted channel, or use the
reset command below to enroll again.
With an older running server, the rest of status remains available and
enrollment reports `unknown (server predates mesh; restart needed)`.
`flk peers status --json` includes `source`, `node_id`, `pin_origin`, `enrollment`, and
`enrollment_reason`; `flk status --json` includes a `peers` array with the same
`pin_origin` values: `dialed`, `inbound_first_contact`, or `unknown`.

A node can accept up to 32 inbound relay edges. `peers status` lists each live
inbound edge separately. Each edge authenticates its own identity; a second hub
can connect without displacing the first. A newer handshake for the same node ID
supersedes the older edge. Resetting an inbound pin clears all edges enrolled
under that identity. Transient connection failures show `retrying` with the
reason; `refused` identifies a handshake or compatibility refusal.

Held SSH edges authenticate both node keys using fresh challenges and require
matching mesh protocol versions (`mesh: 1`). First contact pins the identity.
Enrollment uses trust on first use (TOFU): possession of a node key proves the
key holder, not that its claimed name belongs to the intended machine. Inbound
edges arrive over SSH into this host; a caller with that access who wins first
contact can claim an unpinned configured name. Both directions then trust that
first key and refuse a different one. Verify first-contact identities through a
trusted channel when that risk matters.
Pins survive restarts. An unexpected key change is refused as a possible
impersonation or re-key. After verifying the replacement, reset the pin from
the operator's shell and reconnect:

```bash
flk peers enroll --reset <peer>
```

The default reset clears the configured-peer pin. Use
`flk peers enroll --reset <peer> --direction inbound` for an inbound pin.
The command shows the direction, name, and node ID before clearing that pin.
Reset is refused when invoked from an agent pane or over MCP/relay; the
operator's shell is the trust boundary. Peers using a custom `summary_command`, incompatible versions, or a
failing relay are refused with a concrete reason. Version refusals include
`upgrade flk on <peer>` (or `this node` when the local version is older); discovery does not fall back to one-shot SSH.

## Server

```bash
flk server
flk server stop
flk server reload-config
```

`flk server` runs the headless server explicitly. Use it for supervised or service-style setups. `reload-config` applies reloadable settings without restarting panes.

## Config

```bash
flk config check [--path PATH]
flk config edit
flk config reset-keys
```

`config check` validates a config without starting or touching a server, and exits on a three-way code so it can gate a deploy:

| Exit | Meaning |
| --- | --- |
| `0` | clean |
| `1` | loaded, with advisory warnings (deprecated keys, keybinding conflicts) |
| `2` | did not load — a session would fall back to built-in defaults |

Every diagnostic is printed, unlike the in-app warning banner, which truncates to four lines. The check resolves keybindings in full, so conflicts and deprecation renames are caught rather than just TOML syntax errors.

`--path` checks a file that is not the live config, which is what a build-time gate wants:

```bash
flk config check --path ./config.toml || exit 1
```

Base and `config.local.toml` layering resolves exactly as it does at runtime. This is unrelated to `flk checks`, which runs the health-check runner.

## Preflight

```bash
flk preflight [--require TARGET]...
```

Answers one question: **is flock functional on THIS host right now?** `config check` proves the config parses; preflight also asks whether the things that config switches on are actually wired here. It exits on the same three-way code, so an activation or deploy can gate on it:

| Exit | Meaning |
| --- | --- |
| `0` | ready |
| `1` | works, but something wants attention |
| `2` | a configured feature is broken here |

It checks the config (by running `config check`), each agent integration, that the worktree directory is writable, and that `git` / `ssh` / `gh` are on `PATH`. Failures name the fix rather than the symptom.

**It never touches the network.** Preflight is built to run inside a Home Manager activation, so it cannot be allowed to hang one — peer reachability belongs to `flk status`, on a different clock.

### Why `--require`

An integration that is missing might be a deliberate opt-out, so flock will not fail your deploy over it on its own judgement:

| Hook state | Agent on this host | Result |
| --- | --- | --- |
| current | — | `0` |
| stale | — | `2` — it was wired and is now broken |
| missing | yes | `1` — might be intentional |
| missing | no | silent — not this host's business |

`--require TARGET` (repeatable) says *this deployment meant to have that one*, turning a missing hook into a `2`. flock cannot infer intent; the thing that deploys it can. A required target whose agent has vanished entirely still fails — passing quietly there would hide exactly the breakage this catches.

```bash
# In an activation: fail loudly if the Claude hook did not install.
flk preflight --require claude || exit 1
```

This matters because a half-wired host is silent by nature. Before the prompt-history panel read session transcripts it was fed purely by lifecycle hooks, so a host whose integration never installed showed an *empty panel* — indistinguishable from having no history yet.

:::note
A debug build reads `~/.config/flock-dev/config.toml`, so a debug-built preflight checks a different file than an installed one.
:::

## Worktrees

```bash
flk worktree list [--workspace ID | --cwd PATH] [--scan] [--json]
flk worktree create [--workspace ID | --cwd PATH] [--branch NAME] [--base REF] [--path PATH] [--label TEXT] [--focus] [--no-focus] [--json] [--dry-run]
flk worktree open [--workspace ID | --cwd PATH] (--path PATH | --branch NAME) [--label TEXT] [--focus] [--no-focus] [--json]
flk worktree remove --workspace ID [--force] [--json]
flk worktree kill (--workspace ID | --path PATH) [--dry-run] [--force] [--keep-branch] [--keep-procs] [--json]
```

Allocation commands (`worktree create`, `agent fork`, `agent start`, `workspace create`, `tab create`, and `pane split`) accept `--dry-run`. The server returns an `allocation_plan` JSON result with resolved paths, placement, and command arguments where applicable. It creates no directories, branches, workspaces, or terminal processes. A `pane.split` preview cannot predict a size refusal when the split is executed. Fork previews perform the same admission and transcript checks as a real fork. Generated branch names are chosen independently for each request; reuse the preview's branch and path explicitly to execute that plan. `agent start --dry-run --wait-ready` returns the plan immediately.

Worktrees are normal Flock workspaces with Git checkout provenance. `worktree create` creates a Git worktree checkout, opens it as a workspace, and groups it with the parent repo workspace. Without `--path`, Flock creates the checkout under `<worktrees.directory>/<repo>/<branch-slug>`.

`workspace close` closes Flock state only. `worktree remove` is the explicit checkout deletion path; it runs `git worktree remove`, never deletes the branch, and requires `--force` when Git refuses a dirty checkout.

`worktree list` prints a table ordered stale-first: the repo's own checkout, then linked checkouts oldest work first. `AGE` is the last commit on the branch — deliberately not the directory's mtime, which a build that rewrites `target/` makes meaningless. `--scan` adds a `VERDICT` column resolved through the same gate `worktree kill` runs, so a squash-merged branch reads `merged` here exactly as it does there; it is opt-in because it costs local Git plus a `gh` call per checkout. Absence of a verdict means "not scanned", never "not merged". `--json` prints the raw response, where the fields are `last_commit_at` and `kill_verdict`.

`worktree kill` is the scriptable twin of the TUI's "Kill worktree & branch": it runs the same merge gate (merged PR via `gh`, merged into a landing branch, remote containment, or content already landed by a squash or rebase) and deletes the local branch only with positive evidence. Address it with `--workspace ID` or `--path PATH`; a path that is open as a workspace closes that workspace too. `--path` is what makes a stale checkout nobody has open actionable at all — removing one with raw `git worktree remove` leaves the workspace pointing at a directory that no longer exists. `--dry-run` prints the gate verdict as JSON (exit 0 evidence found, 3 none); `--keep-branch` always preserves the branch; dirty checkouts exit 4 until `--force`. The landing branches (the detected default branch plus `dev`, `main` and `master`, and any `[worktrees] integration_branches` entry) and any `[worktrees] protected_branches` entry are kept under every path. See [Which branch counts as merged](/docs/configuration/#which-branch-counts-as-merged) for how that set is decided.

A kill also sweeps the processes left in the checkout. Removing a worktree unlinks a directory but does not touch the processes whose working directory it was, and a `setsid` child is out of reach of the pane teardown — those keep running against a path that no longer exists. Once the checkout is removed and the workspace is closed, anything still alive from inside it gets `SIGTERM`, a grace period, then `SIGKILL`. Matching is against the leaf checkout exactly, never the parent directory worktrees of a repo share, and the calling process and the shell it was typed into are never signalled. The result JSON carries `processes` (what was standing there when the kill began), `orphans` (what outlived the teardown) and `orphans_surviving` (what outlived `SIGKILL`), each as `pid` plus command name; the same is summarised on stderr. `--keep-procs` reports without signalling anything, and `--dry-run` names what is standing in the checkout without touching it.

## Tabs

```bash
flk tab list [--workspace <workspace_id>]
flk tab create [--workspace <workspace_id>] [--cwd PATH] [--label TEXT] [--focus] [--no-focus] [--dry-run]
flk tab get <tab_id>
flk tab focus <tab_id>
flk tab rename <tab_id> <label>
flk tab close <tab_id>
```

`tab create --workspace ID` creates an inner tab in that workspace, including in workspace tab mode. `--cwd` sets the new terminal’s working directory without changing the target workspace. An unknown workspace ID returns an error. Without `--workspace`, workspace tab mode creates a sibling workspace from the active workspace.

## Panes

```bash
flk pane list [--workspace <workspace_id>]
flk pane get <pane_id>
flk pane rename <pane_id> <label>|--clear
flk pane split <pane_id> --direction right|down [--cwd PATH] [--focus] [--no-focus] [--dry-run]
flk pane close <pane_id>
```

`pane read`, `pane send-text`, `pane send-keys`, and `pane close` also accept a terminal ID or a unique agent name/label. A pane ID takes precedence over a same-named agent. Ambiguous names are rejected with candidate details; use a terminal ID or pane ID to select one.

Read output:

```bash
flk pane read <pane_id> [--source visible|recent|recent-unwrapped|detection] [--lines N]
flk pane read <pane_id> --source visible --ansi
flk pane read <pane_id> --source recent-unwrapped --lines 120
```

`pane read` scrapes what is drawn on the terminal. `recent` returns the bottom `--lines` rows of the screen, reaching further up when those rows are blank; `visible` is the user-visible viewport and follows the operator's scroll, so it is not a stable source for a script. For an agent TUI both give you that TUI's own chrome rather than its conversation — use `flk agent history <target>` for what the agent said.

Send input:

```bash
flk pane send-text <pane_id> <text>
flk pane send-keys <pane_id> <key> [key ...]
flk pane run <pane_id> <command>
```

`pane send-text` reports the same observed delivery result and exit codes as plain `agent send` (see below).

`pane send-text` uses bracketed paste when the terminal enables it and does not send Enter. Terminals without bracketed paste receive the text bytes directly. Embedded paste delimiters are removed when bracketed paste is enabled. Use `pane send-keys <pane_id> Enter`, `C-c`, or `Esc` for control keys; control bytes passed to `send-text` are pasted as text when bracketed paste is enabled.

`pane run` types the command and then presses Enter, as two separate writes with a short pause between them. It is deliberately *not* atomic: a program reading a raw-mode stdin sees read boundaries rather than keystrokes, and agent TUIs use those boundaries to tell typing from pasting — text and a carriage return arriving in one read look like a pasted block containing a newline, so the newline is inserted and nothing is submitted. The pause is a heuristic, not a guarantee. A TUI that has not started reading stdin at all misses the text as well as the Enter; wait for the pane to be ready (`agent start --wait-ready`, `agent wait --ready`) before typing into a freshly started agent. `send-keys <pane_id> Enter` still submits a line that is already sitting in an input box.

Arm a self-compaction of your own context:

```bash
flk pane arm-self-compact [--pane <pane_id>] [--abort] <handoff prompt>
```

The one thing flock types into a pane on an agent's own instruction, and the reason it is a verb rather than a `send-text` is that it is not typing *at* the agent — it is the agent asking to be allowed to shorten its context and carry on. The prompt is the agent's own handoff to its next self: the text an operator otherwise copies out of the transcript and pastes back in.

The call **arms** and returns. Nothing is typed, because an agent calling it is mid-turn and its harness cannot compact inside a turn. Then, in order: the agent finishes the turn; once its pane is idle, settled and untouched by a human, flock types `/compact` and submits it; when the harness reports the compaction back through the session hook, flock types the handoff prompt in and submits it as the next turn. A harness that compacts on its own first — Claude Code does, exactly when the context fills up — is not a special case: the report still counts, and flock does not then compact a context that was just compacted.

Two writes and a signal, and the signal is a hook report rather than a timer — `session_start_source: compact` is the harness saying in its own words that the compaction happened. So the wait is bounded: `[session] self_compact_timeout_ms` (default 120 s), `self_compact_settle_ms` and `self_compact_fresh_ms` drop an arming the harness never confirms, naming in the log which half was lost. An arming that has not typed anything is never timed out, because an agent may legitimately be mid-turn for minutes. Flock never types over an operator: a quiet window, an empty prompt box, and a re-check immediately before each keystroke all stand between the arming and the pane.

If a compaction is already armed, a second arming is **refused** with `state: "pending"` rather than replacing the stored prompt — two written handoffs, and silently keeping one discards work the agent believed it had saved. `--abort` drops one. Claude Code only: `/compact` is a harness affordance, and another agent is refused by name instead of being armed into a no-op. Off `[session] self_compact` forbids it outright.

The continuation is checked before anything is typed. A prompt carrying a control or escape byte, an embedded line break, or a leading `/` or `!` is **refused with a reason** rather than scrubbed: the encoder wraps text between the bracketed-paste markers without escaping, so a prompt containing the closing marker would end the paste early and be read as keystrokes, and a leading `/` or `!` is a command the harness runs instead of instructions it reads. A scrub would report success for a plan that is silently missing part of itself.

Both writes go through the same gates. Claude Code auto-compacts mid-turn, so a confirmation can arrive with the agent still working and a human part-way into a prompt; an occupied prompt box is never typed into, because submitting it would submit the human's draft too.

Over MCP the same thing is `flock_self_compact`, which is an allowlisted way an agent can affect its own pane — `pane.send_*` stays off the closed MCP table, and this is an allowlisted exception rather than an unlock.

Report agent state from custom hooks:

```bash
flk pane report-agent [<pane_id>] \
  --source ID \
  --agent LABEL \
  --state idle|working|blocked|unknown \
  [--pane <pane_id>] \
  [--message TEXT] \
  [--custom-status TEXT] \
  [--seq N] \
  [--agent-session-id ID] \
  [--agent-session-path PATH]
```

The pane id is optional, as it is for `report-recap` and `report-reply`: name it as the leading argument or with `--pane`, and with neither the report lands on the calling pane — the one your hook is running in, resolved from `$FLOCK_PANE_ID` or from process ancestry. A pane that cannot be resolved is refused with `pane_not_found` and a non-zero exit, so a hook that only checks the exit status cannot mistake a discarded report for a delivered one.

`pane get`, `pane list`, `agent get`, and `agent list` include a read-only `agent_session` object when an official integration has reported a native session reference. If no native session reference is stored, the field is omitted.

Those commands include `foreground_cwd` when Flock can resolve the cwd of the foreground process controlling the pane. The existing `cwd` field remains the pane/workspace cwd used for labels and follow-cwd behavior.

Report display-only pane metadata without taking over semantic state:

```bash
flk pane report-metadata [--pane <pane_id>] \
  --source ID \
  [--agent LABEL] \
  [--applies-to-source ID] \
  [--title TEXT|--clear-title] \
  [--display-agent TEXT|--clear-display-agent] \
  [--custom-status TEXT|--clear-custom-status] \
  [--state-label STATUS=TEXT] \
  [--clear-state-labels] \
  [--seq N] \
  [--ttl-ms N]
```

The pane defaults to the calling pane. Use `--pane <pane_id>` or a legacy leading pane id to report from outside the pane.

`STATUS` is one of `idle`, `working`, `blocked`, `done`, or `unknown`. `--agent` is a guard for the authoritative agent label. `--applies-to-source` is a guard for the active lifecycle authority source. Use `--display-agent` to change the visible name.

## Agents

```bash
flk agent list
flk agent get <target>
flk agent read <target> [--source visible|recent|recent-unwrapped|detection] [--lines N] [--format text|ansi] [--ansi]
flk agent history <target> [--detail reply|collapsed|full] [--cursor N] [--limit N]
flk agent result <target> [--max-chars N] [--offset N]
flk agent send [--submit] <target> <text>
flk agent rename <target> <name>|--clear
flk agent focus <target>
flk agent wait <target> --status <idle|working|blocked|done|unknown|hibernated|settled> [--after CURSOR] [--settle MS] [--timeout MS] | --ready [--timeout MS]
flk agent attach <target> [--takeover]
flk agent start <name> [--cwd PATH] [--workspace ID] [--tab ID] [--active|--here] [--split right|down] [--focus|--no-focus] [--wait-ready [--ready-timeout MS]] [--dry-run] -- <argv...>
flk agent fork <target> [--branch NAME] [--base REF] [--path PATH] [--label LABEL] [--pivot TEXT|--no-pivot] [--focus|--no-focus] [--dry-run]
flk agent hibernate <target>
flk agent resume <target>
flk agent restart self|<target> --reason TEXT [--continue-with TEXT|@FILE]
flk lineage <target> [--json]
flk msg send <target> <text...> [--repo NAME] [--intent fyi|needs-reply|blocking] [--correlation-id ID] [--reply-to ID] [--await [--timeout MS]] [-- <text starting with dashes>]
flk msg reply <correlation_id> <text...> [--intent fyi|needs-reply|blocking] [-- <text starting with dashes>]
flk msg list [--pane TARGET]
flk msg read [--pane TARGET]
flk msg status <correlation_id>
flk msg mute <seconds> [--pane TARGET] [--reason TEXT]
flk checks list
flk checks ack <name>
flk checks run <name>
```

Agent targets can be terminal IDs, unique agent names, detected or reported agent labels, or legacy pane IDs. Names and labels are agent identities. Terminal IDs and legacy pane IDs are low-level escape hatches.

`pane run <pane_id> --if-input-empty [--min-age-secs N] [--if-session ID] <text>` uses the same server-side guard. It refuses a draft with `input_not_empty`, an unsettled status with `not_settled`, and a different session with `session_mismatch`. The guard and paste are serialized in the server, avoiding a client read-then-send race. Ordinary `pane run` retains its shell command behavior. Socket clients can call `pane.submit` with `pane_id`, `text`, optional `if_session`, and `min_age_secs`; MCP clients use `flock_pane_submit` with the same fields. `delegate start` and `delegate send` also use this guard. An unconfirmed delegate submission preserves its workspace and new round cursor, so `delegate wait` can observe a later accepted turn without sending the brief again.

Send outcome codes (`agent send`, `pane send-text`, and guarded `pane run`):

| Code | Outcome |
| --- | --- |
| `0` | `delivered`, `accepted`, or `observed_accepted` |
| `8` | `unconfirmed`: delivery or acceptance could not be confirmed |
| `9` | `abandoned`: guarded submission stopped because its preconditions changed |
| `1` | API or transport failure |
| `2` | Invalid arguments |

Failure JSON remains on stderr. Guarded results include the delivery `attempt` evidence and `reason`. MCP `flock_pane_submit` uses the same numeric error codes 8 and 9, with the outcome as the error message and the complete result in error `data`. Raw paste tools remain unexposed via MCP.

`agent read` reads the resolved terminal stream. `agent send` pastes text to that stream **without submitting**, using bracketed paste when the terminal enables it so punctuation such as `!` stays literal input. Use `agent send --submit <target> <text>` to type terminal input (bracketed paste when enabled), require a fresh idle agent with a recognized empty composer, wait 120 ms, and send a negotiated Enter key event. The server observes acceptance for 2 seconds and retries **only Enter, once**, if the exact prompt remains in the composer and no operator input, dialog or execution change intervened. It then observes for another 2 seconds. Codex 0.160.1 is supported in both its default alternate-screen mode and `--no-alt-screen` mode. Unknown composers and paste chips cannot authorize a retry. Embedded paste delimiters are removed when bracketed paste is enabled. Use `pane send-keys <pane_id> Enter`, `C-c`, or `Esc` for control keys instead of embedding control bytes in the text. Use `agent send -- <target> <text>` for literal text beginning with `--submit`. Plain send observes the unscrolled composer (or newly visible text for ordinary terminals) for up to 2 seconds and reports `delivered` or `unconfirmed`, with a reason and before/after SHA-256 screen digests. Confirmation only reads the screen and never sends keys. Evidence `level` is `text_matched` when the changed region contains the pasted text, `composer_changed` when a recognized editor changed (including folded paste chips), or `screen_changed` for a weaker screen-only observation without a matching composer change. Plain paste supports busy editors and existing drafts. Repeated input is compared against the changed region, and whitespace is normalized across wrapped rows. A recognized composer that stays unchanged remains unconfirmed even while output streams elsewhere. `screen_changed` is the weakest evidence and is returned only at the two-second deadline, allowing late text or chips to provide stronger evidence first. A ticking clock or `tail -f` output can produce this level without proving that input reached the application. Retained rows shifted by scrolling cannot count as newly matched text. An unchanged screen remains unconfirmed. Operator input, an execution change, or pane disappearance interrupts observation with a specific `unconfirmed` reason. These observation levels never authorize a guarded-submit retry. Initial missing-runtime errors retain `agent_not_found` / `pane_not_found`; disappearance during observation reports `unconfirmed` with reason `pane_gone`. `--submit` reports `accepted` (matching prompt hook), `observed_accepted` (a new working entry), `unconfirmed`, or `abandoned`; the last two exit 8 and 9 respectively and leave the composer untouched. Acceptance does not mark inbox messages read. `agent get`, `agent focus`, `agent wait`, and `agent attach` require the resolved terminal to have agent identity. `agent rename` can assign that identity.

Use `pane send-text`, `pane send-keys`, `pane run`, and `terminal attach` for ordinary terminals, servers, tests, shells, or low-level terminal control. Use `pane run` when you want to submit a command with Enter.

`agent start --wait-ready` and `agent wait --ready` block until the pane reports an agent status other than `unknown`, then print the agent exactly as `agent get` would. `unknown` is the only status Flock reports when its detector has not recognised the agent's own chrome, so it is what a booting TUI looks like — for a Claude pane, for 30-60 seconds during which "still booting", "crashed on launch" and "blocked on a first-run dialog" are the same observation. Ready is the first moment the question is answerable, and the status it lands on is the answer: `blocked` returns immediately rather than waiting a dialog out, which `--status idle` cannot do. A wait that fails says what it saw — the last status and the last line the pane printed — and an agent whose pane exits during the wait ends it straight away with `agent_exited_before_ready` instead of running out the clock. A pane running something Flock does not detect never becomes ready; that is reported at the timeout rather than being papered over. The default timeout is 60s.

`--wait-ready` is opt-in and off unless passed. Because readiness is a detector verdict rather than a liveness check, **a headless agent never becomes ready**: `opencode run "…"`, a CI step, or anything that paints nothing while it works will sit at `unknown` for the whole window and then time out, however healthy it is. Do not pass `--wait-ready` to those; the start itself already refuses a child that dies in its first moments, and `pane_exited` reports the rest.

`agent start` with no placement is refused (`agent_placement_required`) unless the caller is running inside a pane of that server's session, because "the workspace you are looking at" is only an answer to a caller that has one — an `ssh` dispatch or a resume script is told to pass `--workspace`, `--tab`, `--cwd`, or `--active` instead of being placed wherever a human last focused. `--active` names the workspace being looked at; `--here` names the workspace the caller's own pane is in, read from its process ancestry, and is refused (`agent_here_unavailable`) when the server cannot place the caller in a pane. Naming two placements at once is refused (`agent_placement_conflict`). A `--cwd` naming a real directory that matches no open space still gets a space of its own, except under `--split`, which refuses there because there is no space yet to split.

`agent start` registers the name it returns itself, before the child has printed anything and independently of any hook the agent runs. The `name` in the `agent_started` result resolves with `agent get`, `agent read`, `agent send` and `agent wait` straight away, so `agent_not_found` for a just-started name is a real failure rather than a race. An agent name cannot look like a pane ID: targets resolve as a pane ID first, so a name written `1:p1` or `p_1_2` is read as that pane.

The stop-hook mail nudge names `flock_msg_read` and, if the MCP tool is unavailable, `flk msg read --pane <pane_id>` with the stopping pane’s ID filled in. Both read and consume the same inbox.

`msg status` and `msg list` include `attempts`: local wake submission evidence with an attempt id, pane, correlation ids, timestamps, retry flag and reason. Attempts progress through `queued`, `typed` and `submit_sent` to `accepted`, `observed_accepted`, `unconfirmed` or `abandoned`. A genuine inbox read during verification (or after an unconfirmed wake) records `read`; a read before Enter cancels the pending submission. An accepted wake does not mean the inbox was read: mesh messages remain `delivered` until a genuine read; older local messages remain `queued`. Explicit guarded-submit responses carry the same evidence. Mesh attempt queries read the custody store; older local attempts use an in-memory registry restored from the retained audit window. Both restore during boot and live handoff. The registry targets 4,096 entries, matching mailbox history: completed attempts are evicted oldest-first. Pending attempts are never evicted. An unconfirmed attempt stays protected while any of its correlated messages is queued in any local mailbox; once none remain queued (including after expiry or dropping), it becomes eligible for oldest-first eviction on the next submission. Unconfirmed explicit submissions with no correlated mail are also eligible. No additional attempt TTL is used. New submissions are refused with `delivery_attempt_capacity` only if all slots are still protected. Restoring older logs with more protected entries preserves them and refuses new submissions until capacity is available. Mesh attempt recovery is independent of audit retention; older local attempt recovery is limited to the retained log window. Interrupted attempts become `unconfirmed` with reason `server_restarted`, and their keys are never replayed. Older pre-mesh `relayed` records still mean transport handoff, not a read receipt. Unconfirmed and abandoned attempts also appear in the digest. The optional System One advisory is deferred to Clef (#714).

Mesh `msg.status` reports `queued` (origin custody awaiting transport), `custody` (transferred custody), `delivered` (durable inbox import), `read`, `held` (answer awaiting return), `collected` (answer transferred to its origin), `expired`, or `outcome_retention_elapsed`. Refusals and collection failures include `detail`. `reply` contains the best imported answer independently of the original message state. Queries do not commit store changes. Read receipts return over authenticated collection, including the hub's collection exchange with a spoke.

A status result includes a signed `reference`. Retain it and pass it as `reference` to socket/MCP status or reply-wait calls, or as `--reference JSON` to `flk msg status` and `flk wait reply`, to query an exact message after outcome cleanup. A correlation alone cannot distinguish an unknown message from one whose retention elapsed. Status by correlation only answers for messages this node sent; a correlation another node reused for its own mail never stands in. `msg status` exits 0 for known nonfailure states, 3 for expiry, removal, elapsed retention or collection failure, 4 when the receiver refused the message, and 1 for API errors.

`replyable` means a reply can be routed: a same-host sender pane, a sender agent the directory can resolve, or a durable mesh return binding. `msg.read` and the MCP channel push compute it the same way. `reply_contract` says which promise that is: `durable_return_binding` survives the sender being offline; `best_effort_local_or_directory` depends on the sender still being reachable.

`msg send` queues a message for another pane's agent; it is typed and submitted as a chat turn at that pane's next settled turn boundary, tagged with the sender pane and a correlation id the recipient can `msg reply` to. `<repo>:<pane>` splits only when the left side names a known repo; use `--repo` to be explicit. `--intent` says how much you need from the recipient, and it rides the envelope, so the recipient sees it before reading the body and `msg list` shows it on the queued row: `fyi` never wakes the recipient (it is read whenever the inbox next is), `needs-reply` marks the message as one you are owed an answer to and nudges the recipient at its next turn boundary, and `blocking` says you cannot proceed without one — it also puts the recipient in the operator's attention list and, if the recipient has muted itself, files an operator notification naming sender, recipient and count. `blocking` has its own per-sender budget, `[msg] blocking_per_hour`; past it the message is still delivered, as `needs-reply`, and the send result's `warnings` say it was downgraded. It defaults to `fyi` on the CLI — the MCP tool requires the choice instead, since an agent that never has to look at the field will not. Both verbs **refuse an option they do not recognise** rather than treating it as body text, and `--` ends flag parsing so a message may legitimately begin with dashes. Cross-host sends now persist custody before delivery and return a server-minted message key. A held authenticated mesh edge imports the message exactly once per key. A `delivered` result confirms inbox import; `queued` retains the message for retry after a disconnection or restart. An incompatible peer is named with `upgrade flk on <peer>`; sends do not fall back to a one-shot SSH command. `lineage` prints the fork ancestry chain of a pane, worktree, or branch — reconstructed from the durable event log, so it survives server restarts. `agent fork` branches the target's conversation into a new linked worktree: it creates the worktree, then starts a pane that resumes a fork of the agent's session, optionally seeded with a pivot prompt (`--pivot`; `<branch>` resolves to the final branch name, `--no-pivot` opts out of the configured template). Only Claude sessions can fork; other agents are refused with `unsupported_for_agent` because a plain resume would attach two processes to one session id.

`agent hibernate` parks a pane cleanly: the agent's child process is asked to exit, the resume plan is stashed on the terminal, and the pane is kept. The next focus (or an explicit `agent resume`) respawns it. Panes without a resumable session refuse with `hibernate_unsupported` (data-loss guard).

`checks list` enumerates the runner's script checks together with the built-in state (blocked-alert / hibernation / issue-guard). `checks ack <name>` silences the next fire — for script checks the debounce window; for the built-in blocked-alert, the current in-flight episodes. `checks run <name>` forces a script check due right now.

## Waits

Wait for output in a pane:

```bash
flk wait output <pane_id> --match <text> [--source visible|recent|recent-unwrapped|detection] [--lines N] [--timeout MS] [--regex] [--raw]
```

Wait for pane agent state:

```bash
flk wait agent-status <pane_id> --status <idle|working|blocked|done|unknown|hibernated|settled> [--after CURSOR] [--settle MS] [--timeout MS]
```

Wait for the answer to a message you sent:

```bash
flk wait reply <correlation_id> [--timeout MS] [--json]
```

Use `wait output` for normal commands and servers. Use `wait agent-status` for coding agents. Use `wait reply` after a `msg send --intent needs-reply`: it prints the reply's body (metadata on stderr, or everything with `--json`) and exits 0 replied, 3 deferred by a muted recipient or dropped unread, 124 timed out. It works for a sender outside any pane, whose reply is held for it under the correlation id. `msg send --await` sends and waits in one command.

`agent restart` returns after scheduling the restart. Finish the requesting turn normally: Flock waits for a settled idle prompt, stops the agent process tree through the runtime, and resumes the same conversation with its original executable, flags, profile environment, cwd, and agent name. `self` requires the caller to be inside the agent pane; an explicit target accepts the usual pane ID, terminal ID, or unique name.

`--continue-with` supplies the next instructions. Prefix a file path with `@` to read them from a file. Instructions must be a single line of plain text, at most 16 KiB; a terminal newline in the file is removed. The default is “You restarted yourself for: <reason>. Continue your task.” Flock queues this through the message inbox/wake path after verifying a fresh report of the same session and an empty idle prompt.

A configured hard limit or the grace deadline can force a restart mid-turn. The continuation then names the limit, warns that the last tool call may be incomplete, and lists stopped processes and reported background tasks. A failed flush check is disclosed. Unknown startup dialogs and credential prompts are left for the operator; verification timeout emits `restart_stuck` with a screen excerpt. Repeated restarts stop the agent at the rate cap; `agent resume` explicitly releases that stop. See [restart configuration](/docs/preview/configuration/#agent-restarts).

### Waiting for an agent to go quiet

Both wait verbs take the same seven statuses and mean the same things by them. `idle` is **ready for input**, and it matches `done` as well — an agent nobody is watching goes quiet as `done`, which is an effective idle, so `--status idle` is the way to wait for an unattended agent in either verb. `--status done` means exactly `done`. (`flk wait agent-status --status idle` used to match only a literal `idle` and therefore hung on every unattended agent, which is the hang #553 reports.)

`--status settled` is the one to reach for from a supervisor. It is **observed quiescence**, and the distinction is the whole point:

```bash
c=$(flk agent get worker | jq -r .result.agent.turn_cursor)   # capture BEFORE prompting
flk agent send --submit worker "..."
flk agent wait worker --status settled --after "$c" --timeout 3600000
```

`settled` means: after that cursor, the server saw this agent enter `working` (or the cursor was captured while it was already working), and then saw its reported status hold `idle`/`done` with **no state transition at all** for the settle window. Anything in between resets the dwell — including `idle -> blocked -> idle`, which is why the dwell is anchored on a transition counter rather than on the status alone. `--settle MS` sets that window and defaults to `5000`; `--settle 0` settles on the sample after the first qualifying one. Without `--after`, any quiet counts — an agent that is already idle settles after one settle window, so capture the cursor before you prompt.

**It is not proof that a turn produced a result.** It says what Flock observed; for the turn's output use `flk agent result` (once #575 lands). Two consequences follow. Native Claude and opencode agents are read from the screen every 300-500 ms, so a working phase shorter than one sample is never observed — a cursor captured before one waits for the *next* turn instead. And `working_entries` counts *observed* entries, not submitted prompts: capture the cursor after the agent is at its prompt and before you prompt it.

The cursor itself is the `turn_cursor` field on `agent get`, `agent list` and `pane get` — `"{terminal_id}:{execution_epoch}:{working_entries}:{state_seq}:{w|i}"`, opaque to callers. It never satisfies a wait on another terminal or another execution, and one whose counters the server has not reached is refused rather than waited out, so a typo cannot read as "it already worked".

On success `settled` prints one JSON object on stdout:

```json
{"status":"settled","pane_id":"1-1","agent_status":"idle","turn_cursor":"term_1f2e3:0:2:7:i","held_ms":5003}
```

`flk wait agent-status <pane> --status settled` is the same signal with the same result line — a supervisor can use whichever verb fits the command it already has. Exit codes for `--status settled`: **0** settled · **3** blocked (a human has to look) · **4** gone, with `"reason":"closed"|"hibernated"|"restarted"` on the line · **124** timeout · **2** a usage error or a refused cursor · **1** any other error. The non-settled statuses keep their historical codes, including `1` for a timeout.

`--after` and `--settle` mean nothing without `--status settled`, and a non-numeric `--settle` or `--timeout` is a usage error: all of these exit `2` before any request is sent, so a typo does not cost you the wait.

### Delegating a task

```bash
flk delegate start <name> --brief FILE (--cwd PATH | --worktree --branch B [--repo PATH] [--base REF])
                    [--harness opencode|claude|codex] [--model M] [--sandbox MODE] [--await] [--timeout MS] [--settle MS]
                    [--ready-timeout MS] [--max-chars N] [--json]
flk delegate send <name> --brief FILE [--await] [--timeout MS] [--settle MS] [--silence DURATION] [--ready-timeout MS] [--max-chars N] [--json]
flk delegate wait <name> [--after CURSOR] [--timeout MS] [--settle MS] [--silence DURATION] [--max-chars N] [--json]
flk delegate result <name> [--max-chars N] [--json]
flk delegate status <name> [--json]
flk delegate reap <name> [--force] [--json]
```

Codex defaults to `--ask-for-approval never --sandbox workspace-write`. Workspace-write blocks the network, so a delegate that must `git push` or use `gh` needs `--sandbox danger-full-access`, deliberately chosen by the caller. `--sandbox` accepts `read-only`, `workspace-write`, or `danger-full-access` for Codex only; opencode and Claude reject it with exit 2.

`flk delegate` and `flk agent result` use capabilities first shipped in **0.9.0**. If a request fails because a capability is missing, they check the server version best-effort. A confirmed older server gets a diagnostic naming the required and running versions and `flk server live-handoff` or upgrade guidance. If the version is unknown or already 0.9.0 or newer, the original error is preserved.

`delegate` is the sequence above run as one command: create the space, start the harness in it, wait until it is actually up, type the brief, and — with `--await` — wait for the round's outcome and print it. It is composed from socket methods that already existed, so it adds no new protocol; what it adds is the bookkeeping that was previously in somebody's shell history.

The brief is a file, and exactly one sentence is ever typed into the agent: `Read <absolute path> and execute it exactly.` The path is made absolute without resolving symlinks, and is refused if it contains whitespace, a control character, or any of `` ! $ ` " ' \ `` — the path crosses the agent's shell, and a quote that survives that hop names a different file by the time the agent reads it. Put the instructions in the file; the typed text carries nothing else.

The delegate runs in a workspace it created and **never requests focus**, so your focus is unchanged by any of these verbs and a delegate never lands in the workspace you are looking at. With `--worktree` it makes a linked checkout (`--repo`, `--branch`, `--base`; those three mean nothing with `--cwd` and are refused there) and the agent's cwd is that checkout.

`--harness` is `opencode` (the default) or `claude`, and `--model M` is handed to it as `--model M`. The two differ in where the session comes from, which is what `no_result` reports: opencode's plugin names it mid-turn, Claude's `SessionStart` hook names it from inside the harness.

**The brief is only typed into an agent that is at its prompt.** `start` and `send` both wait out a permission prompt rather than answering it, and time out with the status named (`delegate <name> is blocked`) rather than typing into a dialog. That wait also covers readiness — a pane that has painted nothing yet reports `unknown`, which is a booting TUI, not a crash. Claude Code asks `Quick safety check: Is this a project you created or one you trust?` the first time it starts in a directory, and a `--worktree` checkout is always such a directory: that dialog has no input box, so the delegate names it (`delegate <name>: Claude Code is waiting on its folder-trust dialog (see #605)`) and refuses instead of typing at it. Accepting it is a human action — #605 is the pre-trust proposal, not a default.

`--await` stays and reports the round's outcome. Settling is not finishing: an agent goes quiet between tool calls, so the await settles and then waits a further grace for a reply recorded at or after this round's submit. A round is therefore only reported when the agent entered `working` after that round's cursor **and** a reply exists from after the submit — a fix round is not reported from the quiet that preceded it, and not from the previous round's reply. `--timeout` bounds the await only and starts after the submit (for `wait`, at command entry); `--settle` defaults to 5000; `--max-chars` pages the reply.

Exit codes: **0** a finished reply ending on `DONE:` / `VERDICT:` · **3** a `BLOCKED:` reply · **4** the agent's pane closed, hibernated or restarted · **5** a finished reply with no sentinel, or none inside the grace · **6** the agent sitting on a prompt (`blocked`) for the settle window · **7** a stalled round · **8** `not_started` (continuously idle with an empty composer for the startup window and no new turn since the submit cursor) · **124** the timeout · **2** a usage error, or a name that is not a delegate · **1** any other failure. With `--json`, exits 0, 3, 4, 5, 6, 7, 8 and 124 print the same object (a usage error, exit 2, and failures other than readiness expiry, exit 1, print nothing on stdout, only the error on stderr), and its `turn_cursor` is the cursor that await started from — so a timed-out caller resumes with `--after <turn_cursor>` and gets the same round. Without `--json`, stdout is the reply's text and stderr is one summary line.

`send` runs another round on the same delegate; one round at a time, so a `send` while a round is being awaited exits 1 and types nothing. `wait` without `--after` waits from the cursor the delegate recorded with its latest submit. `result` and `status` read without waiting; a `result` for a round with no reply whose agent no longer exists or is hibernated reports `gone` (exit 4), as `wait` does. `reap` removes only the workspace and checkout recorded at start, reads just the registry so it works even when the agent is gone or the workspace was closed by hand, and leaves the branch decision to `worktree kill`'s merge gate — use that when you want to see the gate first.

`reap --force` clears the dirty-checkout refusal and proceeds through a busy lock. The teardown is idempotent: each step re-confirms the identity, treats `workspace_not_found` and `not_git_worktree` as "nothing to do", and derives the `removed` output from what actually happened — so two concurrent `reap --force` of the same delegate each exit 0 with the same end state, and the loser simply reports `removed: false` for the fields the winner removed. If the recorded checkout was removed outside flock, `reap` closes the workspace only when it still belongs to that checkout, prunes stale Git worktree metadata, then clears the entry. A reap that cannot get an answer from the server (a timeout or a dead socket) never counts that as removal: it exits 1 and keeps the entry, so it can be retried.

`pane read --source detection` reads exactly the unscrolled screen used by agent detection, excluding scrollback; `--lines` does not expand that screen. It supports text and ANSI formats.

### Delegate stall verdicts

An await returns `outcome: "not_started"`, reason `idle_without_new_turn`, and exit **8** only after continuously observing an idle agent with an unchanged empty composer and no new turn for **30 seconds (`STARTUP_ALLOWANCE`) plus `--settle`**. The window cannot start before `submitted_at_ms`; a later `wait` starts a fresh observation window instead of assuming the unobserved interval was idle. Composer changes, queued messages, startup indicators, missing samples, and unknown state reset the window. Working state or a new working entry cancels the not-started diagnosis for that round. This allows queued cold-start prompts and prompt hooks that arrive before working state to proceed normally. A shorter `--timeout` still returns timeout. Exit **8** is command-specific: `agent send` uses it for `unconfirmed`, while delegate awaits use it for `not_started`. Every event-time S1 request includes an `Observed outcome` line with the verdict and reason, including this evidence. Guarded submission waits up to two seconds for a partial composer repaint before refusing to send Enter.

`start --await`, `send --await`, and `wait` accept `--silence DURATION` (default `3m`; `0` disables it). Units are `ms`, `s`, `m`, and `h`, including combinations such as `1m 30s`. A working agent whose unscrolled detection screen stays unchanged after removing recognized harness status rows for this duration returns `outcome: "stalled"`, reason `silence`, and exit **7**. Viewport scrolling and recognized spinner, elapsed-counter, and progress-bar rows do not reset the timer; a new transcript line does. OpenCode provider retry screens report blocked with reason `provider_limit`. `agent get` and `delegate status` expose the live `blocked_reason` and `retry_after_ms`. Delegate waits tolerate short retries: they return reason/verdict `provider_limit` and exit **7** only when the ETA is at least the silence window or the retry persists continuously for that window. With `--silence 0`, only an ETA of at least 5 minutes stalls; short retries continue waiting, and idle means recovery. These rules also apply to older servers reporting working or unknown. Readiness timeout verdicts retain the provider reason and ETA, with `unknown` for a short retry rather than a human-input verdict.

Raise `--silence` for long builds or tools that print nothing while running. Recognized Claude, Codex, and opencode spinners do not count as progress; Claude running-tool elapsed counters are normalized while the tool row remains evidence. Unknown harness animations may still reset the timer, so a hung tool in an unknown harness can go undetected.

Readiness still defaults to 60 seconds. On readiness expiry, JSON includes `outcome: "ready_timeout"`, verdict `waiting_on_input`, `stalled`, or `unknown`, and `last_line` (the last nonblank screen line); exit remains 1. Round outcomes include `verdict`, `reason`, `retry_after_ms`, `last_line`, and `s1`. `delegate status` includes the latest persisted verdict for the current round.

System One is optional: configure `[systemone] urls = ["http://127.0.0.1:8000/v1/systemone"]` and `timeout_s = 3`, or set `SYSTEMONE_URL` to comma- or space-separated URLs. The environment variable takes precedence. Only round endings and readiness expiry send the last 4 KB of the unscrolled detection screen; polls never send requests. A response adds advisory `s1: {fused, verdict}` without changing the exit code. Unavailable endpoints yield `s1: null`. Requests share a bounded timeout (default 3 seconds); an endpoint failing three times is skipped for ten minutes.

## Notifications

```bash
flk notification show <title> [--body TEXT] [--position top-left|top-right|bottom-left|bottom-right] [--sound none|done|request]
flk notification list [--unread] [--limit N]
flk notification read <notification-id> | --all
```

`show` raises a notification through the configured `[ui.toast]` delivery. It exits 0 when `shown:true` and 3 when `shown:false`, preserving the JSON response so callers can inspect `reason` and fall back to another channel. `reason:"disabled"` means the server config has `[ui.toast] delivery = "off"` (the default), which disables popups. Other refusal reasons are `busy`, `rate_limited`, and `no_foreground_client`. API errors exit 1; invalid arguments exit 2. `list` reads what Flock has filed — every outcome it decided was worth saying, newest first: an agent that blocked or finished, and every `show` call, including the ones it refused to display. `read` acknowledges one or all of them.

The notification log panel inside the TUI (`prefix+i`, or the sidebar `menu` row → `notifications`) lists and acknowledges the same records: all three surfaces read one filter over one projection, so `--unread` and the panel's `u` filter can never disagree about what is unread.

Each row carries a `kind`, which is what makes the log readable rather than a stream: `attention` is something waiting on you — an agent that went blocked, or `blocking` mail for a recipient that muted itself — `outcome` is something that finished and produced a result, and `notice` is everything else worth keeping, which is every `show` call and every fleet failure. An escalation of that kind also names the pane that is waiting, so the title badge does not count a blocked pane twice.

Filing does not depend on `[ui.toast] delivery`. `off` — the default — asks for no popups, not for Flock to forget: the outcome is still recorded and still readable here. Records survive a server restart, and reading the list is not the same as acknowledging it, because acknowledging is what lets an old record be dropped.

### Sync after an upgrade

Run `flk integration sync --dry-run` to review the plan, then `flk integration sync` with the newly installed binary to refresh installed Claude, Codex and OpenCode hook assets and flock MCP launch paths. This works for package-manager installs and when the binary is already current. Each target reports `updated` (`would-update` in dry-run, including JSON output), `already-current`, `skipped-declarative`, or `failed`; failures return exit code 1 and do not prevent other targets from being checked.

Sync uses the selected `CLAUDE_CONFIG_DIR` and `CODEX_HOME` profiles (or their defaults) and the user OpenCode config; it does not search other homes or profiles. Only MCP entries named flock launching a store-pinned flk executable (including the legacy flock name) with `mcp serve` are migrated; bare PATH commands and explicit stable custom paths are preserved. ## MCP server

```bash
flk mcp serve
```

Speaks the Model Context Protocol over stdio: newline-delimited JSON-RPC 2.0 on stdin/stdout. Wire it into an MCP client (Claude Desktop, `mcp` CLI, agent runners) to give an agent a read-mostly view of the flock — list agents, read panes, fork Claude conversations, send/reply pane-to-pane messages, walk fork lineage, and read the files a human has handed over. `FLOCK_SOCKET_PATH` selects the flock server socket; the default is the current session's.

The server advertises two capabilities: `tools` (the closed table below) and `resources` (handed-over files). It claims no `subscribe`/`listChanged` sub-capability, because it pushes no resource notifications.

### Addressing across hosts

A pane id names a placement on **one** server, so it cannot address anything on another machine. An `agent_id` can: it is fleet-global and restart-stable (ADR-0008), and it is what `flock_agent_list`'s `fleet` rows report alongside the `host` the agent lives on and a `local` flag.

The two-step is the whole story:

```jsonc
// 1. flock_agent_list  →  find the agent, wherever it is
{ "fleet": [
  { "agent_id": "agent_atlas_6f21c4", "host": "atlas",  "local": false, "route": "atlas" },
  { "agent_id": "agent_hopper_9d0e17", "host": "hopper", "local": true,  "pane_id": "w1:p2" }
]}

// 2. flock_msg_send  →  address it by identity
{ "to": { "type": "agent", "agent": "agent_atlas_6f21c4" }, "body": "…" }
```

Replies need no addressing: `flock_msg_reply` carries the incoming `correlation_id` and uses its durable return binding. For a direct mesh request, the target pushes the reply over an enrolled outbound edge when available, or holds it (`state: "held"`) for origin collection. Collection starts about five seconds after confirmed delivery, works without an active waiter, and stops at the first final answer. The target needs no outbound peer entry. Held answers do not consume outbound retry slots, and a newly enrolled outbound edge pushes them. Automatic collection closes at the first final answer; send a new request for a follow-up that needs automatic collection on a one-way edge. Collection survives restart, deduplicates imports, and pauses with the fleet. An active reply waiter or a reconnect restores fast polling; `msg.status` reports terminal import failures as `collect_failed`. Replies to messages without a valid return binding return `reply_unavailable`.

**Spokes can message their hub without outbound peers.** A spoke with a pinned hub and no `[[peers]]` persists its send even while the edge is disconnected and returns `state: "queued"` with a minted `message_key` and `path: "via <hub>"`. The hub collects the spoke's durable outbox over its held edge, checks `allow_from` against the authenticated spoke origin, imports once, and acknowledges. Lost acknowledgements, restart and live handoff preserve custody and deduplication. Replies are pushed down with `mesh.deliver`; an offline edge leaves the answer held until re-enrollment. Step 1 allows a local recipient on the hub; a target beyond the hub is refused with `forward_limit`, visible in the spoke's `msg.status`. Multi-hop forwarding is separate mesh work.

A fresh send can be refused with `msg_target_not_found` (unknown target and no pinned hub), `peer_not_configured` (no usable configured route), or `sender_unresolved` (a spoke send must come from inside an agent pane). Once accepted into custody, `queued` means awaiting delivery, not recipient inbox import. A hub's permanent refusal, including `msg_target_not_found`, `msg_not_allowed` or `forward_limit`, is retained in the originating spoke's `msg.status` as `state: "refused"` with the reason in `detail`.

The tool table is closed and intentionally read-mostly. Mutating verbs (`pane.close`, `worktree.remove`/`create`, `agent.start`/`rename`/`focus`, raw pane `send_*`, `server.*`, `notification.*`, `integration.*`) are not exposed and refuse with JSON-RPC code `-32000` and `data.refusal = "not_exposed_via_mcp"`. Modelled flock refusals (`unsupported_for_agent`, `no_agent_session`, `transcript_not_found`, …) propagate through the same code with the flock error code in `data.refusal`.

### Resources: files handed over to an agent

Tools are not the whole surface. A file dropped on a pane used to reach its agent only as a pasted path, deleted when the operator's client disconnected. It is now also an **MCP resource** — content the server holds and can name — so an agent lists and reads it natively instead of scraping it out of its own input surface.

```jsonc
// resources/list
{ "resources": [{
  "uri": "flock://handoff/file:1a04ff2c3b:0",
  "name": "client-1-clipboard-1756-0.pdf",
  "description": "file handed to agent_atlas_6f21c4; staged at /tmp/… on this host",
  "mimeType": "application/pdf",
  "size": 184320
}]}

// resources/read
{ "contents": [{ "uri": "flock://handoff/file:1a04ff2c3b:0", "mimeType": "application/pdf", "blob": "JVBERi0…" }] }
```

Text comes back in `text`, everything else base64 in `blob`. `resources/read` takes a URI carrying a flock-minted id and nothing else — there is no path parameter anywhere on this surface. Files over 4 MiB refuse with `handoff_too_large`; read them from the `path` in the listing instead. The list is not filtered by which agent is asking, because a filtered list that comes back empty cannot be told apart from a server that was handed nothing.

The paste still happens as well: flock cannot tell from outside a pane whether the agent in it has this MCP server wired up.

## Reporting a bug

```bash
flk report template [bug] > bug.md
flk report bug --file bug.md [--print|--open|--body-only] [--repo owner/name] [--last N] [--all-levels] [--no-diagnostics]
flk report bug --current TEXT --expected TEXT --repro TEXT --impact TEXT
```

`flk report` composes a bug report from what you wrote plus what the binary already knows: version, update channel, build commit, OS and architecture, terminal, shell, client protocol, and the running server's version and protocol compatibility. Logs come from the same directory with the server dead — which is exactly when you file one — filtered to WARN and ERROR by default (`--all-levels` includes routine activity, `--last N` changes the count, `--no-diagnostics` attaches none). Every record goes through the allowlist and scrubber first, so paths, hostnames, tokens and usernames are stripped before anything is shown. `--repo owner/name` files against some other repository; nothing else can redirect a report, not even the environment.

Getting the report off your machine takes a human, and there are two ways to do it.

`--open` prints a preview, copies the log tail to your clipboard, and opens GitHub's real bug form, prefilled. This is the route that runs the template's own required-field validation and gives you the reproducibility confirmation to tick.

`--body-only` writes **just the issue body to stdout** — no `destination:` header, no prefilled link, no footer — so it pipes straight into a filing command you run yourself:

```bash
flk report bug --file bug.md --body-only > "$HOME/flock-bug.md"
gh issue create --repo gerchowl/flock --title "pane read never returns" --body-file "$HOME/flock-bug.md"
```

The preview, any advisories and the exact command to run go to **stderr**, so what you reviewed is what gets piped and the preview never lands inside the body. The body has no URL length cap, so on this route the redacted log tail rides inside it rather than going to the clipboard: a headless report carries more evidence than a browser one, not less. `gh` posts a raw body and bypasses the issue form, so nothing validates it and the reproducibility confirmation is not one `gh` can set — use `--open` when you want GitHub's own form to run the checks.

Where you redirect that body is your call and worth choosing deliberately: unlike `--open`, this route writes a file, and the file holds paths, versions and the log tail. Keep it out of a checkout you might commit from, and delete it once the issue is filed.

Flock never files the report itself (ADR-0010 decision 6). The one write path it has is `flk issue drop --file-it`, which is yours to confirm.
