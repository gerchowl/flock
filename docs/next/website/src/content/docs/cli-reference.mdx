title: CLI reference

Flock’s CLI talks to the running server over the same local socket API used by integrations and agents.

Most commands print JSON responses. Use them from scripts when you want deterministic automation.

## Launch and status

```bash
flock                         # launch or attach to the default session
flock --session work          # launch or attach to a named session
flock --remote workbox        # attach through SSH, using local keybindings
flock --remote workbox --remote-keybindings server
flock --remote workbox --handoff
flock --no-session            # single-process escape hatch
flock --default-config        # print default config
flock update                  # download and install from the configured channel
flock update --handoff        # opt into live handoff for supported running servers
flock channel show            # print stable or preview
flock channel set preview     # opt into preview builds
flock channel set stable      # return to stable releases
flock --version               # print version
```

Status commands:

```bash
flock status
flock status server
flock status client
```

## Server

```bash
flock server
flock server stop
flock server reload-config
```

`flock server` runs the headless server explicitly. Use it for supervised or service-style setups. `reload-config` applies reloadable settings without restarting panes.

## Config

```bash
flock config check [--path PATH]
flock config edit
flock config reset-keys
```

`config check` validates a config without starting or touching a server, and exits on a three-way code so it can gate a deploy:

| Exit | Meaning |
| --- | --- |
| `0` | clean |
| `1` | loaded, with advisory warnings (deprecated keys, keybinding conflicts) |
| `2` | did not load — a session would fall back to built-in defaults |

Every diagnostic is printed, unlike the in-app warning banner, which truncates to four lines. The check resolves keybindings in full, so conflicts and deprecation renames are caught rather than just TOML syntax errors.

`--path` checks a file that is not the live config, which is what a build-time gate wants:

```bash
flock config check --path ./config.toml || exit 1
```

Base and `config.local.toml` layering resolves exactly as it does at runtime. This is unrelated to `flock checks`, which runs the health-check runner.

## Preflight

```bash
flock preflight [--require TARGET]...
```

Answers one question: **is flock functional on THIS host right now?** `config check` proves the config parses; preflight also asks whether the things that config switches on are actually wired here. It exits on the same three-way code, so an activation or deploy can gate on it:

| Exit | Meaning |
| --- | --- |
| `0` | ready |
| `1` | works, but something wants attention |
| `2` | a configured feature is broken here |

It checks the config (by running `config check`), each agent integration, that the worktree directory is writable, and that `git` / `ssh` / `gh` are on `PATH`. Failures name the fix rather than the symptom.

**It never touches the network.** Preflight is built to run inside a Home Manager activation, so it cannot be allowed to hang one — peer reachability belongs to `flock status`, on a different clock.

### Why `--require`

An integration that is missing might be a deliberate opt-out, so flock will not fail your deploy over it on its own judgement:

| Hook state | Agent on this host | Result |
| --- | --- | --- |
| current | — | `0` |
| stale | — | `2` — it was wired and is now broken |
| missing | yes | `1` — might be intentional |
| missing | no | silent — not this host's business |

`--require TARGET` (repeatable) says *this deployment meant to have that one*, turning a missing hook into a `2`. flock cannot infer intent; the thing that deploys it can. A required target whose agent has vanished entirely still fails — passing quietly there would hide exactly the breakage this catches.

```bash
# In an activation: fail loudly if the Claude hook did not install.
flock preflight --require claude || exit 1
```

This matters because a half-wired host is silent by nature. Before the prompt-history panel read session transcripts it was fed purely by lifecycle hooks, so a host whose integration never installed showed an *empty panel* — indistinguishable from having no history yet.

:::note
A debug build reads `~/.config/flock-dev/config.toml`, so a debug-built preflight checks a different file than an installed one.
:::

## Sessions

```bash
flock session list [--json]
flock session attach <name>
flock session stop <name> [--json]
flock session delete <name> [--json]
```

Use `default` as the session name when you need to stop the default session explicitly.

## Workspaces

```bash
flock workspace list
flock workspace create [--cwd PATH] [--label TEXT] [--focus] [--no-focus]
flock workspace get <workspace_id>
flock workspace focus <workspace_id>
flock workspace rename <workspace_id> <label>
flock workspace close <workspace_id>
```

Create a workspace without stealing focus:

```bash
flock workspace create --cwd ~/project --label api --no-focus
```

## Worktrees

```bash
flock worktree list [--workspace ID | --cwd PATH] [--json]
flock worktree create [--workspace ID | --cwd PATH] [--branch NAME] [--base REF] [--path PATH] [--label TEXT] [--focus] [--no-focus] [--json]
flock worktree open [--workspace ID | --cwd PATH] (--path PATH | --branch NAME) [--label TEXT] [--focus] [--no-focus] [--json]
flock worktree remove --workspace ID [--force] [--json]
```

Worktrees are normal Flock workspaces with Git checkout provenance. `worktree create` creates a Git worktree checkout, opens it as a workspace, and groups it with the parent repo workspace. Without `--path`, Flock creates the checkout under `<worktrees.directory>/<repo>/<branch-slug>`.

`workspace close` closes Flock state only. `worktree remove` is the explicit checkout deletion path; it runs `git worktree remove`, never deletes the branch, and requires `--force` when Git refuses a dirty checkout.

## Panes

```bash
flock pane list [--workspace <workspace_id>]
flock pane get <pane_id>
flock pane rename <pane_id> <label>|--clear
flock pane split <pane_id> --direction right|down [--cwd PATH] [--focus] [--no-focus]
flock pane close <pane_id>
```

Read output:

```bash
flock pane read <pane_id> [--source visible|recent|recent-unwrapped] [--lines N]
flock pane read <pane_id> --source visible --ansi
flock pane read <pane_id> --source recent-unwrapped --lines 120
```

Send input:

```bash
flock pane send-text <pane_id> <text>
flock pane send-keys <pane_id> <key> [key ...]
flock pane run <pane_id> <command>
```

`pane run` submits text plus Enter atomically. Prefer it over `send-text` plus `send-keys Enter` for commands.

Report agent state from custom hooks:

```bash
flock pane report-agent <pane_id> \
  --source ID \
  --agent LABEL \
  --state idle|working|blocked|unknown \
  [--message TEXT] \
  [--custom-status TEXT] \
  [--seq N] \
  [--agent-session-id ID] \
  [--agent-session-path PATH]
```

`pane get`, `pane list`, `agent get`, and `agent list` include a read-only `agent_session` object when an official integration has reported a native session reference. If no native session reference is stored, the field is omitted.

Those commands include `foreground_cwd` when Flock can resolve the cwd of the foreground process controlling the pane. The existing `cwd` field remains the pane/workspace cwd used for labels and follow-cwd behavior.

Report display-only pane metadata without taking over semantic state:

```bash
flock pane report-metadata <pane_id> \
  --source ID \
  [--agent LABEL] \
  [--applies-to-source ID] \
  [--title TEXT|--clear-title] \
  [--display-agent TEXT|--clear-display-agent] \
  [--custom-status TEXT|--clear-custom-status] \
  [--state-label STATUS=TEXT] \
  [--clear-state-labels] \
  [--seq N] \
  [--ttl-ms N]
```

`STATUS` is one of `idle`, `working`, `blocked`, `done`, or `unknown`. `--agent` is a guard for the authoritative agent label. `--applies-to-source` is a guard for the active lifecycle authority source. Use `--display-agent` to change the visible name.

## Agents

```bash
flock agent list
flock agent get <target>
flock agent read <target> [--source visible|recent|recent-unwrapped] [--lines N] [--format text|ansi] [--ansi]
flock agent send <target> <text>
flock agent rename <target> <name>|--clear
flock agent focus <target>
flock agent wait <target> --status <idle|working|blocked|unknown> [--timeout MS]
flock agent attach <target> [--takeover]
flock agent start <name> [--cwd PATH] [--workspace ID] [--tab ID] [--split right|down] [--focus|--no-focus] -- <argv...>
flock agent fork <target> [--branch NAME] [--base REF] [--path PATH] [--label LABEL] [--pivot TEXT|--no-pivot] [--focus|--no-focus]
flock agent hibernate <target>
flock agent resume <target>
flock lineage <target> [--json]
flock msg send <target> <text...> [--repo NAME] [--correlation-id ID] [--reply-to ID]
flock msg reply <correlation_id> <text...>
flock msg list [--pane TARGET]
flock checks list
flock checks ack <name>
flock checks run <name>
```

Agent targets can be terminal IDs, unique agent names, detected or reported agent labels, or legacy pane IDs. Names and labels are agent identities. Terminal IDs and legacy pane IDs are low-level escape hatches.

`agent read` reads the resolved terminal stream. `agent send` writes literal text to that stream. `agent get`, `agent focus`, `agent wait`, and `agent attach` require the resolved terminal to have agent identity. `agent rename` can assign that identity.

Use `pane send-text`, `pane send-keys`, `pane run`, and `terminal attach` for ordinary terminals, servers, tests, shells, or low-level terminal control. Use `pane run` when you want to submit a command with Enter.

`msg send` queues a message for another pane's agent; it is typed and submitted as a chat turn at that pane's next settled turn boundary, tagged with the sender pane and a correlation id the recipient can `msg reply` to. `<repo>:<pane>` splits only when the left side names a known repo; use `--repo` to be explicit. `lineage` prints the fork ancestry chain of a pane, worktree, or branch — reconstructed from the durable event log, so it survives server restarts. `agent fork` branches the target's conversation into a new linked worktree: it creates the worktree, then starts a pane that resumes a fork of the agent's session, optionally seeded with a pivot prompt (`--pivot`; `<branch>` resolves to the final branch name, `--no-pivot` opts out of the configured template). Only Claude sessions can fork; other agents are refused with `unsupported_for_agent` because a plain resume would attach two processes to one session id.

`agent hibernate` parks a pane cleanly: the agent's child process is asked to exit, the resume plan is stashed on the terminal, and the pane is kept. The next focus (or an explicit `agent resume`) respawns it. Panes without a resumable session refuse with `hibernate_unsupported` (data-loss guard).

`checks list` enumerates the runner's script checks together with the built-in state (blocked-alert / hibernation / issue-guard). `checks ack <name>` silences the next fire — for script checks the debounce window; for the built-in blocked-alert, the current in-flight episodes. `checks run <name>` forces a script check due right now.

## Direct terminal attach

```bash
flock terminal attach <terminal_id> [--takeover]
```

Detach from direct attach with `ctrl+b q`. Send literal `ctrl+b` with `ctrl+b ctrl+b`.

## Waits

Wait for output in a pane:

```bash
flock wait output <pane_id> --match <text> [--source visible|recent|recent-unwrapped] [--lines N] [--timeout MS] [--regex] [--raw]
```

Wait for pane agent state:

```bash
flock wait agent-status <pane_id> --status <idle|working|blocked|done|unknown> [--timeout MS]
```

Use `wait output` for normal commands and servers. Use `wait agent-status` for coding agents.

## MCP server

```bash
flock mcp serve
```

Speaks the Model Context Protocol over stdio: newline-delimited JSON-RPC 2.0 on stdin/stdout. Wire it into an MCP client (Claude Desktop, `mcp` CLI, agent runners) to give an agent a read-mostly view of the flock — list agents, read panes, fork Claude conversations, send/reply pane-to-pane messages, and walk fork lineage. `FLOCK_SOCKET_PATH` selects the flock server socket; the default is the current session's.

The tool table is closed and intentionally read-mostly. Mutating verbs (`pane.close`, `worktree.remove`/`create`, `agent.start`/`rename`/`focus`, pane `send_*`, `server.*`, `notification.*`, `integration.*`) are not exposed and refuse with JSON-RPC code `-32000` and `data.refusal = "not_exposed_via_mcp"`. Modelled flock refusals (`unsupported_for_agent`, `no_agent_session`, `transcript_not_found`, …) propagate through the same code with the flock error code in `data.refusal`.

Exposed tools:

| Tool | Wraps | Notes |
| --- | --- | --- |
| `flock_agent_list` | `agent.list` | `blocked` agents need attention. |
| `flock_agent_get` | `agent.get` | Target is a pane id, terminal id, or unique agent name. |
| `flock_agent_read` | `agent.read` | Reading marks the pane seen — use sparingly. |
| `flock_agent_fork` | `agent.fork` | Fork a Claude conversation into a new worktree+pane; `pivot` seeds the opening turn. |
| `flock_agent_lineage` | `agent.lineage` | Fork ancestry chain, deepest first. |
| `flock_msg_send` | `msg.send` | Delivered at the recipient's next settled idle boundary. |
| `flock_msg_reply` | `msg.reply` | Routes to the original sender's pane. |
| `flock_msg_list` | `msg.list` | Undelivered messages. |
| `flock_pane_read` | `pane.read` | Same seen caveat as `agent.read`. |
| `flock_worktree_list` | `worktree.list` | Feeds the fork-vs-message decision. |

## Read sources

| Source | Meaning |
| --- | --- |
| `visible` | Current rendered screen. Best for UI feedback loops. |
| `recent` | Recent scrollback with terminal wrapping. |
| `recent-unwrapped` | Recent scrollback without soft wrapping. Best for logs. |

## Environment variables

| Variable | Purpose |
| --- | --- |
| `FLOCK_CONFIG_PATH` | Override the config file path. |
| `FLOCK_SESSION` | Select a named session for CLI commands. |
| `FLOCK_SOCKET_PATH` | Low-level socket path override. |
| `FLOCK_LOG` | Set log filter, for example `FLOCK_LOG=flock=debug`. |
| `FLOCK_<UPPER_SNAKE_PATH>` | Generic override for any scalar config field (ADR-0002); sits BELOW the config file. |
| `FLOCK_DISABLE_SOUND` | Deprecated alias for `FLOCK_UI_SOUND_ENABLED=false`. Sits below the file (removal after one release). |
