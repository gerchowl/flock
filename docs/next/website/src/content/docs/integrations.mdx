Flock detects supported agents automatically. Official integrations can add native session identity for restore, semantic state reports, or both. Claude Code, Codex, and OpenCode state comes from screen detection even when their session identity integrations are installed.

Use integrations when you want native agent session restore, direct state reports from Pi/OMP/Copilot/Kimi/Hermes/Qoder-style hooks or plugins, or both.

## Install integrations

Open settings inside Flock and use the integrations tab to install recommended integrations for agents found on your `PATH`, or run commands manually:

```bash
flk integration sync [--dry-run]
flk integration install pi
flk integration install omp
flk integration install claude
flk integration install codex
flk integration install copilot
flk integration install kimi
flk integration install opencode
flk integration install hermes
flk integration install qodercli
```

Claude, Codex, and OpenCode installation also adds an MCP entry named flock when none exists. Its command is an absolute launch path, retaining profile symlinks instead of resolving them into `/nix/store`. Claude uses `~/.claude.json`, or `$CLAUDE_CONFIG_DIR/.claude.json` for a selected profile; Codex uses `$CODEX_HOME/config.toml` (default `~/.codex/config.toml`); OpenCode uses `~/.config/opencode/opencode.json` or an existing `opencode.jsonc`.

Existing MCP entries, including custom commands, arguments and environment, are preserved. Symlinked or read-only MCP configs receive guidance for their configuration owner. Initial registration in JSONC with comments requires an owner-managed edit; sync preserves JSONC comments when updating a registered command. `flk integration status` and `--outdated-only` flag flock MCP commands pinned to `/nix/store`; update the owning configuration to an absolute profile/user-local launch path and reconnect the harness. Already-running bridges retain their executable and tool catalog. Uninstall removes hooks/plugins and leaves MCP entries under their configuration owner's control.

MCP registration failures print guidance and leave successful hook/plugin installation intact, including installations launched only from `/nix/store` and commented OpenCode JSON files. Pane hooks use their own server executable; when no stable profile path exists, they retain its store path so hook calls still work. The existing macOS TCC copy behavior remains the same.

Claude profiles that register a shared hook script in `settings.json` report that script's version. Reinstalling reuses the shared registration without adding a second profile copy.

## How Flock uses integrations

Flock combines three signals:

| Signal | Purpose |
| --- | --- |
| Process detection | Identifies which pane owns which running process. |
| Screen heuristics | Infers visible native agent state such as `working` or `blocked`. |
| Integration events | Reports native session identity, semantic state, or both depending on the integration. |

Claude Code, Codex, and OpenCode state detection is screen-read first. Their Flock-owned integrations do not author `idle`, `working`, or `blocked` state. Pi, GitHub Copilot CLI, and Hermes Agent report semantic state and session identity. OMP, Kimi Code CLI, and Qoder CLI report semantic state but do not provide native session restore. Custom socket integrations can report state when they define state that is not visible in the native terminal UI.

Some integrations report native agent session references. Flock uses official session references to resume Claude Code, Codex, GitHub Copilot CLI, Pi, Hermes Agent, and OpenCode panes after a Flock server restart unless `[session] resume_agents_on_restore = false` disables it.

Native session restore requires current Flock integrations: Pi integration version `2`, Claude Code version `5`, Codex version `5`, GitHub Copilot CLI version `1`, OpenCode version `4`, or Hermes Agent version `2`. OMP integration version `2`, Kimi Code CLI integration version `1`, and Qoder CLI integration version `1` report agent state only. Check installed versions with `flk integration status`.

## Pi

Install the Pi integration:

```bash
flk integration install pi
```

Flock writes the bundled extension to:

```text
~/.pi/agent/extensions/flock-agent-state.ts
```

If `PI_CODING_AGENT_DIR` is set, Flock writes to `$PI_CODING_AGENT_DIR/extensions/flock-agent-state.ts` instead. The extensions directory must already exist. Uninstall removes only that extension file.

## OMP

Install the OMP integration:

```bash
flk integration install omp
```

Flock writes the bundled extension to:

```text
~/.omp/agent/extensions/flock-omp-agent-state.ts
```

If `PI_CODING_AGENT_DIR` is set, Flock writes to `$PI_CODING_AGENT_DIR/extensions/flock-omp-agent-state.ts` instead. The extensions directory must already exist. Uninstall removes only that extension file.

The OMP integration reports `omp` as the agent label through Flock's socket API. It does not require native process detection for the `omp` executable.

## Claude Code

Install the Claude Code hook:

```bash
flk integration install claude
```

The hook reports Claude Code session identity to the local Flock socket on session start. Claude Code state comes from Flock's screen detection.

Flock uses `~/.claude` by default, or `CLAUDE_CONFIG_DIR` when set. The Claude config directory must already exist. Install writes `hooks/flock-agent-state.sh` and updates `settings.json` with Flock hook entries. Uninstall removes the matching hook entries and deletes the hook script.

## Codex

Install the Codex hook:

```bash
flk integration install codex
```

The Codex hook reports session identity through the same local socket API used by other integrations. Codex state comes from Flock's screen detection.

Flock uses `~/.codex` by default, or `CODEX_HOME` when set. The Codex config directory must already exist. Install writes `flock-agent-state.sh`, updates `hooks.json`, and ensures `[features] hooks = true` in `config.toml`. It also removes the deprecated top-level `codex_hooks` flag when present. Uninstall removes Flock entries from `hooks.json` and deletes the hook script, but leaves `config.toml` unchanged.

## GitHub Copilot CLI

Install the GitHub Copilot CLI hook:

```bash
flk integration install copilot
```

Copilot state is reported through the same local socket API used by other integrations.

Flock uses `~/.copilot` by default, or `COPILOT_HOME` when set. The Copilot config directory must already exist. Install writes `hooks/flock-agent-state.sh` and updates `settings.json` with Flock hook entries. The hook maps prompt submission, tool use, post-tool progress after approvals, `ask_user` prompts, `exit_plan_mode` plan review prompts, permission notifications, agent idle notifications, turn stops, and session exits into Flock state. Uninstall removes Flock entries from `settings.json` and deletes the hook script.

The shell hooks for Claude, Codex, Copilot, Kimi, and Qoder CLI delegate to `flk hook` and require no Python interpreter. Inside a Flock pane, a missing or non-executable Flock binary prints a stderr diagnostic on each hook call. Reinstall the integration to update an older hook script.

After Copilot emits a session-bearing event, Flock can use the reported session id to resume the pane with `copilot --resume=<id>`.

## Kimi Code CLI

Install the Kimi Code CLI hook:

```bash
flk integration install kimi
```

The hook reports semantic state to Flock when Kimi Code emits lifecycle, tool, approval, and session events. It requires Kimi Code CLI `0.8.0` or newer.

Flock uses `~/.kimi-code` by default, or `KIMI_CODE_HOME` when set. The Kimi Code config directory must already exist. Install writes `hooks/flock-agent-state.sh` and appends Flock-managed `[[hooks]]` entries to `config.toml`. Uninstall removes the Flock-managed config block and deletes the hook script.

Native screen heuristics remain available when the hook is not installed.

## OpenCode

Install the OpenCode plugin:

```bash
flk integration install opencode
```

Flock writes the plugin to `~/.config/opencode/plugins/flock-agent-state.js`. The OpenCode config directory must already exist. Uninstall removes only that plugin file.

The plugin reports session identity while OpenCode runs inside a Flock pane. After OpenCode emits a session-bearing event, Flock can use the reported session id to resume the pane with `opencode --session <id>`. OpenCode state comes from Flock's screen detection.

## Hermes Agent

Install the Hermes Agent plugin:

```bash
flk integration install hermes
```

Flock writes `~/.hermes/plugins/flock-agent-state/` and enables `flock-agent-state` in `~/.hermes/config.yaml`. The Hermes config directory must already exist. Restart Hermes after installing so the plugin loads. Uninstall removes the plugin directory and removes `flock-agent-state` from `plugins.enabled`.

The plugin reports lifecycle, tool, approval state, and session id while Hermes runs inside a Flock pane. Flock can use the reported session id to resume the pane with `hermes --resume <id>`. Native screen heuristics remain available when the plugin is not installed.

## Qoder CLI

Install the Qoder CLI hook:

```bash
flk integration install qodercli
```

The hook reports semantic state to Flock when Qoder CLI emits lifecycle events.

Flock uses `~/.qoder` by default, or `QODER_CONFIG_DIR` when set. The Qoder config directory must already exist. Install writes `hooks/flock-agent-state.sh` and updates `settings.json` with Flock hook entries. Uninstall removes the matching hook entries and deletes the hook script.

Native screen heuristics remain available when the hook is not installed.

## Custom status labels

Integrations can report a short visual label without changing the semantic state.

For example, an agent can remain semantically `working` while showing `indexing` in the UI.

```bash
flk pane report-agent \
  --source custom:docs \
  --agent docs-bot \
  --state working \
  --custom-status indexing
```

A hook running inside the pane's agent can leave the pane id out: `report-agent` then reports to the calling pane, exactly as `report-recap` and `report-reply` do. Pass it as the leading argument, or with `--pane <pane_id>`, when the reporter runs outside the pane.

User hooks that run next to a Flock-managed integration should use metadata instead of `report-agent`. Metadata changes presentation without taking over the integration's `idle`, `working`, `blocked`, or session restore authority. `--agent` guards the report so it only applies while that authoritative agent is active. `--applies-to-source` guards the report so it only applies while that lifecycle authority source is active. `--display-agent` changes the visible name.

```bash
flk pane report-metadata \
  --source user:claude-title \
  --agent claude \
  --title "Refactor auth middleware" \
  --display-agent "Claude: auth" \
  --custom-status "refactor auth" \
  --state-label working="refactoring auth" \
  --ttl-ms 3600000
```

`report-metadata` defaults to the calling pane. Pass `--pane <pane_id>` or a legacy leading pane id when reporting from outside the pane.

Custom status and state labels are visual-only. Waits, notifications, and workspace rollups still use the semantic state.

## Debug integration state

List known agents:

```bash
flk agent list
```

Read a pane when you need to verify what Flock can see:

```bash
flk pane read 1-1 --source recent --lines 50
```

If integration state looks wrong, first confirm the agent is running inside Flock and that the relevant hook or plugin was installed for the same user account.

### Sync after an upgrade

Run `flk integration sync --dry-run` to review the plan, then `flk integration sync` with the newly installed binary to refresh installed Claude, Codex and OpenCode hook assets and flock MCP launch paths. This works for package-manager installs and when the binary is already current. Each target reports `updated`, `already-current`, `skipped-declarative`, or `failed`; failures return exit code 1 and do not prevent other targets from being checked.

Sync uses the selected `CLAUDE_CONFIG_DIR` and `CODEX_HOME` profiles (or their defaults) and the user OpenCode config; it does not search other homes or profiles. Only MCP entries named flock launching a bare or store-pinned flk executable (including the legacy flock name) with `mcp serve` are migrated; explicit stable custom paths are preserved. Custom commands and unrelated entries are preserved, as are arguments, environment, permissions, comments and Codex hook trust. Symlinked or read-only configs are skipped with a fragment to merge through their Nix/Home Manager configuration owner.

Sync reports client, installed binary and server drift but does not perform a server handoff or stop sessions. Use `flk server live-handoff` when needed. Running agents need `flk agent restart` or an MCP reconnect to load the new bridge and tool catalog.
