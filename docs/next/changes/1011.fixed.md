- Live handoff no longer times out forever on a pane with a healthy terminal (#1011). An empty input write (from an inbox wake, paste or injection) used to sit at the head of the pane's write queue and be retried forever, because writing zero bytes "succeeds" by writing nothing. Empty writes are now never queued and are skipped if one is already queued. A write of a non-empty buffer that keeps accepting zero bytes is retried a bounded number of times, then the pane's writer is marked broken: its queue is dropped and later input is refused with an error (so a guarded submit reports `write_failed`, `pane.send_input` fails, including input queued behind held keystrokes, and a guarded submit whose held keystrokes could not be replayed records `held_input_not_written: true` in its delivery attempt), never accepted and silently lost. The writer is re-armed after five seconds, or when a handoff rolls back. The warning is logged at most once a minute per pane. This also ends the flood of `PTY actor write returned zero bytes` warnings in the server log (#997).
- A live handoff that still cannot drain a pane names it (#981): the error lists each stuck pane as `wX:pN` with its pending bytes, pid and title instead of an anonymous timeout. A writer that accepts zero bytes during the drain fails the handoff at once with the queue kept, and the pane is named the same way. Panes drain concurrently, so many stuck panes cost one two-second deadline, not one each. `flk server live-handoff --skip-undrained` hands off anyway, drops those panes' pending input and prints what it dropped per pane; if the handoff then fails at a later step, the error still names the input that was dropped. A server older than this release still sends the bare error, so the CLI prints how to find and close the stuck panes on it.
