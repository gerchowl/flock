- Report outcomes a forwarding hub decides on its own to the original sender. When a hub's custody of a forwarded message ends without passing it on, the hub signs an `undeliverable` receipt. That happens when a later node refuses the message, or when the hub's deadline passes while the route is still refused (`loop_detected`, `hop_budget_exhausted`), missing (`no_route`), or never taken (`custody_expired`). The sender's `msg.status` then reports `undeliverable`, with the reason and the hub in `detail`. A hub refusal also ends `msg.wait_reply` as `undeliverable`. For an expiry, the origin's own deadline usually passes first, so `msg.wait_reply` returns `expired` and the reason shows up afterwards in `msg.status`. `expired` is therefore no longer final for such a message, and a later recipient receipt still replaces `undeliverable`. Hubs on the path are trusted: a hub can never assert a recipient's `delivered`, `read` or `refused`, but it can report `undeliverable` for a message it forwarded. No protocol bump: a v1.0.0 origin refuses the new receipt once, and the hub drops it. (#876)
