- Report outcomes a forwarding hub decides on its own to the original sender. When a hub's custody of a forwarded message ends without passing it on, because a later node refused it or because its deadline passed while the route was still refused (`loop_detected`, `hop_budget_exhausted`) or missing (`no_route`), the hub signs an `undeliverable` receipt. The sender's `msg.status` and `msg.wait_reply` then report `undeliverable`, with the reason and the hub in `detail`, instead of a bare `expired`. A hub can never assert a recipient's `delivered`, `read` or `refused`, and a recipient outcome always replaces `undeliverable`. The mesh protocol is now version 6, so a version 5 peer is refused at `mesh.hello` with `upgrade flk on <peer>`. (#876)
