# Changelog

## Unreleased

## [0.7.0] - 2026-10-06

### Added
- **An agent can now compact its own context and carry on, unattended** (#540). The user story is two manual steps an operator was doing by hand: compact the pane, then find the continuation prompt **the agent had already written for itself** in the transcript and paste it back in. Both steps were transcription, so getting the agent to finish the next stretch of work unattended meant babysitting the copy-paste. `flock_self_compact` (socket `pane.arm_self_compact`, CLI `flk pane arm-self-compact [--pane ID] [--abort] <handoff prompt>`) takes the agent's own handoff prompt, and the interesting part is that **nothing may happen when it is called**. An MCP tool call happens mid-turn and a harness cannot compact inside a turn, so the call only *arms* and returns; the sequence then completes at a turn boundary. The shape is two writes with one signal between them, and the signal is a hook report rather than a timer: once the pane is freshly idle, settled, untouched by a human and showing an empty prompt box, flock types `/compact` and submits it, and when the harness comes back with `session_start_source: compact` — the harness saying in its own words that the compaction happened, already normalized in `agent_resume` — flock types the handoff prompt in and submits it as the next turn. `Armed` therefore means *stored*, never *done*, and the tool's own answer says so, because an agent told "armed" must not go on to assume its context is already shorter. Four properties are the design rather than decoration. **Flock never types over an operator**: the idle wake's quiet window, settle, freshness and empty-prompt-box gates are re-checked immediately before each keystroke, and again before the Enter — submitting a prompt a human is editing cannot be undone, so a withheld Enter leaves the sentence in the box where whoever is there can keep or delete it. **A second arming is refused, not merged**: two written handoffs exist and silently keeping one discards work the agent believed it had saved, so the answer is `state: "pending"` and the stored prompt is untouched; `--abort` drops one. **The wait is bounded**: `[session] self_compact_timeout_ms` (120 s) drops an arming the harness never confirms, naming in the log which half was lost (`compact_timeout` versus `continuation_timeout`) because an operator finding `/compact` sitting unsubmitted in a prompt box needs to know whether the compaction half or the resumption half died. That timeout is measured from when flock **began waiting**, not from when it armed. An agent arms mid-turn, so measuring from arming meant a turn longer than the timeout would have `/compact` typed and then, on the very next tick, find the clock already expired — dropping the arming with the command left unsubmitted. Nothing is waited on before flock submits its first write, so nothing can time out then. An arming that has typed **nothing** is still never timed out, because an agent may legitimately be mid-turn for minutes and silently discarding its handoff prompt is the one unrecoverable outcome. And the continuation's Enter **drops the arming**: left in place it logs every success as a `continuation_timeout` when its clock runs out and refuses the next arming as `pending`, so a feature meant to let an agent keep working would wedge its own pane after one compaction. **A session start that is not a compaction drops the arming**, so an operator who cancelled the slash command does not get a continuation claiming a context that was never shortened. Everything else about the two writes is the idle wake's, reused rather than reinvented: flock-authored writes that do not stamp the operator clock (or the sequence would block its own Enter), and the Enter a whole `pane run` gap after the text, because text and a carriage return in one read are a paste containing a newline and nothing is submitted (#362). It is a **sibling** of `app::idle_wake` and not a parameter of it: sharing would mean either the message path growing a "what to type" argument — ADR-0008's injection hole, one argument wide — or the compaction inheriting mute semantics that have nothing to say to it. **Both writes go through the same gates**, rather than the continuation being typed straight from the hook report. Claude Code auto-compacts MID-TURN, so a confirmation can arrive with the agent working and a human part-way into a prompt; an occupied box is never typed into, because submitting it would submit the human's draft too. **The continuation is checked before anything is typed, and refused rather than scrubbed.** It reaches a real PTY, and the text encoder wraps it between the bracketed-paste markers WITHOUT escaping — so a prompt containing the closing marker would end the paste early and be read as keystrokes, and with bracketed paste off it is raw bytes, so a control byte is a control byte. A leading `/` is a slash command and `!` is Claude Code's bash mode, either of which the harness runs rather than reads. A prompt carrying a control or escape byte, an embedded line break, or a leading `/`/`!` is refused **with a reason**: a scrub would tell the agent it had saved a plan it had silently lost part of, which is worse than being told no. That check is what makes the next sentence true rather than aspirational, so it is enforced on both surfaces — refused at the MCP tool without a round trip, and again server-side. `[session] self_compact_min_interval_secs` (300) bounds the opposite failure: compact → resume → compact with nobody present is an agent's own choice until a harness whose Stop hook keeps pushing leaves it no natural gap, so the bound is on how FAST a session may compact, not how often.

The one verb that lets an agent affect its own pane is deliberately an **allowlist entry, not an unlock**: `pane.send_*` stays off the closed MCP table because an agent driving its own pane with arbitrary bytes is a real hazard, and an agent shortening its own context is the opposite of one. `[session] self_compact` (default on) forbids it outright for a machine where an agent restarting its own session is not acceptable, and `[session] self_compact_fresh_ms` is deliberately separate from `self_compact_settle_ms` for the same reason `[msg] idle_wake_fresh_ms` is: the loop wakes a compaction at `state_changed_at + settle`, and the screen was observed when the turn ended, so tying the two puts the wake exactly on the freshness boundary and one millisecond of jitter reads as `stale_screen` — a compaction that silently never fires. Claude Code only — `/compact` is a harness affordance, and another agent is **refused by name at the verb** rather than armed into a no-op it would wait on forever. The other four properties of the answer are the same refusals as everywhere else: an empty continuation is refused before the cap (a compaction with no prompt behind it shortens the context and then hands back no thread to hold, which is strictly worse than not compacting), the prompt is capped at 16 KiB like `agent.spawn`'s because text crossing into a session is capped rather than trusted to be short, and `abort` is the one call that legitimately needs no prompt. `flock_agent_history` gains `after_compaction` on a turn, so the read side matches the write side: `TranscriptEvent::Compacted` was parsed and then **dropped by every consumer**, so no agent could see where its own context had been cut, and ADR-0012's "compaction is an epoch, not a turn" describes a boundary nothing yet exposed. The flag rides the turn *after* the boundary rather than emitting a divider, because a boundary is not something an agent read — it is a fact about the turn that follows, and a page cut mid-epoch says so on its first entry instead. The `flock` skill gains the same behavior in CLI form, which is not a courtesy: that skill is entirely CLI and hands the agent no MCP tools at all, so without the CLI verb the feature would be unreachable for exactly the audience the skill is written for. Compaction boundaries remain read-only — flock never collapses superseded turns out of a transcript, which is ADR-0012 §6's rendering question, not this verb's.
- **`just release-plan`: what landed since the last release, and the version that calls for** (#509, ADR-0025 §4). `just release-prepare 0.x.y` took a number a human had already chosen and checked two things about it — that it looked like a version, and that no tag already carried it. Nothing checked that it was *greater* than the last release, and nothing derived anything from what actually landed, so the number was picked by feel and a typo shipped as a downgrade. The input for a recommendation already existed: `scripts/conventional_commits.py` classifies commit subjects and CI already rejects a non-conventional one. `just release-plan` reads the commits since the last `v*` tag, groups them by conventional type, and reports the bump they call for — major for a `!` or a `BREAKING CHANGE` footer, minor for a `feat`, patch for anything else that ships in the binary — with the `feat`-and-fix and fix-and-break cases both resolving to the stronger signal. It is a **recommendation, not an automation**: `release-prepare` refuses a version that is not greater than the last release, or that is below the recommended bump, and both refusals are overridable (`--allow-not-greater`, `--allow-below-recommended`), because holding a release back is a normal thing to want and a check that cannot be argued with gets bypassed and then stops checking anything. The two overrides are separate because they answer different questions: holding a release back is routine, shipping a number that is not greater than the last release can only be a first release or a mistake. **This repository has no `v*` tag at all**, so the interesting case is the one that has never run: "since the last tag" is defined as the whole history, the plan reports a first release with no line to bump from, and the number is reported as the operator's to choose — which is the honest answer, and is why the version line is ADR-0025's to decide rather than this command's.
- **The operator's notification log can now be read in the TUI** (#516, ADR-0016 §6). ADR-0016 promised "a place to read them in the TUI" and #381's PR body deferred it as "a UI review of its own" without filing an issue, so the durable record of every outcome flock filed was reachable only as `flk notification list` — a shell command, on a mouse-first TUI where everything else is one click. The panel is the settings overlay's modal language rather than a new screen (same centred 76×22 popup, same stack, same `↵ primary` / `esc close` button row), opens with `prefix+i` (`keys.notifications`), from the sidebar's `menu` row, or from the launcher's `notifications` item, and the `menu` row wears a dot while the log holds something only it knows about. Acknowledging goes through the same `AppState::acknowledge_notification` seam the socket API uses, so there is no second counter, and the panel's unread filter is the same predicate `flk notification list --unread` reads — three surfaces, one `NotificationLog::filtered`, so they cannot disagree about what is unread. **Acknowledgement is treated as irreversible here, because it is:** `seen` is the only bit retention acts on, `trim()` gives up read records before unread ones, and the log keeps no "was unread" history. So `enter` acts on the selected record only, the bulk action is **armed before it fires** (`a` then `enter`, the shape flock's other bulk destructive action uses), every letter binding requires an unmodified key so `ctrl+a` cannot become the bulk ack, and the pointer does not move the cursor at all — hovering only ever precedes a deliberate click elsewhere. The panel inherits the eviction rule and says so rather than implying completeness: a standing line names the 512-record cap and dates the oldest surviving record, and once the projection is full it says older records may already have been evicted, because an eviction emits nothing into the log and a decision that was never answered and has aged out is otherwise indistinguishable from one that was never filed. **No retention changed here** — ADR-0016 §3's premise is an open question and the panel reports it instead of answering it (#372).

- **`flk report bug --body-only`: a composed bug report that survives a pipe** (#427, ADR-0010). `flk report` could compose, redact and preview a complete report and then stop one step short — the only route that sends it, `--open`, hands a prefilled browser form to a human, so in a terminal-only or agent-driven session the report was finished and stuck. The report is still submitted by a human; what was missing was a way to *get it out*. `--body-only` writes just the issue body to stdout — no `destination:`/`kind:` header, no 7 500-character prefilled URL, no `nothing has been sent` footer — so `gh issue create --body-file -` takes it directly, and the `awk` script between `--print` and a filing command goes away. The preview, its advisories and the exact ready-to-run `gh` line go to **stderr**: ADR-0010 decision 5 requires the composed block to be previewed before anything can be sent, and on this route that only holds if the preview moves off stdout with the body, since a pipe can carry one of them. The body has no URL length cap, so the redacted log tail rides inline instead of going to the clipboard — a headless report now carries strictly more evidence than a browser one rather than less, which is the inversion #427 complained about. Diagnostics are already allowlisted and scrubbed, so this does not widen what can leave the machine, and the preview saying so on stderr is what keeps that true. There is deliberately **no `--submit`**, and the issue asked for one: ADR-0010 decision 6 refuses it ("The binary never submits … Shipping a write-capable token in a public binary is refused outright", with `gh issue create` "deferred" rather than permitted), and ADR-0015's amendment does not reach here — its §3 refuses to post through a repo that defines a template, which flock's own `.github/ISSUE_TEMPLATE/bug.yml` is, and its §5 keeps the mutation off the MCP surface and leaves "whether an agent should ever file" as the operator's call. `flk issue drop --file-it` remains the only write path. `--open` is unchanged, and the two flags are refused together rather than letting one silently win.
- **Experimental: agent mail pushed into a Claude session as a channel event** (#438, ADR-0019 Proposed). This is a spike, and it is off by default. With `[msg] channel_push = true`, `flk mcp serve` declares the `claude/channel` capability. It subscribes to its own pane's inbox through a new `msg.queued` event subscription, which is event-driven: the server's stream sleeps on the event hub, and nothing polls or spawns per message. Each message the wake path would knock for is pushed as `notifications/claude/channel`. The body rides along only for a locally attested sender under `channel_push_body_max_bytes`. Every other message is a count-only doorbell. A push is never an ack: the message stays unread until `flock_msg_read`, or until the agent replies to it with `flock_msg_reply`, which, with the flag on, now settles a still-queued original in the replier's own inbox. The stop-hook nudge and the idle wake keep running as the fallback. Under the flag, the idle wake waits `channel_push_idle_wake_grace_ms` for the push to start a turn, so the two no longer race. `msg.wake` now names the pane it counted and carries the server's live `channel_push`. A pushing session checks it before every push, so switching the flag off with a reload stops pushes at once. A reply settles the pushed original only once the reply has actually gone out: at once when it was queued locally or relayed to a peer, and only on the hub's delivered answer when it was handed up. A failed or refused reply leaves the original unread. A pushing `flk mcp serve` logs to its own `flock-mcp-<pid>.log`.
- A mute's deferral handed up to the hub is now **recorded only once the hub confirms it**, and retried when it does not (#408, #410). A deferral to a sender on another spoke was marked answered — and written to the log as sent — the moment it was queued for the hub's relay, so a hub that refused it or never answered left the question marked answered while its sender heard nothing, and no later mute would try again. The claim is still taken at hand-up, so a mute renewed meanwhile sends nothing twice, but a refusal or an uplink timeout now releases it and the next mute hands it up again; the durable `message_deferred` record is written when the hub delivers.
- A message **handed up to the hub now carries only a sender the spoke can attest** (#410, #408). A send with no local process ancestry fell back to whatever `from_agent` the caller supplied, and the hub relays a handed-up frame as the sender it names — so any process on a spoke outside a pane could speak as any agent id it could spell. That fallback is gone: an unattested caller's send that would need the hub is refused with `sender_unresolved`. Messages relayed in from another host never hand up again, so the relay's own `--from-agent` leg is unaffected.
- **A spoke now sees the rest of the fleet.** Gossip only ever flowed UP: a server learned what the peers it polls relayed to it. A spoke polls nobody, so its servers band showed nothing past itself — atlas had no status for bastion or node-b — and its directory had no rows for their agents. The hub now sends its view of the fleet (the peers it polls, minus the spoke itself) DOWN the `flk peers relay` connection it already holds into each spoke, one line per poll and never a new ssh. The spoke merges it through the same path a poller uses: every row validated by `relayed_entry_from_wire` (#392 — an ssh target or ProxyJump this host will not dial is dropped), freshest-wins, rows about itself dropped, and routed via the hub — the same route a message for one of those agents then takes up (#410). The band marks such rows `via <hub>`, they go stale on their own clock when the hub goes quiet and are evicted after, and the spoke never relays the hub's view back up as its own. Those rows are display-only — a spoke holds no key to dial anything, so clicking one never dials its ssh target. Nothing but the hub's relay can write them, either: the relay now binds this server's uplink to its own process (`peers.relay_attach`), and `peers.hub_fleet`, `msg.uplink_take` and `msg.uplink_result` are refused from every other process, so a stray local process can no longer take a spoke's pending messages, kiln the hub's answer to them, or plant fleet rows. Uplink ids are unguessable besides. A mute's automatic deferral (ADR-0018 §3) to a sender this spoke cannot reach itself now takes the same way up through the hub, so a muted agent on one spoke still answers a question from another.
- **A mute now answers.** `flock_msg_mute` / `msg.mute` stopped the nudge and told the sender nothing, so from the other side a muted agent and a dead one looked the same (#408, ADR-0018 §3). Now every `needs_reply` message that is waiting when the mute is set, or arrives while it holds, gets exactly one automatic reply: threaded `in_reply_to` the question, intent `fyi` by construction so two agents muted at each other cannot ping-pong, and a body that says it was deferred, why (the new optional `reason`, also `flk msg mute --reason TEXT`; sanitised like a message body and bounded by `[msg] mute_reason_max_chars`), and the UTC time the mute lifts — a deadline the sender can act on. It rides the ordinary reply path, so a sender on another host hears it too; that hop runs off the event loop, because the sender's server is at that moment still inside its own relay to us. Renewing or extending the mute, or restarting the server, never repeats a deferral — each one is a durable `message_deferred` event the mailbox reseeds from — `fyi` messages get none, and clearing a mute sends nothing. `msg.mute` now also reports `deferred`, how many waiting senders it just answered (sent, not delivered: a cross-host hop that fails is retried by the next mute). Cross-host deferrals go out at most `[msg] deferral_relay_concurrency` (default 4) at a time.
- An agent message's **intent now decides how hard flock knocks**, and there is a third tier for "I am blocked on you" (ADR-0018 §1, §4, §5). #280 gave messages an `fyi` / `needs_reply` stamp, but nothing in the wake path read it: an `fyi` cost its recipient a turn exactly as a question did, and a sender that genuinely could not proceed had no way to say so louder than one that merely had a question. The wake now reads the stamp. An inbox holding only `fyi` messages produces **no** stop-hook nudge — `msg.wake` reports zero with `suppressed: "fyi_only"` — and once any waking message is queued the nudge names *every* queued message, notices included, so the read it prompts clears them rather than leaving them for a turn that may never come. **An answer wakes whoever asked**: a reply defaults to `fyi` (answering is what a reply normally does), so a message whose `in_reply_to` names a `needs_reply` or `blocking` message wakes its recipient whatever its own stamp — including an answer coming back from another host, which the relaying server now records on `message_relayed` so it survives a restart. The one exception is a mute's automatic deferral, which replies to a question by construction but carries no answer. `blocking` (`flock_msg_send` `intent: "blocking"`, `flk msg send --intent blocking`) does everything `needs_reply` does and two things more. The recipient pane joins the attention cycle — after `blocked`, before done-unseen — and its agents-panel row carries a `✉N from <sender>` label: its **own** label, never the `blocked` state, which #311 spent a PR making mean "waiting on input" and which waiting mail is not. And a `blocking` message for a recipient that has muted itself is a disagreement about urgency that neither side should win silently, so the operator gets a notification through the ADR-0016 log naming sender, recipient and count — once per message, including mail already waiting when the mute lands, and never the body. Because the sender declares it, every sender would like it, so `blocking` carries its own per-sender budget, `[msg] blocking_per_hour` (default 6), on top of the general 20 a minute. Past it the message is **downgraded, not refused**: it is delivered as `needs_reply` — still read, still waking its recipient — and the send result's `warnings` say so (`blocking_budget_spent_sent_as_needs_reply`, or `blocking_disabled_sent_as_needs_reply` with `blocking_per_hour = 0`). The budget is keyed only on an agent the receiving server attested itself; every unattested sender — which includes every relayed message — shares one bucket, because on that path both the sender id and its host are claims, and keying on a claim let a caller mint fresh budget per invented name or spend a real agent's by naming it. Sharing is safe because spending the budget only ever downgrades, so nobody can be silenced by someone else exhausting it. A claimed `from_agent` or `from_host` that is not shaped like an id or a host name is refused at ingress with `invalid_request`, because both reach operator surfaces; a label with nothing validated to show says `unknown@<host>` or `unknown sender`. Version skew fails toward being heard in both directions: a relayed tier the receiving build does not know is read as `needs_reply` and logged on the receiving server (an operator typing an unknown `--intent` by hand still gets the refusal — a typo is not skew), and a `blocking` relay refused by a peer that predates the tier is re-sent as `needs_reply` rather than failing. The MCP tool's `intent` enum is generated from the tiers themselves, with a test that every tier is expressible on both message tools, so the schema cannot fall behind the server the way the `agent` target did in #320. (#408)
- **A spoke can message another spoke — through the hub, the way the fleet is built.** The fleet is hub-and-spoke on purpose: only the hub carries `[[peers]]`, and a spoke holds no key to any other machine. Flock's message routing did not honour that. On a spoke, an agent learned through the hub resolved with no route, and `msg.send` refused with `peer_not_configured` — advising the operator to add the very `[[peers]]` entry, the N×N trust, that the topology exists to refuse. So an agent on atlas could not message one on node-b even though atlas knew it existed and the hub could reach both. Now a message a server cannot deliver itself goes UP the `flk peers relay --push` connection the hub already holds into it — one more push kind on a channel that already carried summaries up, so no new transport and no new trust — and the hub delivers it with its ordinary `msg.send`. The sender's `msg.send` waits for the hub's real answer rather than reporting a hopeful "queued": the result says `"path": "via hopper"` and where it went, `msg.status` says the same later, and replies (and anything else that answers a message) come back the same way. The originating agent stays the sender — the hub vouches only for which spoke handed the message up, and refuses a spoke claiming to speak for another host. A message crosses at most one hub, so it cannot loop, and a re-offered frame cannot double-deliver because the recipient's mailbox dedupes on `correlation_id`. A relayed directory row on a server that DOES have peers now routes via the peer that relayed it instead of `None`, so that case is fixed too. Failures name the hop and the reason: `hopper cannot reach node-b (connection refused): …`, with `data.hop` and `data.reason`, or "no hub holds a relay to this server" on a spoke nobody is attached to — never the generic "not in [[peers]]". `[msg] uplink_timeout_secs` (45) and `[msg] uplink_heartbeat_secs` (20) are the two new knobs. A peer dial that fails now also says HOW in the servers band and in `flk peers summary`'s error text — connect refused, auth refused, host key, timeout, unknown host, or "jump host reached, next hop refused" for the `ProxyJump` case that showed only as an unreachable peer in #406 (#410).
- **An idle agent now receives its mail without a human prompting it** (ADR-0018 §2, #408). The stop-hook wake fires only at a turn boundary, so an agent that had already stopped never learned it had mail. On atlas a message sat 131 minutes next to an idle recipient with zero delivery attempts. Now, when a message whose intent is not `fyi` is queued for an idle Claude pane, flock types one constant sentence into it and presses Enter: "You have N unread message(s) from other agents. Read them with the `flock_msg_read` tool." The count is the only variable. No sender, subject or body is ever typed, so the body is still pulled through the tool and ADR-0008's boundary is unchanged. Every gate is checked again at the moment of typing, and the operator-input and pause/mute checks again before the Enter:
  - the agent has been idle for a settle window, and the screen positively shows the idle prompt, read recently — an unreadable screen or a hook that has gone quiet (#309) is not idle;
  - no operator input reached the pane within a quiet window. This needed a new per-pane input clock, stamped where every forwarded write passes, so client keystrokes, pastes and `agent.send` / `pane.send-text` count, and flock's own wake does not;
  - the fleet is not paused and the recipient is not muted, through the same single decision `msg.wake` uses;
  - the agent is Claude; other agents stay pull-only;
  - the input box on screen is empty. A draft someone typed and left an hour ago is outside any quiet window, but it is still in the box, and the Enter would submit it along with the sentence.
  Flock types at most once per batch of mail. The in-flight marker clears when the agent reads its inbox or leaves idle, and only a message it has not yet been told about can earn another wake. The Enter is a separate write, one `pane run` gap after the sentence (#362). If the operator types in that gap, the Enter is withheld, because submitting a prompt a human is editing cannot be undone. Configure it with `[msg] idle_wake` (the kill switch, default on), `idle_wake_settle_ms`, `idle_wake_operator_quiet_ms` and `idle_wake_fresh_ms`. Messages relayed from another host are woken on the recipient's own server, which is where its state is known.
- The worktree list can now answer **"which of these is stale, and which is safe to delete"** — and act on the answer. `worktree.list` said what existed and nothing about what was old or what was done, so deciding what to prune meant leaving flock and reconstructing it by hand: `git worktree list --porcelain` for the checkouts, `gh pr list` per branch, `git status` per checkout, then `git worktree remove` on the survivors. Doing it that way is not merely tedious, its natural form is WRONG — removing checkouts with raw `git worktree remove` goes behind flock's back and leaves workspaces pointing at directories that no longer exist (#360). Every row now carries `last_commit_at`, the last commit on its branch, and the list is ordered stale-first: the repo's own checkout, then linked checkouts oldest work first. The last commit is deliberately not the directory's mtime, which is the obvious field and the wrong one — a `cargo` build rewriting `target/` makes a checkout abandoned for three weeks look fresher than one edited this morning, which one of the audited worktrees was doing with a `target-nixrust/`. `flk worktree list` prints that as a table now rather than raw JSON, with `--json` for the old output, matching `flk status`, `flk peers` and the rest of the CLI. The TUI's worktree picker shows the same age in the same order, through the same comparator, so the question cannot have two answers depending on where it was asked. **The verdict is the existing gate, not a second one.** `--scan` (`"scan": true` on the socket) resolves each row's `kill_verdict` through the SAME `resolve_kill_verdict` that `flk worktree kill`, the kill dialog and the fleet sweep all run. That matters most in the common case: a squash-merged branch is not an ancestor of the default branch, so the obvious independent check reports landed work as unmerged — which is exactly what happened, three checkouts sitting for five weeks looking like unpushed work at risk while `kill --dry-run` said `merged: true` the whole time (#287). Scanning is opt-in because it costs local git plus a `gh pr view` per checkout, and spawning `gh` is not free: ~158x curl's exec cost under macOS Gatekeeper. Absence of a verdict means "not scanned", never "not merged", and a row the gate could not answer inside its bound reports `timed_out` rather than a verdict nothing produced. And the rows the verdict marks safe are now actionable: `flk worktree kill` takes `--path` as well as `--workspace`, because the prune candidates are precisely the checkouts nobody has open — until now reachable by no flock verb at all, which is why they got removed by hand. A path that IS open routes through its workspace, so the workspace is closed with the checkout. (#396)
- The per-agent **spawn environment is now declared in config** rather than compiled into flock. An argv-exec'd child runs no shell init, so whatever a login shell would have exported never reaches it — and for an agent CLI whose profile selector is shell-session state, that is not a missing convenience but the wrong **account**: the child falls back to the CLI's own default home, comes up looking perfectly healthy, bills someone else, and writes its history into a config dir nobody is watching (#359, #366). flock has carried that selector down from the requester since #383, but *which* key to carry was a `match` in its binary naming one vendor's variable — so a fleet whose Codex or Kimi installs need a key of their own had to wait for a flock release to say so, and a fleet that needs none still carried it. `[spawn.env]` is that table in config (`claude = ["CLAUDE_CONFIG_DIR"]`, keyed by the agent name flock detects), and it is read by **both** halves of the child's environment — the carry from the requester and the allowlist through `env_clear()` — so a key can no longer be resolved by one and cleared by the other, which two separate tables naming the same constant could always drift into. A declaration **replaces** the compiled default for that agent rather than adding to it, because a table that can only grow is a one-way ratchet: a fleet that pins one account per host writes an empty list and carries nothing, and removal has to be expressible or the default becomes permanent. The default still declares `CLAUDE_CONFIG_DIR` for `claude`, so an existing fleet needs no config change at all. What does *not* move is as deliberate as what does: the `env_clear()` inversion stays flock's because the scrub is the security property and only the table was ever policy, and a declared key that is absent from a requester flock cannot read still refuses with `agent_profile_unresolved` rather than starting the child on the default profile — a flock that stopped validating and merely inherited would be #359 reopened, and #359's whole finding was that the failure is invisible. Credential-shaped keys (`ANTHROPIC_API_KEY` and its siblings) stay compiled in for the same reason they are not policy: a declared key carries a refusal, and a missing API key means this deployment does not use one, not that the spawn should stop. An agent name flock does not detect is a startup diagnostic rather than a parse error, so one config shared across a fleet never costs a node running an older flock the rest of its table. (#397, ADR-0002, ADR-0014)
- `flk agent start` can now **wait until the agent is actually up**, and say what it saw if it never is. A start has always answered as soon as the child exec'd and outlived a short liveness window (#178) — an honest statement about the *process*, and a silent one about the TUI. A Claude pane then spends 30-60 seconds painting nothing flock's detector recognises, and for all of it `pane read` returns an empty string, so "still booting", "crashed on launch" and "blocked on a first-run permission dialog" are the same observation. That is how starting one agent on a remote host took five attempts with four silent failures: every retry was made blind. `flk agent start <name> --wait-ready [--ready-timeout MS]` and `flk agent wait <target> --ready [--timeout MS]` block until the pane reports an agent status other than `unknown`, then print the agent exactly as `agent get` would. The definition is doing the work and is deliberately not "the pane is non-empty" — a pane can be non-empty and still be mid-splash. `unknown` is the only status flock reports when its detector has not recognised the agent's own chrome, so the first non-`unknown` status is exactly the moment the question becomes answerable, and the status it lands on **is** the answer: `blocked` returns immediately rather than waiting a dialog out, which `--status idle` could not do because it cannot distinguish "not there yet" from "not coming". Two properties matter as much as the flag. A wait that fails says what it saw — the status flock last had and the last line the pane printed — because a timeout reporting only "timed out" puts the caller straight back in the window the flag exists for. And an agent that dies at second one, too late for the start-time liveness window to catch, ends the wait right there with `agent_exited_before_ready` instead of running out the caller's clock. The wait is client-side, composed over events the server already publishes: the alternative blocks the app loop for tens of seconds, which would stop the render loop and the detector producing the very signal being waited on. A pane running something flock does not detect never becomes ready, and that is reported at the timeout rather than papered over. (#362)
- A file handed to flock is now an **MCP resource**, not just a paste. Dropping a file on a pane staged it server-side and typed the path into the agent's input surface — and that path was the whole record: it lived in one client connection's list, was **deleted when that connection went away**, and nothing anywhere could enumerate it. An agent could read the file once, in the turn the paste arrived, and only because the bytes had gone through its terminal. `flk mcp serve` now advertises a `resources` capability: `resources/list` names every handed-over file (`flock://handoff/<file_id>`, with its media type and size) and `resources/read` returns the content — text in `text`, images and PDFs base64 in `blob`. The socket API carries the same pair as `handoff.list` / `handoff.read`. Neither takes a path: the only addressable bytes are the ones a human handed over, named by an id flock minted, which is what keeps a resource surface from quietly becoming a file-read surface. The record is durable the way #372's outcomes are — a new `file_handed_over` kind on the **existing** event log, folded into a read model rebuilt at boot, with the bytes deliberately left on disk rather than base64'd into a JSONL audit log that would then be held hostage by its own rotation. So the seed is a reconciliation: a record whose staged file is gone is dropped rather than advertised as a resource that cannot be read. Staged files are no longer deleted when a client disconnects or the server stops; retention is 128 records (oldest first, and eviction deletes the file with the record) plus the staging directory's 24-hour age sweep, which now also runs at boot instead of only when another file happens to be staged. The listing is **not** filtered by which agent is asking — a filtered list that comes back empty cannot be told apart from a server that was handed nothing, and that is the one answer that must never be a guess — so each row says who it was handed to, `total` always reports the whole projection, and `target` narrows on request. The paste still happens too: flock cannot tell from outside a pane whether the agent in it has this MCP server wired up, so suppressing it would silently lose the file for every agent that does not. (#286, P2 of #79, ADR-0017)
- Agents can now read **another agent's conversation** rather than its terminal. `flock_agent_history` (socket method `agent.history`) serves the session transcript itself — unwrapped, one entry per turn — where the only agent-reachable history until now was `flock_agent_read`, i.e. scraped pane output hard-wrapped at whatever width it happened to be drawn at. An agent pointed at the flock MCP could already discover *who* is running and in which checkout; it could not discover what any of them had actually done. Two properties are the design rather than decoration. It touches **no pane state**: nothing marks the pane seen and nothing reorders the operator's attention, which is precisely what makes it safe to poll — `flock_agent_read` documents the opposite and is unsafe on a loop for that reason. And it renders at the `detail` the *caller* asked for (`reply`, `collapsed`, `full`), never at whatever level the operator's prompt-history panel happens to be showing, so a human clicking Tab cannot change what an agent sees. Cost is bounded by a byte window and not by the transcript: a call parses at most 1 MiB, and a caller that hands back the `next_cursor` it was given parses only what has been appended since — normally a few kilobytes, against files that reach ~15 MB and are read on the same task that draws the UI. `truncated` says older turns were skipped and `more` says to page again now; the `session_id` in every response is what tells a poller its cursor has outlived the transcript it named. Claude only, since that is the transcript format flock parses; other agents refuse with `unsupported_for_agent` rather than being reported as sessionless. (#276)
- Flock now **keeps** the outcomes it tells you about. A toast was a field on `AppState` that a timer cleared: an agent that blocked or finished at 03:00 announced itself to an empty room and left nothing behind, and the pane holding the answer may already be closed. Worse, the one content-bearing verb flock had was already dropping text on the floor — `notification.show` refuses with `busy` when a toast is on screen, `rate_limited` under load, `no_foreground_client` when nobody is attached, and `disabled` when `[ui.toast] delivery = "off"`, **which is the default** — and in all four cases the caller's title and body were simply discarded. Every outcome is now filed as a durable `notification_filed` event on the existing log (ADR-0005's substrate, whose design round explicitly ruled out a second event system), with `notification_seen` as its acknowledgement; the unread list is the fold of one over the other and is rebuilt at startup, exactly as the agent mailboxes already are. Read it in the TUI with `prefix+i` (or the sidebar `menu` row → `notifications`) and acknowledge there, or from a terminal with `flk notification list [--unread]` and `flk notification read <id> | --all`, or over the socket API as `notification.list` / `notification.ack` — all four read and write the same records (#516). Filing deliberately does not depend on `[ui.toast] delivery`: `off` is a request for no popups, not for amnesia. Listing is not acknowledging, because acknowledging is what lets retention drop a record — the log keeps 512 and gives up **read** records before unread ones, which inverts the usual failure where the thing you were about to read is the thing that ages out. The #367 title badge gains a `U` term for outcomes that outlived the pane they happened in — only those, so an agent that is still blocked stays one `B` rather than becoming a `B` and a `U`. Nothing new may write: flock files from what it already decides, and no agent-facing filing verb is exposed. (#372, ADR-0016)
- An agent message now says on its **envelope** whether the sender is owed an answer. `flock_msg_send` gained a required `intent` of `fyi` or `needs_reply` (`flk msg send --intent needs-reply`, and the same optional flag on `flk msg reply`), carried through to `flock_msg_read`, `msg.list`, the durable event log and the cross-host relay. A recipient could previously see who sent a message and whether a reply could be routed, but not whether one was *wanted*, so it either replied to every notice — burning the sender's turn and inviting a loop — or read a question as a notice and silently stranded whoever asked. The one real agent-to-agent redirect sent so far had to encode "please answer" in English in the last line of a ~2 500-character body, which is precisely where an envelope reader cannot see it. The field is deliberately binary: it says what the sender *wants*, not how hard Flock should knock, and nothing in the wake path reads it — a nudge still names a count and a tool and never a word a sender chose. It is required on the MCP tool and defaulted to `fyi` everywhere else, which is not a contradiction but where each cost belongs: the wire default keeps every existing caller working and reads an unstamped envelope the conservative way, while an agent that never *has* to look at the field will not, and a question confidently stamped `fyi` is worse than no stamp at all. On a reply the default is `fyi` and stays optional, since answering is what a reply normally does — but a reply that asks something back can say so, so a two-turn exchange does not strand its intent in prose again. (#280, R4 of #213)
- Agents can now say **"not now"** to their own mail nudge. `flock_msg_mute` (and `flk msg mute <seconds> [--pane TARGET]`) stops the turn-boundary nudge for a bounded window without stopping anything else: messages keep arriving, `flock_msg_read` keeps returning them, and the first nudge after the window names everything that queued meanwhile — so a mute costs latency and never a message. It is capped at 30 minutes and cleared by a server restart, because a mute that survives a restart is a mute nobody remembers setting, and forgetting one fails toward being woken rather than toward silence. A recipient mid-refactor previously had no way to defer, and ignoring the nudge was indistinguishable from not having heard it. (#316)
- Added **`flk issue drop`** and a dialog to go with it, so an idea about a repo you are *not* in becomes an issue without leaving flock and without disturbing the agent in the focused pane. That last part is the requirement, not a nicety: the workaround until now was to go find whichever agent happened to be in the right repo and interrupt *it*, which moves the cost rather than removing it. Pick any repository your GitHub token can reach — enumerated once over GraphQL and cached, ranked so the ones you have checked out sort above the ones you merely have access to, and a repo you have never cloned is reachable by typing `owner/name`. Labels and issue types are fetched per repo on selection. The body is composed in **your own editor in a new pane**, not in an overlay: flock's only text primitive is single-line, overlay paste is discarded today, and overlay text cannot be selected or copied (#327) — a pane is a real PTY that already has all three. Filing goes through the `createIssue` mutation rather than a prefilled browser URL, because the URL route caps at 7 500 characters (this feature's own issue is 9 791 URL-encoded, so it would have been silently truncated) and has no parameter for an issue type at all. Nothing is filed without an explicit `--file-it` and an interactive confirmation, no write credential is compiled into the binary (your own `gh` token is used), and the mutation is deliberately kept off the MCP surface. A repo that defines an issue template is *not* posted through: flock carries no YAML parser, so it says so and points you at the browser form rather than bypassing the structure the repo asked for. Drafts survive dismissal and restart. The keybind (`keys.drop_issue`) is unset by default. (#371, ADR-0015)
- Flock now **labels the host terminal's window**, so a row of terminals is no longer a row of identical cwd strings. The title reads `● 2B  feat/foo · hopper — flk`: what wants your attention first, the focused workspace next, which server after that, and a short identity marker last. Everything in it was already computed for the sidebar and simply never published outward — Flock emitted no OSC title sequence of any kind. The badge counts only the states that want you (`B` blocked, `D` finished-but-unseen) and disappears entirely when none apply, because a count that is always present stops being a signal: a calm fleet reads `main · hopper — flk`, an empty one reads `flk`. The ordering is not decoration — titles are read in their first couple of words and truncated by pixel width from the right, so a leading app name spends the only reliably-read region on the one thing that never changes. Publishes are rate-limited and skipped when the text is unchanged, since a title rewritten every frame flickers and bounces taskbar entries on some window managers. Flock sets the window title only (OSC 2, never the icon name some tiling window managers match on) and hands it back on exit. Because a title carries your branch and your server name to anyone watching a shared or streamed terminal, `[title] enabled = false` turns it off completely — no bytes at all, rather than a blank title. Inside tmux it needs `set -g allow-passthrough on`; without it tmux swallows the sequence and the title is simply unchanged, as it is today. (#361)
- Added per-node **thermal health** to the fleet gossip and the servers band. A node declares its own coarse severity — nominal, fair, serious, critical — via a new top-level `thermal_command`, and every viewer tints that node's matching metric glyph amber or red. Nothing is added to the row: the band is already out of columns (a self row runs ~30–32 against ~24 at the default sidebar width, so the GPU metric was already being truncated), and the metric glyphs were rendered in a constant dim grey, an unused channel. Below `serious` nothing tints, so a healthy fleet looks exactly as it did. The point is the divergence between heat and load that no load metric can express: a red glyph beside a busy value is a machine doing its job, while a red glyph beside an idle one is cooling failure. It is deliberately an ordinal and not a temperature — 90 °C is normal on Apple silicon under load and an RTX 5090 is fine at 80 °C — so Flock holds no temperature thresholds at all and the host owns calibration. The reporter runs on a ~30s tick behind a hard 5s timeout and fails closed: a missing binary, non-zero exit, unparseable output or a timeout all declare *nothing* rather than a made-up healthy reading, and a repeatedly failing one is slowed down and logged rather than disabled. Prompted by a Mac Studio that sat at full fans for an extended period with no way to tell "stuck or busy" from the band — the same box having earlier hit a 47-minute thermal emergency and hard-powered off. (#291, #298)
- Peer rows in the servers band now show **GPU utilization**. It had been sampled locally since the status line shipped but never had a wire field, so every viewer saw a GPU number on its own row and a blank column on every other machine's — most misleading on exactly the inference boxes where the GPU is the busy component and the CPU number reads near-idle. (#291)

It checks the config (by running `config check`), each agent integration, that the worktree directory is writable, and that `git`/`ssh`/`gh` are on `PATH`; every failure names the command that fixes it. ### Changed
- **A headless `flk agent start` that names no place to put the agent is now refused instead of being placed in the workspace you happen to be looking at** (#398). **This is a breaking change for scripts, and it is gated on the caller's shape rather than switched on globally** — read the paragraphs below before upgrading one. The reported failure was four agents resumed over ssh after a reboot, each with a **distinct** `--cwd`, all landing in the one focused workspace, each then moved by hand. `--cwd` inference (#390) closes the half where the cwd names a checkout this server already has open. This closes the rest, and the fallback it removes is `let ws_idx = self.state.active.unwrap_or(0)` — "the active workspace" is whatever a human last focused, which is an answer for a person in front of the TUI and an arbitrary one for everybody else, racy against every other dispatch in flight. **Read this if you run `flk agent start` from a terminal window outside the Flock session** — you are treated as headless and refused with `agent_placement_required` unless you name a placement. The remedy is one flag, `--active`: `flk agent start x --active --split right -- claude` puts the agent beside what you are looking at exactly as before. Ancestry can see that a caller is not in a pane of this session; it cannot see that a person is at the other end, so "outside" and "nobody is watching" are the same observation and both are refused. That is the price of refusing over guessing, and it is paid by a real workflow, not a hypothetical one. Calls made from inside a pane of the session keep the active-workspace default unchanged.
  **Three ways to name a placement, and they are not the same question.** `--workspace ID` and `--tab ID` name a destination outright, and they are what you want 99 times out of 100. `--active` (or `--here` when you are asking from inside a pane) names **the workspace you are looking at** — a recollection the server reads from its own focus state, which is why it has to be asked for. **`--here` is a different flag, not an older spelling of `--active`: it names the workspace *your own pane* is in**, read from your process's ancestry, so a script run from a pane in a background space gets that space rather than the one somebody happens to be looking at — and it is refused, rather than quietly answered with the focused workspace, when the server cannot place your process in any pane. Two placements named at once is refused (`agent_placement_conflict`); a placement plus `--cwd` is not, because `--cwd` names where the *process* starts and only implies a space, so an explicit placement outranks it exactly as it always has (#365).
  **What is NOT refused — a deliberate narrowing of #398's wording, and it does not apply to `--split`.** The issue asked for a refusal whenever a `--cwd` resolves to no open checkout. On the **untargeted** path this refuses only when the cwd gives flock nothing at all: absent, or naming a path that is not a directory. Operator-confirmed as the right reading: **a real directory IS placement** — #364 established that flock mints a space for a cwd it has never seen, and no other flag expresses "start a space for a checkout this server has not got open". **`--split` still refuses an unmatched cwd even when it names a real directory**, because a split subdivides a space that already exists and there is nothing here to subdivide; `--active`, `--workspace`, `--tab` and a `--cwd` naming an *open* checkout all name such a space, so all four fix that refusal. Only the untargeted call is refused, and it is also the one that otherwise answered with the **server's** own working directory and started a Claude agent in `$HOME` under a trust prompt over every file the operator has (#365). An untargeted `--split` on a server with no spaces open is likewise allowed: there is no active workspace to be wrong about.
  **Shape, in `tab_mode = "workspace"`.** `--active`/`--here` without `--split` place the agent as the only pane of a **new tab** in the named workspace under the default tab mode, and as a **sibling space carrying that workspace's worktree membership** under `tab_mode = "workspace"`, where a tab is never drawn and would be a pane you cannot reach (#390's behaviour, inherited).
  **Who counts as headless is decided at the server, from attested evidence.** `SpawnCaller` already walks the API peer's process ancestry to tell an agent from an operator (ADR-0014 §6), and this reuses that one classification rather than adding a second — a drifting parallel classifier is this codebase's recurring defect (#124, #197, #199-#210). What it attests is **where the caller is**, not whether a human is at the keyboard, and the code says so: ancestry cannot see a keyboard. The active default is therefore kept for a caller attested to be *inside a pane of this session* — the operator's own shell, which is the gesture `--split` was written for ("put this beside what I am looking at") — and for nobody else. An agent pane is attested and still not a keystroke (ADR-0014 §7), so an agent dispatch does not get the default either. Everything unattested is refused: ssh, launchd, cron, and an operator's own terminal outside flock. The alternative signal considered and rejected was a TTY stamp from `flk`: it is a claim the server cannot verify, and the exact caller this rule exists to catch could allocate a pty and turn the guess back on. `agent.spawn` keeps its own location union and is unaffected; applying the same rule to its callers is deliberately left for later (#398 P1).
- **Bare `flk peers` now prints the peer status table and exits 0** (#418). It used to print usage and exit 2; `flk peers help` still prints usage. Remote text in the table (ssh's last error line) has terminal control sequences stripped before it is printed.
- flock's **own peer dials no longer ride an ssh ControlMaster mux** (#418): they pass `-o ControlMaster=no -o ControlPath=none`, whatever the ssh config says. With a global `ControlMaster auto`, dials worked exactly while some interactive session had left a mux alive — which is what hid hopper's dead agent socket (see Fixed) — and a stale mux hangs a dial rather than failing it. The held relay stream remains the fast path; the one-shot fallback pays an honest handshake. Interactive `--remote` sessions are unchanged.
- **`flk agent start --cwd` now names the space the agent joins**, not only where its process starts. `--cwd` decided the child's working directory and nothing else, so pointing an agent at a checkout flock already had open minted a *second* space for it — ask for three agents in `~/dotfiles` and the sidebar grew three more `dotfiles` rows beside the one already there, and you finished the job by hand with `flk pane move`. It bit hardest on headless dispatch: four agents resumed over ssh after a reboot, each with a **distinct** `--cwd`, all landed in one workspace. A requested cwd that names an open checkout now selects that checkout's space — as a new tab, or under `tab_mode = "workspace"` as a sibling space carrying the source's worktree membership, because the inner-tab strip is never drawn in that mode and a tab there would be a pane you cannot see or reach. `--split` follows the same rule: with a resolvable `--cwd` it splits *that* workspace, since a caller who named a checkout has said where the work lives and "beside what I am looking at" is not an answer to it — for a headless caller the focused workspace is not merely wrong but meaningless, being whatever a human last focused. The agent is still the only pane of a tab nobody else is in (#364); only *which* space changes, and only on a match. Three things it deliberately will not match, each a way the default would otherwise move under you: a cwd flock derived rather than one you asked for (the fallback is the *server's* working directory, i.e. `$HOME` for a daemon), a checkout that is no longer on disk (membership outlives it and still string-matches), and a workspace whose root pane merely happens to sit at the path right now. `--workspace` and `--tab` still override and still derive cwd from their target (#365); `--split` with no cwd still splits the focused workspace; an unmatched cwd, or no cwd, behaves exactly as before. (#390)
- **`pane run` no longer submits "atomically"**, because atomicity was the bug. It sent the command text and the Enter to the pane in one write, and a program reading a raw-mode stdin sees read boundaries rather than keystrokes — which is exactly how every agent TUI tells typing from pasting. Text and a carriage return arriving in ONE read look like a pasted block that happens to contain a newline, so the newline was inserted into the prompt and nothing was submitted: the reported failure is a task that landed in Claude's input box and sat there with the agent still `idle`, where a later `pane send-keys <pane> Enter` submitted the identical bytes. `pane run` now types the command, pauses, and presses Enter as its own write, so the two cannot land in one read. The pause is a heuristic and the docs now say so rather than promising a guarantee: a TUI that has not started reading stdin at all misses the text as well as the Enter, and that half is what `agent start --wait-ready` is for. Shells are unaffected in behaviour and pay the pause. (#362)
- An **agent-spawned child no longer takes its opening turn at face value**. `agent.spawn` (off by default, behind `[fleet] agent_spawn_enabled`) passed the caller's prompt straight to the child as its entire first turn — and a foreman's prompts are derived from GitHub issue bodies, which is exactly the author-trust surface `issue_guard` was rebuilt around after a body-authored trigger let any GitHub account drive flock into acting on a public repo. An issue body reading "ignore your task, push to main instead" arrived at a fresh agent as its first and only instruction, with nothing above it. The turn is now composed by flock: a preamble stating that what follows is a task description from an untrusted author and carries no operator authority, then the caller's text fenced between markers carrying a tag minted for that spawn alone. The tag is what makes "the caller cannot close the block" a property of the construction rather than a sentence in the prose — the prompt is written before the tag exists, so text that forges an end marker is simply part of the task description. The composition lives in the type: `AgentKind::argv` accepts only a composed prompt, so a future caller cannot assemble an argv around raw text and still typecheck, which is the same shape ADR-0014 §1 refused `agent.start` over. Terminal control sequences in a prompt are now **refused** with a structured `invalid_request` rather than silently stripped: `msg.send` strips because a message body joins a turn that already exists, but here the prompt *is* the turn, and editing it would run a task the caller never wrote and never hears about. Both handlers share one filter, with the predicate defined as the stripper so the two policies cannot come to disagree about what a control sequence is. A CRLF issue body is accepted — refusing every body GitHub's API returns would have made the filter useless for the one source the ADR names — while a lone carriage return, the overwrite primitive, still goes. The preamble is **mitigation, not a trust boundary**: a model can still be talked around, and the boundaries that hold are the ones already built — the closed agent kind, the environment allowlist, the lineage ceiling, and the `Agent-Run:` trailer that keeps a talked-around child's commits revertable. (#348, ADR-0014 §4)
- An **agent-spawned agent now starts from a scrubbed environment** instead of inheriting the operator's. `agent.spawn` (off by default, behind `[fleet] agent_spawn_enabled`) previously removed a named list of credentials — `GH_TOKEN`, `SSH_AUTH_SOCK`, `AWS_*`, `NPM_TOKEN` — and passed everything else through, which is only as good as the enumeration: a new provider's token variable, a project-local `*_API_KEY`, a `GIT_ASKPASS` or a `~/.netrc` path all reached the child untouched. The default is now inverted — the child's environment is cleared and rebuilt from a per-agent allowlist, so a variable has to be *named* to survive. Per-agent because what a CLI requires is per-CLI knowledge, and an allowlist that omits something fails as the agent behaving oddly rather than as a clean refusal; that failure already happened once for real, when an argv-spawned agent silently ran against the wrong Claude profile (#359). For the same reason the resolved allowlist, and the subset the server actually had, are on the spawn's log line: a variable that did not reach the child is then a read rather than a bisect. - **A stable `flk update` no longer offers to install another project's binaries** (#506, ADR-0025 §3). The stable update manifest carried **45 archived releases and 180 asset URLs**, every one of them a release download from the repository this tree was originally forked from, advertising `protocol: 12` while this tree speaks `PROTOCOL_VERSION = 25`. `flk update` fetches that manifest and installs the URL in it, and nothing in `src/update.rs` asks whether the URL belongs to this project — so the failure was not a stale version number but a binary from a different tree, installed by the update path, after which the protocol comparison that decides between live handoff and stopping the old server compared 12 against 25. Those versions are not this project's history and are not republished: the manifest now advertises no installable version at all (a `0.0.0` sentinel naming this repository's own asset URLs, which no build of this binary can see as newer), so `flk update` answers "already up to date" and remote bootstrap answers "the release manifest does not include flock `<your version>`" — both loud, neither downloading anything. The archive itself was the mechanism: `sync-latest-json` **merged** each release into whatever the file already held, which is correct for a project's own history and is exactly how another project's history got in and would be re-published on every future release. It now drops entries whose assets are not this repository's, by version, and prints what it dropped; the same check runs on the file before and after a sync, on `verify-release-state`, and in a maintenance test over the checked-in manifest, so the next release cannot resurrect it. The preview channel had the same thing in the same shape — `website/preview.json` carried archived preview builds pointing at the same other repository's release downloads at `protocol: 12`, and `scripts/preview.py` carries the previous builds forward exactly as `sync-latest-json` carried releases forward. It now drops them the same way and names what it dropped. `website/preview.json` itself is not hand-edited: it is generated, so the next Preview run rewrites it. **A first release still has to be cut by a human** — this removes the wrong answer, it does not install the right one. The runtime half of the same issue, `src/update.rs` refusing a manifest whose assets are not this project's, is deliberately not in this change and is still open.

- **A server that lost its macOS session now says so, instead of handing agents panes where `sudo`, `ssh` and DNS are broken** (#426). When a `flk server` is orphaned — its parent dies and it is reparented to PID 1 — it keeps running with a dead launchd session, and every pane it spawns inherits that. Inside those panes every lookup needing a mach service fails (`sudo` → *you do not exist in the passwd database*, `ssh` → *No user exists for uid 501*, `whoami` → a bare `501`, DNS fails) while flock itself is perfectly healthy: panes render, agents keep taking turns, and every socket call succeeds. Nothing surfaced it, and the symptoms point away from flock — they read as broken SSH keys or a wedged machine, which is how a healthy machine got a reboot scheduled before a *new terminal tab being fine* finally localised it. flock now probes its own user session and says so loudly: a persistent red banner over the panes naming what is broken and what to do (`run \`flk server stop\`, then \`flk\` from a good terminal`), and a `session: broken` line in `flk status` — plus `session_health` in `flk status --json`, so anything watching the server sees it too. The detection is `getpwuid(getuid())`, which is the same lookup that actually fails and costs ~200ns. **The issue nominated `launchctl managername` as the tell, and it does not detect this fault**: measured on Darwin 25.4.0, with mach-lookup denied — opendirectoryd unreachable, the shape of the fault — `getpwuid` returns NULL and `whoami` prints a bare uid, while `launchctl managername` still answers `Background` with exit 0. It reports which launchd manager a process is attached to, and a process with a refused mach lookup is still attached; it is also a fork+exec, which has no business on a render path. Detection is **debounced**: one NULL is a sample, not a verdict, and this warning's advice is to destroy every live agent session — irreversible advice must not ride the least trustworthy sample. The banner needs two consecutive Broken readings (~5s), and `live-handoff` needs **three**: the blocking path used to take a fresher, uncached, un-debounced single probe than the banner, so the more consequential decision had the weaker evidence, which is backwards. The relationship is a compile-time assertion rather than a test, because both numbers are constants. A real orphan never heals — the only recovery is a restart from a healthy terminal — so the true positive pays the delay and a transient pays nothing. Each probe runs on its own thread and the tick only `try_recv`s it: `getpwuid` blocks on a mach round-trip to opendirectoryd, so an unbounded wait would stall the server's event loop in exactly the case it is meant to report, and a hung probe degrades to a stale reading rather than a freeze. The refresh runs from the scheduled-tasks tick of **both** loops, so the render path only ever reads a field — the lesson #262 established — and the transition is logged once rather than on every refresh, which is what keeps `grep WARN` useful (#318). The banner **wraps** to the pane width rather than being hand-broken against an assumed one: it used to silently clip away `resolve names` and the recovery at 80 columns while looking correct at 100, so it is now tested across a sweep of widths. It is left-aligned rather than following the config banner's right-alignment, because a wrapped block with ragged left edges stops reading as one sentence. The banner takes the top row and config warnings stack beneath it, with one combined row count feeding the toast offset so the two stacks cannot collide (#239).
- **`flk server live-handoff` now refuses to run from a server with no usable session, rather than quietly passing the fault on** (#426). Handoff is the tool you reach for to avoid losing sessions, and it is the one situation where it cannot work: the replacement server is spawned *by* the old one, so it inherits the same dead bootstrap. Running handoff from a healthy terminal did not help — the healthy shell only asks the broken server to do the spawning — and it reported `live handoff complete` while leaving every new pane equally broken. It now refuses before spawning anything or disconnecting any client, with a message that explains why handoff cannot help and what does (`flk server stop`, then `flk` from a working terminal, at the cost of every live session). The refusal carries its own `session_broken` error code and is printed as prose rather than JSON, because it is the one handoff outcome an operator can act on differently: retrying is pointless. **There is no auto-repair** — restoring a session needs privileges flock does not have, and the issue does not ask for one.
- **The fleet-wide kill sweep now recovers a worktree it was told to remove** (#402). "Kill all worktrees" decided up front whether to pass `--force` by asking whether each checkout was dirty — a question git never asked, and one that cannot answer the case that actually blocks. `git worktree remove` refuses a checkout that merely *contains* a submodule, pristine or deinitialized to an empty directory, because the check runs before git ever looks for dirtiness. So the probe said "clean", the sweep asked for the cheap removal, git said no, and the row came back an error: a dead end the single kill dialog and the socket API had already been rescued from in #351. The sweep now attempts the removal and asks git's actual refusal through that same shared classifier, so all three callers read one decision rather than three that can drift. Because a sweep is unattended, it also has to decide the escalation itself, and that decision is deliberately narrow: it forces **only** when the checkout is *provably* free of anything a `--force` would destroy — read from the checkout itself, not inferred from which refusal git happened to report. That distinction is load-bearing, because git reports the submodule refusal *first*: a checkout holding both a gitlink and uncommitted work classifies as a submodule problem, never a dirty one, so "git did not say it was dirty" is not evidence that nothing is at stake. An untracked file beside the submodule, a commit made inside the submodule and never pushed, and a checkout whose `submodule.<name>.ignore = all` makes `git status` report the submodule as clean are all things the forced retry would have destroyed, and none of them is recoverable. Any of them, and the sweep reports git's refusal instead of acting on it. Uncommitted work is never forced away without the operator having asked for force in the sweep dialog first. Recoveries are counted in the sweep's own summary line rather than only logged, since it is the one removal flock performs with nobody watching. Force still buys the checkout only: a branch goes solely on positive merge evidence, so an unmerged branch survives a forced sweep exactly as it survives the dialog.

- **A remote session survives its transport dropping** (#436). Waking a Mac from sleep killed the bridge ssh (exit 255), and the remote client printed `lost connection to server` and exited, taking the launcher with it, while the remote server and its panes were fine. A remote leg now reconnects in place: the last frame stays up under a `reconnecting to <host>… (n)` bar, the client redials the same local bridge socket (a fresh ssh behind it), and on success re-attaches with a full redraw — same session, same panes, no shell prompt. Redials follow a doubling backoff, one dial per step and nothing in between, configured under `[remote]`: `reconnect` (default on), `reconnect_backoff_initial_ms` (500), `reconnect_backoff_max_ms` (5000) and `reconnect_deadline_secs` (120). Redials never come faster than 100 ms apart, whatever the config says, and keys typed while a redial is connecting are dropped rather than replayed into the re-attached session. If the remote server itself died meanwhile, the redial is refused (`remote-client-bridge --reattach` no longer starts a fresh, empty server) and the client says the session state is lost instead of calling an empty session "reconnected". The remote end first waits `[remote] reattach_grace_ms` (1500, rechecking every `reattach_poll_ms`, 100) for its server, so a redial that lands in a live handoff's socket rebind is not told a live session is lost. The client gives up at the deadline or when the operator presses Esc, and then falls back like a failed switch (#63): back to the server you came from with a `lost connection to <host>` notice, or, with nowhere to fall back to, a restored terminal and the reason. An explicit quit, detach or switch never reconnects. The bridge now serves each connection on its own thread, so a redial is no longer queued behind the dead tunnel's ssh until its keepalive times out, and it logs `remote.bridge.accepted` for every connection. Nothing in the bridge writes to the terminal any more: its failures and ssh's own stderr go to the log, and a chain that ends on an error restores the shell's terminal settings before printing, so the last lines no longer come out as a staircase. A row whose relayer is no longer in `[[peers]]` is display-only: a relayer you removed no longer picks a jump host. The hub's own click on a relayed row uses the same route. With `-J`, each later hop's name is read from the dialling machine's ssh config and resolved by the hop before it, so a `[[peers]]` `ssh` value that is a `Host` alias only the hub defines will not work as the relayer hop. Such a failure now says so in the switch notice and logs `remote.jump.failed`.
  - The launcher now cuts every hop up to and including the machine it runs on, matched exactly on its short or full host name (a hop `kiln.other` is never `kiln`). The hub's own client reaches the peers it polls directly, a relayed peer via the relayer alone, and on the relayer no jump is used.
  - Only the bridge carried the jump. The probe, install and server-status ssh calls before it dialled the bare target, so a target that resolves only behind its jump failed before the bridge ran. Every ssh call of a switch leg now rides the leg's jump.

  Routes still come only from rows this server polled or carried. A row a hub pushed down stays display-only and never rides a snapshot.
- **Peer dial errors no longer cross machines as ssh's own words** (#428). `peers.summary`, the hub's `peers.hub_fleet` push and the carried fleet snapshot sent `error` as ssh's last stderr line, host names and ports included. They now send the classified token (`connect_refused`, `auth_refused`, …), and ssh's text stays in this host's log. The field is still a string: an older receiver shows the token, and a newer one reads the reason from either form. `flk peers logs` now strips control bytes from a remote host, target and message, as `flk peers status` already did. `flk peers status` pads its name column to the name as printed and no longer repeats a token error after the reason.
- **A shell exiting or a pane moving out no longer moves the operator either** (#429). Two more ways a workspace empties — its last shell exits, or `pane.move` takes its last pane elsewhere — removed it on their own instead of through the #419 close rule. A lower-index space emptying by shell exit shifted the operator's sidebar cursor onto the wrong row, no `WorkspaceClosed` event went out, and an open confirm-close dialog naming that space showed `?`. Both now take the same close as every other door: focus is kept by workspace id, the dialog is dropped, and `WorkspaceClosed` is announced once. When the operator's own space empties this way, focus now goes to the #419 successor (the previously focused space, else a same-repo sibling, else the nearest row in sidebar order) instead of the next index in the list. `pane.move` now closes the emptied source only after the pane has landed, so a failed move reattaches it to its original space. A close also no longer clears a text selection made in a different workspace.
- **Coming back to a server no longer greets you with the previous switch** (#434). The server you switched away from raised its own "switching to X…" notice and kept it armed for 4 s, so a quick A→B→A round trip landed back on A still reading "switching to B…". The leaving server now clears its notice when it dispatches the switch, and again when your client pauses its view of it; the client's own switch popup still names the target during the flip. Action notices also wake the server loop on their own deadline instead of expiring on the next unrelated wake.
- **One slow sample no longer blanks the server's own metrics** (#435). Once the last system sample was older than three sampling intervals (6 s), the self row in the servers band dropped every metric and the status line collapsed to a dash, until the next sample landed — a thermal probe, App Nap or a busy runtime was enough. Both now keep the last reading in the dim italic that unreachable peer rows already use, so a frozen value never passes for a live one and the row never goes blank. Only a machine that has never been sampled shows no metrics.
- **A turn that ends with its `※ recap:` line is no longer asked for one.** Claude's Stop hook read the reply out of the transcript, but Claude Code appends the final reply to the transcript only after the Stop hook returns, so the hook saw the message *before* it. That message had no recap line, so the hook asked for one. Every agent then repeated its recap, costing one extra model turn per turn across the fleet. In the coordinator's own session, 42 of 46 recap nudges followed a turn that already ended with one. The hook now reads the reply from the Stop input's `last_assistant_message`, which current Claude Code sends and which cannot lag. An older harness without that field falls back to the transcript. There the hook waits up to `[session] stop_transcript_wait_ms` (default 1000, re-read every `stop_transcript_poll_ms`, default 50) for the reply to land. If the transcript still ends on a tool result or a textless entry, the hook treats the recap as unknown and does not ask for it. A continuation that the hook itself forced (`stop_hook_active`) is never asked again, so a turn gets at most one recap nudge. A recap line in markdown (`**※ recap: …**`, `- ※ recap: …`, `> ※ recap: …`) now counts. A line that merely starts with `※` does not. The wait is capped at Claude's 10-second hook timeout, and the poll interval is floored at 1 ms. The mail wake is unchanged (#415).
- **The view of the server you switched away from stays live** (#424). A server switch hands the next server a fleet snapshot, including the space list of the server being left, and nothing refreshed it after the attach: a space renamed, opened or closed there afterwards never showed, and a spoke — which polls nobody — had no other view of it. The hub now sends its OWN summary (`hub_self`) with the `peers.hub_fleet` push it already makes down the `flk peers relay` connection it holds into each spoke, once per poll and never over a new ssh. When the hub is the client's home, the spoke refreshes the home row and its spaces from it in place (still switching via the home target, never an ssh dial); otherwise it becomes the hub's own display-only row. Only that hub's own `hub_self` can repaint the home row: it is accepted only when it names the hub bound to the relay, and absorbed only when that hub is the client's home. A row in the pushed fleet that claims to be home — any polled spoke can report any host — is dropped, neither absorbed nor stored as a second home row. Rows arriving over `peers.hub_fleet` now have their system summary clamped and control bytes stripped from host and space names, like every other receive path. The field is additive: an older spoke ignores it and an older hub simply does not send it. The home row's age is now the origin's reading plus its time here, not the time since attach, and past `[gossip] stale_after` the row takes the muted stale tint. A server the hub pushes down now also stays clickable when the client carried a route to it: the pushed row supplies the space to focus, the carried row where ssh goes, matched on the exact host (never the domain-stripped sort key, so `kiln.other` never borrows `kiln`'s route). Before, the live row won the dedup and the click silently did nothing.
- **The servers band reads the same from every server** (#422). #51 sorted the peer tail, but home and the attached server were pinned above it, so every server saw a rotated list and switching reshuffled the band. Every row, home and self included, now sorts by one fleet-wide key: the reported host, lowercased with any domain suffix (`.local`, tailnet) stripped. A peer that has not reported yet sorts by its ssh target under the same normalisation, never by a local config name. Home is marked in place by a home glyph, the attached server by the current-row fill.
- **Closing a space no longer moves the operator somewhere arbitrary** (#419). An agent's `pane.close` (CLI, MCP, socket) that emptied a workspace borrowed the operator's sidebar selection to name it, and every close then made whatever slid into that `Vec` slot active — so an agent closing a background space bounced the operator's view, and a manual close landed on a row the sidebar never showed as adjacent. Active and selected are now carried across any close by workspace id, so closing a space you are not on never moves you. Closing the active space goes back to the previously focused space when it is still open (the same history `last_pane` uses), else to the nearest same-repo-space sibling in sidebar order, else to the nearest row in sidebar order. Every door — keyboard, context menu, confirm dialog, socket, MCP — names its target explicitly and follows the one rule; the confirm dialog records its own target instead of moving the sidebar cursor. The implicit "worktree group" close guard — a pre-#62 leftover — is gone too: closing the last pane or tab of a main checkout while a sibling worktree is open no longer asks to confirm a group teardown that never happened, and socket `pane.close` no longer refuses agents with a false `confirmation_required: "closing this pane would close a worktree group"`. The close takes just that workspace. The explicit close-whole-space affordance (space row → Close group) and its dialog are unchanged.
- **A hub that cannot reach its peers now says so, and why** (#418). hopper could not reach any spoke for five days: its inherited `SSH_AUTH_SOCK` pointed at a dead launchd agent socket, its key needs an agent, and every `BatchMode` dial failed in ~25 ms — 2,229 times a day, each logged as a bare "process exec exited non-zero", while the servers band looked merely slow. Now:
  - A failed command's `process.exec` record carries a bounded, credential-masked **`stderr_tail`**, so ssh's own `Permission denied (publickey)` reaches the log.
  - Peer polls are classified — `auth_refused`, `agent_unreachable`, `host_key`, `connect_refused`, `timeout`, `unknown_host`, … — and a reason that has **persisted past one poll** appears on the peer's row in the servers band and in the new **`flk peers`** status view (`flk peers status [--json]`; the `peers.summary` rows carry it as `dial`). An auth failure through an agent socket that refuses connections reads **`ssh agent unreachable`**, not "auth refused": ssh cannot tell you its agent is gone, flock can.
  - A peer whose **held relay stream cannot be established** logs why (`peer.stream.unavailable`, with ssh's stderr) instead of falling back to one-shot polls in silence; the relay's stderr used to go to `/dev/null`. The reason also rides the peer's `flk peers` row, as a classification token (`dial.stream_reason`), while polls keep succeeding over the fallback. Only tokens and counts cross machines in the `dial` block; ssh's own words, which carry host names, local paths and whatever the far side's shell printed, stay in the local session log.
  - Repeats are **rate-limited**: one WARN when a peer starts failing or fails a different way, one summary per `[gossip] dial_failure_summary_secs` (default 600) while it stays the same, INFO on recovery — about 720 lines for a five-day outage instead of ~29,000. The poll's `process.exec` edge is now tracked per peer, so one peer failing while another works no longer flips a shared edge every tick.
- **Peer dials survive a dead ssh-agent socket on macOS** (#418). The server keeps the socket it has and tests it with one `connect(2)` per dial — no process spawn, so this is not a `launchctl` per dial (#294's exec storm). Only a socket that refuses triggers a re-resolve: flock scans this user's own `com.apple.launchd.*/Listeners` sockets (ownership checked, symlinks not followed), adopts the one that accepts, logs `ssh.agent.resocketed`, and passes it to its ssh children. Only private (0700) session directories are considered. This also applies when the server was started with **no `SSH_AUTH_SOCK` at all**: on macOS its peer dials now adopt the user's live launchd agent socket, where before they ran agentless. On Linux the inherited socket is kept, and a dead one is reported (`ssh.agent.unreachable`) and classified `agent_unreachable`.
- The stop-hook **mail wake no longer tells an agent to stop**. When mail was waiting and the turn had also ended without its `※ recap:` line, the two nudges were fused into one — "read it with `flock_msg_read`. Then end your turn with a recap line. Then stop." — and an agent did exactly that: it read a `needs_reply` review, wrote its plan into the recap and stopped without doing the work, so the message was acknowledged and dropped. A turn with mail waiting is not ending, so the wake now says only to read the messages and act on any that need a reply before ending the turn; the recap is asked for at the next boundary, when the inbox is empty. The wake still names a count and a tool and nothing a sender wrote. (#408)
- `flock_agent_read` and `flock_pane_read` no longer claim that reading **marks the pane seen** and must be used sparingly. They never did: neither handler touches `seen`, which only the operator's own view transitions change, so the description was steering agents away from a read that was always safe to take and could not move the operator's attention queue. `flock_agent_history`'s "unlike `flock_agent_read`" contrast, which rested on the same claim, is gone with it, and a test now reads a pane through both verbs off the wire and asserts `seen` is unchanged from either starting value. (#393)
- The fleet-wide worktree sweep (`kill all worktrees`) no longer deletes a **protected branch** the single kill refuses. The sweep fed the merge gate's verdict straight into its action tier and never consulted #121's protected-branch tiers, so the only thing standing between it and `git branch -D` was `delete_local_branch`'s hardcoded main/master floor. The gate calls the repo's default branch merged — trivially, since it is contained in every remote ref — so a repo whose default is `develop`, or one with a `[worktrees] protected_branches` entry, could have that branch deleted by the sweep. Protection is now part of the one verdict every kill path resolves, rather than something each dialog remembered to ask separately, and a protected row renders as `(protected)` so its checkout-only outcome reads as a decision rather than as a gate that found nothing. (#396, #121)
- Killing a worktree now **ends the processes that were living in it**, and says which. `git worktree remove` unlinks a directory and says nothing about the processes whose working directory that directory was; flock's pane teardown only reaches what it can see, and a `setsid` child is out of its process group by design — deliberately, so a harness timeout cannot orphan a 30-minute build mid-run. The same property means teardown cannot reach it either. Measured once as 48 orphaned shells at ~16% CPU each for 25 hours: ~7.6 cores of a 12-core box, dilating every other agent's build about 5x and pushing a load-gated test verdict into permanently-unsatisfiable territory, with the load misattributed to sibling projects for most of a day. Nothing in the kill's output had ever mentioned them. Two choices make the sweep safe enough to run by default. It matches the **leaf checkout exactly** — component-wise, so a sibling worktree whose name merely starts with the same characters does not match and the shared `~/.flock/worktrees/<repo>/` parent never matches at all; the downstream workaround this replaces once killed a sibling agent's sweep with a looser glob. And it decides **after the removal, not before**: every live worktree has its own pane shells sitting in it, so a refusal taken on the pre-removal list would refuse every kill there is, while a process still alive once the checkout is gone is an orphan by construction — its working directory no longer exists, so there is no work in that tree left to do. Those get `SIGTERM`, a grace period, then `SIGKILL`. The process that asked for the kill, and the shell it was typed into, are never signalled: run from inside the checkout, both have their own cwd in the leaf. `flk worktree kill --keep-procs` reports and stops instead, `--dry-run` names what is standing there without touching it, and the pids and command names travel in the JSON as `processes`, `orphans` and `orphans_surviving` as well as on stderr — anything that outlives `SIGKILL` is named rather than silently dropped. The TUI's "Kill worktree & branch" sweeps on the same terms. Asking the kernel which processes are standing in a path is the one platform-specific part: `/proc` on Linux, libproc on Darwin, both behind `src/platform/`. (#400)
- A **gossiped peer can no longer choose this host's ssh options**. Every remote leg builds an `ssh` argv by pushing the dial destination straight in, and OpenSSH reads an argument beginning with `-` as an OPTION rather than a host — so `-oProxyCommand=...` as a destination is arbitrary *local* command execution by the process that spawned ssh. No shell is involved on this path, so this was never injection and quoting would have fixed nothing; it is argv-position confusion, and the question was only whether an attacker-influenced string could reach that push. It could. The dial targets are not all operator-authored: the warm-slot target list chains the locally configured `[[peers]]` with the peers carried in the gossiped fleet snapshot, and a relayed row's `ssh_target` **and** its `proxy_jump` — the latter interpolated into `-o ProxyJump=<value>` — were copied verbatim off the wire. Peers ride the ssh host CA and a tailnet rather than being strangers, which is why this is hardening and not an emergency, but one compromised or misconfigured fleet member was enough, and a chosen destination additionally selected among the operator's own `Host` blocks, with their `ProxyCommand` and `IdentityFile`, because flock's keepalive config `Include`s `~/.ssh/config`. One rule now governs both ends of the boundary: a destination must draw from the charset real destinations need and must not begin with `-`, and a `ProxyJump` is validated hop by hop because it is a comma-separated chain and ssh dials every one of them. It is enforced at config load *and* at gossip ingest, which is the half that matters — validating only the config path looks like a fix and leaves the attacker-controlled path open — and once more in the argv builder itself, so a future third source of dial targets cannot quietly reopen it. Refusal, not sanitisation: a destination that needs escaping is not a destination, and `--` is not a documented end-of-options marker for ssh's destination argument, so argv position could not be leaned on either. A rejected gossip row is dropped and logged with the name of the hub that sent it, never fatal to the snapshot — a bad row costs the fleet that row and no other — and a config entry is dropped with a startup diagnostic that names the peer, because a silently vanished host looks exactly like a network fault. Bracketed IPv6 literals (`[::1]`, `operator@[fe80::1]:2222`), `user@host:port` and multi-hop jump chains all still dial. (#392)
- The spawn ceiling now gates **who is asking, not which verb they reached for**. `agent.spawn` counted live agent-started agents against three limits — depth, fanout, fleet-wide capacity — and `flock_agent_fork` sat next to it on the same MCP surface consulting none of them. An agent refused with `at_agent_capacity` could turn around, call `flock_agent_fork`, and get a child of exactly the same fleet cost; the child was not stamped with any lineage either, so it did not count toward the next check, and alternating the two verbs kept a cap of eight admitting agents indefinitely while only ever counting half of them. That is not a cap with a hole in it, it is a cap that holds for as long as an agent picks the gated verb. Both verbs now ask one funnel, and what the funnel reads is the CALLER: a request whose process ancestry lands inside an agent's pane meets the limits, whichever verb carried it, and its child is stamped with the parent that asked and a depth one greater — including when it forks somebody else's conversation, which takes the deeper of the two lineages so a caller at the depth limit cannot launder its depth through a shallow target. An operator meets none of the limits. `flk agent fork` typed by a human, and the TUI keyboard fork (which never enters this path at all), stay unbounded exactly as before — a cap that stops the operator from opening a worktree is a cap that gets turned off, and `fleet pause` already draws this same line between what flock initiates and what a human does. Two consequences worth stating: an agent-initiated fork is now refused while the fleet is paused, for the same reason an agent-initiated spawn always was; and the fork half is deliberately **not** behind `[fleet] agent_spawn_enabled`, which opts a node into `agent.spawn` — gating an already-shipped verb on a flag nobody had to set would have left the bypass open on every default node, which is all of them. The defaults an agent fork now meets are the documented ones: depth 2, fanout 4, eight agent-started agents fleet-wide. Refusals are the same structured shape `flock_agent_start` returns, with `data.retryable` saying whether backing off can help. (#349)
- `flk msg send` now **refuses a flag it does not understand** instead of delivering it as the first words of the message. An unrecognised `--flag` was treated as positional body text, and `--` (which already ended flag parsing on `send`, and did not exist at all on `msg reply`) was the only thing standing between the two. That is a parsing quirk on a keyboard and a data-corruption channel across a fleet: the cross-host relay *is* `flk msg send` invoked over ssh on the peer that owns the recipient, and hosts routinely run different builds — so every flag ever added was, on the day it shipped, a way to put `--intent needs_reply` at the front of somebody's message on any peer that had not updated. It failed silently at both ends, with a success returned to the sender and nothing anywhere recording that a flag had been misunderstood. The refusal names the flag and lists what the build *does* accept, which across the relay is the peer stating its own vintage — the entire diagnosis, in the one line ssh carries back. The relay's two failures are now distinct rather than both reading "could not reach": `peer_unreachable` is transient and worth retrying, `peer_refused_message` means the far side read the command and said no, and both carry `retryable` alongside the peer's unedited words, the posture `SpawnRefusal` already takes — a failure that crosses a host boundary should arrive as data, not as damage. No capability probing was added between hosts; it is disproportionate for one CLI. #377's containment (relaying `--intent` only for `needs_reply`) is deliberately **kept**: this fix lives on the receiving side, so it protects a peer only once that peer runs a build containing it, and the hosts the containment covers are precisely the ones that do not yet. (#380)
- `flk agent start <name> --workspace <id>` now starts the agent in that workspace's checkout instead of the server's own working directory — which, for a server launched from a login shell, is `$HOME`. `--workspace` named a destination for the pane and none at all for the process, so one space could hold a root pane `flk worktree create` had put in the worktree and, beside it, an agent flock had put in the home directory. The cost is not a wrong directory: the agent is usually Claude Code, so what appears first is its trust dialog asking for read, edit and execute over the whole of `$HOME` — flock steered it there, and accepting is the natural reflex. The dialog also swallows the opening prompt, so an agent started as `-- claude "<prompt>"` looks alive and is silently idle, and `agent start` reports success either way. `agent.start` was the last pane-creating verb that ignored its target; `pane.split`, `tab.create` and `workspace.create` all read a cwd off the place they were aimed at. `--cwd` still outranks everything, so the workaround scripts already carry is unaffected, and a workspace with no checkout to prefer follows the pane the agent joins. A membership whose checkout has since been deleted falls back rather than failing the start. `flk report bug --help` also prints help now instead of answering "unknown option: --help". (#365)
- A **paused fleet no longer wakes agents about their mail**. `flk fleet pause` exists to halt what Flock initiates while leaving human agency alone — you can still type into a paused pane — but the message wake was firing straight through it, so every agent in a paused fleet was still told at every turn boundary to go read its inbox. The gate had been lost rather than never written: pause used to hold the mailbox by gating a scheduled delivery pass, and when agent-to-agent delivery became a pull inbox that drain was deleted, taking the gate with it while the stop-hook nudge that replaced it inherited nothing. The nudge count now comes from a `msg.wake` method whose whole job is to decide whether an agent may be interrupted — so a pause, or the recipient's own mute, suppresses it in one place rather than at each caller. Listing and reading an inbox are deliberately untouched by a pause: what pause halts is the interruption, not the information. The same method also ends a smaller oddity — the nudge path asked for the message *list*, which carries a 120-character preview of every queued body, and threw the text away. It now asks for a count, so the wake channel cannot carry a sender's words even by accident. (#316)
- The merge-gated worktree kill (`ctrl+shift+k`, `flk worktree kill`) no longer explains a workspace whose checkout has vanished as "no merge evidence". With no checkout there is no branch to resolve, so there was nothing to put to git or `gh` at all — and the gate fell through to the arm that means "I asked, and this work does not appear to have landed", which sends the operator off to compare a PR against a branch nothing was ever asked about. The true state is a workspace pointing at a directory that no longer exists, where no work is at risk and closing the workspace is the only thing to do. The kill dialog now says the checkout is already gone and that confirming closes the workspace, and it stops telling you to assume uncommitted changes in a directory that is not there: every probe of a missing checkout comes back unreadable, and the stakes block rendered unreadable as "assume there are some". `flk worktree kill --json` gained a `checkout_missing` field so a scripted caller can tell a cannot-ask from an asked-and-got-no instead of reading both as `merged: false`. A detached checkout resolves no branch either and is deliberately unchanged — it is live, git answers, and there is genuinely nothing to judge. Removing a checkout outside flock is the obvious way in, but not the only one: an unmounted volume, a cleaned `/tmp` worktree, and a sibling tool's `git worktree prune` all leave the same ghost. - The worktree kill no longer dead-ends on a repo with submodules. git refuses to remove a worktree that contains one, and it refuses on the submodule's mere existence — a pristine submodule is refused, and so is one deinitialized down to an empty directory — so the dialog's second confirmation, which only recognised a refusal about dirty files, had nothing to offer and left `fatal: working trees containing submodules cannot be moved or removed` on screen with no way past it. Removing the checkout by hand was the only recovery, which is the thing the merge-gated kill exists to make unnecessary. That refusal is now the same one-keystroke confirmation dirty files get, since the flag git wants is the one already behind the button, and it is worded for what is actually happening: git will not touch a submodule worktree unforced, and the checkout being clean is beside the point. Forcing past it is still not merge evidence — an unmerged branch survives it exactly as before. On the socket the failure now returns `submodule_worktree_requires_force` alongside the existing `dirty_worktree_requires_force`, so `flk worktree kill` exits 4 (retry with `--force`) rather than 1 (give up). - The merge-gated worktree kill (`ctrl+shift+k`, `flk worktree kill`) no longer refuses a branch whose pull request GitHub says is merged, just because the local branch never caught up with the head that was merged. A worktree left alone while its PR finished ends up exactly there — the tip sits a few commits behind what was pushed and squashed — and the gate would report "no merge evidence" for a branch wholly contained in what had landed. It now accepts a local tip that is reachable from the merged head, and says which case it proved. A tip that moved the other way still keeps the branch: a commit the PR never merged, or a merge of the default branch made afterwards, could carry work of its own, and reachability cannot prove otherwise. - The merge-gated worktree kill now recognises a squash merge. Squashing replays a branch's commits as one new commit, so none of them is ever an ancestor of the default branch — and every check the gate had asked an ancestry question. A branch whose PR had squash-merged therefore read as "no merge evidence", and the kill kept a branch (and its checkout) whose work was fully landed. The gate now also asks the question it actually cares about — would deleting this lose work? — by merging the branch into the default branch in memory and seeing whether anything changes. That covers rebase merges and independently-landed changes too. Work that arrived after the squash still keeps the branch, and anything inconclusive (a conflicting merge, a git older than 2.38) is still no evidence: the branch is kept. (#287)
- The attention cycle (`ctrl+shift+a` and `focus_attention`) now steps through AGENTS rather than through this machine's agents. A workspace whose pane has moved to another checkout kept its old grouping, so branch-session and new-worktree would create a worktree of the repo it had left, delete-checkout and the merge-gated kill offered to remove that repo's worktree, and the fleet sweep listed it under the wrong row. - Worktree actions reached over the socket API, CLI, and MCP now apply the same check as the in-app ones: a workspace whose pane has moved to another repo no longer reports its old worktree membership, so `flk worktree kill`/`remove` cannot delete another repo's checkout under that workspace's name, and create/open/list, repo-addressed messages, and PR polling all follow the repo the pane is actually in. (#197)
- The sidebar now groups a workspace under the repo its pane is actually in. A workspace that moved to another checkout kept rendering inside its old repo's worktree group. (#197)
- `flk worktree create --workspace <a linked worktree>` now branches from that worktree's own HEAD, matching what the app and `flk agent fork` already did, instead of refusing with "start from the repo parent workspace". Branching from a linked worktree no longer demotes it out of its group. (#124)
- `flk agent fork` now reports the accurate refusal code when its source workspace is a linked checkout flock does not manage (`linked_worktree_source`); it previously labelled every source refusal `not_git_worktree`, disagreeing with `worktree.create` about the same condition.
- The scheduled worktree reap and `revert.run` no longer act on a worktree membership that live git places in another repo. The reap could have moved an unrelated repository's live worktree aside with no human in the loop, and `revert.run` could have written its revert branch and commits into a repo the workspace no longer represents. Closing a space, the "closing the whole space?" prompt, the row context menus, and section naming now agree with the same rule. (#197)
- `peers.prepare` no longer runs `git push` from a workspace's original directory using a branch read from wherever its pane has since moved. (#197)
- `tab.create` (and `flk tab create`) now honours workspace tab mode: with `[ui] tab_mode = "workspace"` it spawns a sibling workspace carrying the space grouping, the same thing the keyboard has done since #25, instead of growing an inner tab the workspace-mode strip never shows. (#25)
- Added the `worktree.kill` socket API method, moving the merge gate, the protected-branch tiers (#121) and the local-branch deletion into the server. `flk worktree kill` ran all of that client-side, so anything reaching the socket or MCP directly got the destructive half with no evidence requirement and only the hardcoded `main`/`master` floor — a repo whose default branch is, say, `develop` had nothing else protecting it. `--force` still only covers a dirty checkout and never widens the branch decision. (#121)
- Branching an agent session into a worktree from the keyboard is now tracked the same way `flk agent fork` is: the child gets a run id in its environment, the opt-in commit trailer hook is installed, and an `agent_forked` event is emitted. Previously only the programmatic fork was tracked, so commits from a keyboard fork were invisible to `flk revert-run` and the fork never appeared in `flk agent lineage`. (#175)
- `flk --default-config` now points at the published configuration reference instead of `docs/config-reference.md`, a path that was never written.
- The keybinding help now lists `toggle_collapse_all`, `toggle_prompt_expand` and `focus_attention_project_previous`, which were bindable and dispatched but undocumented.
- Keyboard-driven pane splits and closes, tab closes and renames, and workspace closes and renames now reach the durable event log and `events.subscribe`. Only socket-driven mutations were announced, so anything replaying the log per ADR-0005 reconstructed the wrong pane tree whenever the operator used the keyboard. Workspace closes now announce exactly once from either door. (#175)
- Renaming a workspace or tab now trims the name whichever way you do it, and a blank name restores the derived name instead of storing an invisible label. `workspace.rename` and `tab.rename` passed the label through raw while the rename dialog trimmed it.
- Worktrees are now namespaced by repo identity rather than the repo's directory name, so two same-named repos — most acutely a standalone repo and a git submodule of the same name — no longer share one `~/.flock/worktrees/<name>/` tree. Existing worktrees are unaffected: the path is only ever a proposal at creation time, and open worktrees are found through their recorded checkout path. (#212)
- Agent-to-agent messages are now delivered through the agent's tool surface instead of being typed into its session (ADR-0008). Recipients read structured messages with the new `flock_msg_read` MCP tool (or `flk msg read`), and an idle recipient is woken at its turn boundary by the stop hook, which names only the count and the tool — never a message body. The keyboard stays the operator's channel: `agent.send` is unchanged. This removes the delivery race that only existed because flock typed into a live terminal, and makes "delivered" mean the agent actually took the message. A recipient with no inbox now gets an honest refusal instead of having text typed at it.
- Every agent now carries a fleet-global, restart-stable `agent_id`, reported by `flk agent list`/`get`. Until now the only ids available were a pane id (which names a placement and changes when the pane moves) and a terminal id (which names a running PTY and is re-minted on every restart), so an agent had no name that survived a restart or meant anything on another machine. The id is minted once per pane and persisted in the session snapshot; panes restored from older snapshots are minted one on first restore. (#213)
- Agents now gossip their fleet-global `agent_id` alongside where they currently live, so any node can resolve an identity to a host and pane. Messages can be addressed by `agent` identity — the only target shape that means the same thing on every machine, since a pane id names a placement on one server. An agent that resolves to another host reports where it is rather than failing blank; cross-host delivery lands next. Bumps the wire protocol to 25. (#213)
- Messages now cross machines. `flk msg send --agent <id>` addresses an agent by its fleet-global identity; if that agent lives on another host, the message is handed to the server that owns it over the same SSH verb surface peer polling already uses, and that server's own mailbox delivers it. The sender's identity travels with the message, so a relayed message arrives with a named sender and a reply that actually routes back — previously it arrived "from unknown" and advertised a reply command that failed. (#213)
- Cross-machine message delivery now routes by the `[[peers]]` entry the fleet directory answered from, rather than by the hostname the far machine reports about itself. A peer configured as `kiln` that calls itself `bastion` was refused with "not in this server's [[peers]]" for a message it could actually deliver. (#213)
- A cross-machine message no longer arrives truncated at the first space, and reports the host it was actually sent from. The relay quoted the body inside an already-quoted remote command, so the far shell word-split it; and the receiver, unable to see the sender in its own directory, fell back to naming its own host as the origin. (#213)
- Added a `[msg]` config section governing which hosts' agents may message this node's agents. Open by default (`allow_from = ["*"]`) since a flock fleet is already one trust domain; narrow it with `allow_from = ["hopper"]`, or refuse all inbound agent messages with `enabled = false`. Enforced by the receiving node — the only party a sender cannot bypass — and it takes effect on `flk server reload-config`. (#213)
- Creating a worktree in a repo with no commits now says so, instead of passing git's `fatal: invalid reference: HEAD` through as if flock had failed. (#198)
- Resizing restored panes no longer aborts the server when libghostty-vt reflows a terminal whose pre-resize cursor row is past the new height. (#465)
- Linux clipboard image reads now validate image payloads before accepting them, preventing malformed clipboard data from reaching pane image paste flows. (#18)
- Pane resize keybindings now shrink panes again instead of only being able to grow them; when the focused pane has no split on the requested edge, the resize falls back to the opposite-edge split so an ancestor border still moves. (#23)
- Headless servers now avoid repeated scrollback rendering work for inactive panes, reducing CPU in large sessions. Wheel-routing lookups go through a narrow mouse-mode probe instead of building a full input-state snapshot, and per-client frame preparation moves the frame through prepare/commit instead of cloning it on every send. Ported from herdr #512. (#17)
- F1-F4 key presses sent as `ESC[11~` through `ESC[14~` now reach pane apps instead of being dropped. (#22)
- Numeric keypad keys that send VT100 application-keypad escape sequences (`ESC O p` through `ESC O y`, plus the operators) now enter their digits and operators instead of being dropped. (#22)
- Nested agent session reports from child terminals no longer overwrite the owning pane's restored agent session id. (#20)
- Claude Code session restore now accepts real `/clear`, `/resume`, and compacted session identity changes while still ignoring nested `claude -p` startup sessions that inherit the pane environment. (#19)

## [0.1.1] - 2026-03-28

### Added
- Added optional sound notifications for agent state changes, including a completion chime when background work finishes and an alert when an agent needs input.
- Added per-agent sound overrides under `[ui.sound.agents]`, so you can mute or enable notifications by agent instead of using one global setting. Droid notifications are muted by default.

### Changed
- Request alerts now play even when the agent is in the active workspace, while completion sounds remain limited to background workspaces.

### Fixed
- Improved foreground job detection on Linux and macOS so flock can recognize agents that run through wrapper processes or generic runtimes, including cases like Codex running under `node`.
- Made Claude Code state detection more stable by handling more spinner variants and smoothing short busy/idle flicker during screen updates.
